## きっかけ

2026-11-24、ツールの設定をパターンにしたい(「読み込みのみ」のようなものを作ってプロファイルに付ける)→ 配布プロファイルを強制できるか → 管理側にとって大事なのは
**「利用者にこれしかやらせない」こと**で、ツールだけでなくモデルや使用量まで含めて実現したい(ユーザー)。そこで、パターンを仕様にする前に、制限の全体を見渡した。

## まず前提:どこで守らせられるか

制限は、**判定と実行がサーバーにある道でしか本当には守れない**(0018 の「守らせられる場所」)。

| 道 | 生成 | ツールの実行 | 守れる制限 |
|---|---|---|---|
| ブラウザの会話 | サーバー | サーバー | 全部 |
| aibow-server につないだアプリ | サーバー(OpenAI 互換の口) | **アプリの手元** | モデル・トークン・使用量はサーバーで守れる。ツールは「アプリが守る約束」 |
| API キー(Cline など) | サーバー(OpenAI 互換の口) | クライアント | モデル・トークン・使用量だけ。プロファイルの考えが無い |

→ 「これしかやらせない」を本気でやるなら、制限は**プロファイルではなく利用者の側**に付ける必要がある。API の口にはプロファイルが届かないため。

## 今あるもの・足りないもの(2026-11-24、Chat が `profile.go`・`rules.go`・`tools.go` を読んで確かめた)

| 何を | 今あるもの | 足りないもの |
|---|---|---|

| モデル | サーバー全体の「使えないモデル」(`server-models.json`。0018)・プロファイルでモデルを固定 | 人・グループごとの使えるモデル。API の口は、サーバーで使えるモデルなら何でも選べる |
| ツール | 管理者の禁止(`server-tools.json`。全員・ブラウザとサーバーの MCP)・プロファイルの「使えない」と、グループの固定 | 人・グループごと。ツールごとの「使う」の固定。確認の扱いを配る側で決める(今は PC ごと)。パターン(下の「ツールの設定のパターン」) |

## まとめ方の案

### 案1:利用者の「枠」を作る(Chat のおすすめ)

プロファイルとは別に、**「何をしてよいか」の上限を名前付きでまとめたもの**(仮に「枠」)を作り、利用者の側に付ける。

- プロファイル = 「どう使うか」の既定(値)。枠 = 「どこまで使ってよいか」(上限)。0014 の「値は写し、決まりは参照」の、決まりの側を利用者に移す形
- 枠に入るもの:使えるプロファイル(配布のものだけ / 指定したもの)・使えるモデル・ツールのパターン(枠の部品になる)・トークンの上限の上限・使用量の上限・API キーを使えるか
- 判定の順:サーバー全体(管理者)→ 利用者の枠 → プロファイルの決まり → 会話の上書き。どの段も「狭めることしかできない」
- 守る場所:モデル・トークン・使用量は OpenAI 互換の口で(どの道でも効く)。ツールはブラウザでは確実、アプリでは約束
- 学べること:権限を「人 × できること」で持つ(RBAC に近い考え方)。プロファイル(作業の型)と権限(上限)を分けると、どちらも単純になる

### 案2:配布プロファイルを強制し、プロファイルを枠として使う

人・グループに「使えるプロファイル」を決め、配布プロファイルの決まりで全部しばる。
足すものが少ないが、API キーの口にはプロファイルが無いので、モデルと使用量の制限が抜ける。プロファイルに「作業の型」と「上限」が混ざり、配布プロファイルが増えやすい。

### 案3:項目ごとに足していく

人・グループごとのモデル、使用量の上限…を、それぞれ別の設定として足す。一番早いが、制限の置き場所がばらけて、どこで止められたか分かりにくくなる。

## 未決:枠の付け先とプロジェクト(2026-11-24、ユーザーの考え)

- 枠を人に付けるか・グループに付けるかは、**今は決めない**
- まだ作っていない「プロジェクト」の概念(backlog の「共有の再検討」)では、人は**プロジェクトの中での振る舞い(役割)**で制限されるべき。同じ人でも、プロジェクトによってできることが違いうる
- **グループは人を一括で管理する道具**(0031)で、制限の単位そのものではない。グループとプロジェクトをどう紐づけるか(グループをプロジェクトに入れる・プロジェクトの役割にグループを割り当てる など)と一緒に考える
- そのため、Chat が出した「グループに付け、人ごとは例外」「複数のグループなら広いほう」のおすすめは**保留**。プロジェクトの形が決まってから見直す
- 作る順番の案(段1:枠の入れ物と「使えるプロファイル」「使えるモデル」→ 段2:ツールのパターン → 段3:トークンの上限の上限と使用量の上限)も、枠の付け先が決まるまでは仕様にしない。
  段2のツールのパターンは、付け先によらず作れる部品なので、先に考えてもよい

## ツールの設定のパターン(枠の部品。2026-11-24 の相談)

### ユーザーの考えと選んだ形

プロファイルでツールを1つずつ設定するより、ツールの設定に**パターン**(「読み込みのみ」など)があり、それをプロファイル(や会話)に当てはめるほうがよいのでは(ユーザー)。

Chat が出した3つの案のうち、ユーザーは **B:パターンを自分で作って名前を付ける**形を選んだ。

- A:組み込みのパターン(「すべて」「読み込みのみ」「書き換えまで」「ツールなし」)をコードで持つ
- **B:パターンを自分で作って名前を付ける**(表を1つ足し、編集画面と、プロファイルからの参照を作る。一番自由で、変更は一番大きい)← 選んだ
- C:パターンは今の `rules.off` の一覧を埋める「当てはめるボタン」だけ

### 今の作り(Chat がコードを読んで確かめた)

- 扱いを決める場所は `tools.go` の `policyOf` の1か所。順は「プロファイルで使えない → 管理者の禁止 → 会話の上書き → PC の既定(`tools.json`)→ 決まりの既定」
- プロファイルの**値**:組み込みを使うか・使う MCP のサーバー・最初は使わないツール(`tools_off`)。**決まり**:使えないグループやツール(`rules.off`)と、グループの固定
- どれも「使えないものを並べる」形(ブラックリスト)。「読み込みのみ」は「これだけ使える」形(ホワイトリスト)なので、ここが一番大きな変化。ホワイトリストなら、あとから足したツールやサーバーは勝手には使えない
- **ロックは、グループ単位なら「使う」側にも固定できる**(錠の「使うツールのグループ」)。**ツール1つずつは「使えない」側にしか固定できない**
- 確認する / しないは PC ごとの設定(`tools.json`)で、配布プロファイルでは固定できない(サーバーでは管理者の `server-tools.json`)
- 組み込みのツールの目印は確認が要るかどうか(`Confirmable`)だけ。読むだけの `fetch_url` も確認の側に入るので、「読む / 書く / コマンド / ネット」の種類は別に要る
- MCP のツールは名前がその PC の `settings.json` のサーバー名で決まり、ツールの一覧も起動するまで分からない。MCP の「読むだけ」の印(`readOnlyHint`)は仕様で「信じてはいけない」とされている

### B で進めるときに決めること(Chat のおすすめ。ユーザーの答えはまだ)

1. **パターンの持ち主と配布**:配布プロファイルが個人のパターンを指すと、受け取った人から中身が見えず、作った人が変えると勝手に効いてしまう。
   おすすめ:パターンもプロファイルと同じく「自分のもの」と「配るもの」に分ける(0059 の形)。配布プロファイルは配布パターンしか選べない。別案:配るときにパターンの写しを埋め込む(直しても配った先に効かない)
2. **パターンに入れる中身**:ツールごとに「使えない / 確認して使う / 確認せずに使う」の3択を持ち、**確認の扱いもパターンに入れる**(おすすめ。今の `tools.json` の確認の設定は移行でパターンへ)。
   グループごとに「全部 / 選んだものだけ / なし」を選べる(「全部」ならあとから足したツールも入る)。別案:使える / 使えないだけにして、確認は今までどおり PC ごと。
   **確認をパターンに含めるかは、ユーザーの答えがまだ**
3. **今のプロファイルのツール設定との関係**:パターンを「上限」として**参照**する(直すと今ある会話にもすぐ効く)。プロファイルの「使えない」の決まりはパターンに置き換え、
   「最初から使うグループ・最初は使わないツール」はパターンの中での初期の選択として残す。移行は、決まりが空のプロファイルは「すべて」、決まりがあるものはその中身から「〈プロファイル名〉のツール」を自動で作る(動きは変わらない)
4. **「会話で外させない」の印**:パターンの中にツール・グループごとの印を足せば「使う」側にも固定できる。おすすめは仕組みだけ用意して既定は付けない(外すのはできることを減らす方向で、安全面の心配は無いため)
5. コマンドの頭ごとの許可(backlog の「コマンドごとの許可」)は、パターンに入れられる形にしておき、中身は次の段で作る

## 配布プロファイルの強制(2026-11-24 の相談)

- 今の作り(`profile.go` で確かめた):**利用者に配布プロファイルだけを使わせることはできない**。誰でも自分のプロファイルを作って変えられ、初めてのときには個人の「既定」も自動でできる。
  新しい会話で選べないのは、アーカイブしたものと配布を外されたものだけ
- そのため、配布プロファイルのツールの錠は**そのプロファイルを選んだときだけ**効く。全員に必ず効く守りは、管理者の禁止(`server-tools.json` の「使わない」)だけ
- 足すとしたら(Chat の案):サーバーの設定に「利用者は配布プロファイルだけ使う」を足し(0061 の画面)、かかった人は個人のプロファイルを作れず変えられない(Go の側でも断る)。
  個人のプロファイルで作った今ある会話は読めるが、続けて送るかは決める(案:送れない。写して配布プロファイルで続ける)。管理者・ログインなしの形にはかけない
- パターンと組み合わせて初めて意味が出る(強制が無いと、利用者は自分のプロファイルで「すべて」のパターンを選んで避けられる)。
  ただし、これも「誰に付けるか」が枠の付け先と同じ問いになるので、上の未決と一緒に決める。枠(案1)を作るなら、「使えるプロファイル」は枠の1項目になる
