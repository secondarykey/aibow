# 調整の記録

生成のパラメータなどを試して決めた値と、実際に動かして分かったことの記録です。値を変えるときは読み、試したことを書き足してください。

## presence penalty

`AIBOW_PRESENCE_PENALTY`、既定 1.5、直近 256 生成トークンが対象。

- Qwen3.5 4B は「1+1は？」でも数百トークン考える
- CPU で各1回試したところ、0 と 1.0 は 700 トークン以内に答えまで届かず、1.5 は 662 トークンで答えた。思考オフの日本語の答えの自然さはどれも同程度
- 試行は各1回なので、変えるときは複数回比べること

## compact(0002)の動作確認

2026-10-12、Linux・CPU・重みがランダムな極小モデル。文章の中身は無意味。

- truncate で古い組を外すと、モデルに渡す文字列の先頭(system の直後)が毎回変わるので、KV キャッシュの再利用は system プロンプトの分だけになる
- summary は要約の生成で KV キャッシュが入れ替わるので、要約した直後の返事はプロンプトをほぼ最初から読む(再利用 20 トークン程度)
- バイト単位の語彙のモデルでは、日本語1文字が約3トークンになり、要約の指示文だけで約 1,200 トークンになる。
  作業領域 − 要約の上限(1024)に入らないと要約できない(その回は truncate になる)。Qwen3.5 の語彙ならずっと少ないはずだが、未確認
- 実際のモデル(Qwen3.5)で同じ長い会話を truncate と summary で比べる作業(仕様の作業の順番 5)は、まだ行っていない

## ツール呼び出し(0004)

2026-10-13、Windows・GPU(VRAM 8GB)・Ollama の qwen3.5:4b(Q4_K_M)。temperature 0.7・presence penalty 1.5・
システムプロンプト「あなたは親切なアシスタントです。日本語で簡潔に答えてください。」。各1回の試行。

| 質問 | 思考 ON・ツール ON | 思考 OFF・ツール ON | 思考 ON・ツール OFF |
|---|---|---|---|
| 今何時? | `get_current_time` を呼んで正しく答えた | **呼ばずに**「ツールを使用しきれませんでした」と答えた | 「把握できません」(思考 817 トークン) |
| 1234 × 5678 は? | `calculate` で 7,006,652 | `calculate` で 7,006,652 | 思考が返事の上限(4096)に達して答えが出なかった |
| (続けて)それを 7 で割ると? | 前の答えを使って `7006652 / 7` | 同じ | 同じく上限に達した |
| 7 ÷ 2 は? | `7 ÷ 2` で呼んでエラー → 自分で `7 / 2` に直して 3.5 | 呼ばずに 3.5(正解) | 3.5(思考 472 トークン) |
| 今日の日付を調べて、大晦日まであと何日? | 時刻 → `(31 - 13) + 30 + 31` → 79 日(正解。ツール2回) | 時刻だけ呼び、暗算で「2027年1月1日まで 80 日」と間違えた | 「日付を確認できません」 |
| ニューヨークは今何曜日の何時? | `timezone=America/New_York` を自分で選んだ | 同じ | 「取得できません」 |

- **書式は一度も崩れなかった**。引数の名前(`expression` / `timezone`)も正しく、`timezone` は省略と指定を使い分けた
- **ツールの結果のエラーで立て直せる**: `7 ÷ 2` は「使えるのは数・+ - * /…」のエラーを見て、次の回で `/` に直した。エラーの文に使える書き方を入れておく効果が見えた
- **思考 OFF だとツールを呼ばないことがある**: 呼ぶべきところで呼ばずに、それらしい文(「使用しきれませんでした」)を書いた。
  ツールを使うなら思考 ON のほうが確実。思考 OFF の答えは速い(1 秒前後)が、暗算の間違いも出た
- **ツールがあると思考が短くなる**: ツール ON では思考は英語で 50〜170 トークン程度(「The user is asking… I should use the calculate tool」)。
  ツール OFF では「Thinking Process: 1. **Analyze the Request:**…」の長い思考になり、4 桁の掛け算は 4096 トークンでも答えまで届かなかった
- **ツールの説明だけでプロンプトが約 400 トークン増える**(OFF の 35〜48 トークンに対し ON は 420〜435 トークン)
- **ループの途中は KV キャッシュがほぼ全部効く**: 2回目の生成のプロンプトは「前回のプロンプト + 生成した分 + ツールの結果」で、
  生成した分も書き戻した文字列がモデルの出力と一致するので、前回までの全部を再利用できた(例: 541 トークン中 493 再利用 = 420 + 生成 73)
- **次の質問では再利用が 0 になる**: 公式テンプレートは、新しい質問の後ではループ中の思考を捨てる。プロンプトが途中から変わり、
  Qwen3.5 は一部の層を途中まで巻き戻せないので、最初から読み直しになる(ツールの機能より前からの性質。プロンプトの読み込みは 0.4 秒程度で、今の長さでは困らない)

## ファイルを読むツール(0005 の 3-1)

2026-10-13、Windows・GPU(VRAM 8GB)・Ollama の qwen3.5:4b(Q4_K_M)。temperature 0.7・presence penalty 1.5・思考 ON・
会話の上限 16384。作業フォルダは小さな Go のプロジェクト(`main.go`・`greet/greet.go`・テスト・300 行の `notes.txt`)。画面を通さない小さなプログラムで試した。

| 質問 | 動き |
|---|---|
| このフォルダに何がある? | `list_files()`(引数なし)→ ファイルとフォルダを分けて答えた。2.1 秒 |
| main.go を読んで説明して | `read_file(path="main.go")` → 中身を正しく説明した。3.5 秒 |
| notes.txt の 250 行目に何が書いてある? | **自分で `offset=250, limit=1` を指定**して1行だけ読んだ。2.9 秒 |
| notes.txt を最初から読んで「合言葉」の行を探して | `read_file`(200 行)→「続きは offset=201」を見て `offset=201` で残りを読み、250 行目を答えた(4 回試して全部同じ流れ)。5.8 秒 |

- **パスは相対パスで書いた**。環境の説明に作業フォルダの絶対パスを書いたが、絶対パスで呼んだことは無かった
- **数の引数は文字列で届く**(`offset="250"`)。`CheckArgs` が JSON Schema の `integer` を見て変換するので問題なし
- **ファイルの中身で会話が速く長くなる**: 300 行(1 行 10 文字ほど)を読むだけでプロンプトが 787 → 5,300 トークン程度になった。
  200 行のかたまり 1 回でおよそ 2,900 トークン。会話の上限 8192 なら 2〜3 回読むと compact が要る長さになる(2-2 の比較で観察する)
- **ループの途中でも KV キャッシュの再利用が 0 になることがある**(4 回中 3 回、200 行を読んだ直後の生成で 3,700 トークンを読み直した)。
  原因はトークンの分け方: モデルは思考の中で「して」「ほしい」を別々のトークンとして生成したが、同じ文字列を書き戻して
  トークンにし直すと「してほしい」の1トークンになる。文字列は同じでもトークンの並びが変わるので、その位置から先が一致しない。
  Qwen3.5 は途中から巻き戻せないので、全部読み直しになる(0004 のころからある性質。プロンプトが短いうちは目立たなかった)。
  直し方の案: 前回のトークン列(生成したトークンを含む)を文字列に戻し、新しいプロンプトがその文字列で始まるなら、
  その部分は前回のトークンをそのまま使い、残りだけをトークンにする(エンジンの変更なので、0005 とは別に相談する)

aibow のリポジトリそのもの(`D:\Go\Projects\aibow`)を作業フォルダにして、会話の上限 8192 で試した:

- 最初の版の `list_files` は `.claude/`(worktree のコピー)だけで 500 件・約 43,000 文字になり、1回で会話の上限を超えた。
  件数の上限だけでは大きさを抑えられない(深い場所はパスが長い)。隠しフォルダは中に入らない・8,000 文字で切る・浅い順に並べる、に変えた
- 変えた後は、ルートの一覧が約 2,850 トークン(プロンプト 729 → 3,581)。直下のファイルと `_docs/`・`store/`・`tool/` が全部見え、`_cmd/` の奥(DLL・ビルド結果)が切られる
- 「このフォルダに何がある?」→「AGENTS.md を見て概要図を mermaid で書いて」の2問で、最後は 7,359 / 8,192。次の送信で compact が要る長さ。
  AGENTS.md は 1 回(約 2,800 トークン)で読めた。`list_files` を経ずに AGENTS.md を直接読んだ回もあった(絶対パスで指定したが、受け付けて読めた)
- 4B が書いた mermaid は、ノードの名前に括弧を入れて図が描けないことがあった(`GPU[NVIDIA GPU (VRAM 8GB)]`)。中身も一部取り違えた(Ollama を MCP と書くなど)

入らない結果をエラーで返すようにしてから、会話の上限を 3000 に下げて「notes.txt を最初から読んで合言葉の行を探して」を試した:

- 最初の `read_file`(200 行・約 2,800 トークン)が「長すぎて渡せません(残りは約 2,100 トークン)」になると、**自分で `limit=100` に絞って**読めた
- その後も「残りは約 N トークン」を見て、`limit` を 200 → 50 → 20 と小さくしていった。ただし残りに合う量を計算できてはいない(残り 352 で 758 トークン分を頼むなど)
- 残りを使い切ると、今までどおり「上限を超えています」で止まった(3,046 / 3,000。超えた 46 トークンはエラーの結果の文そのもの)。
  1件のエラーの結果が 150 トークンほどあるので、残りが少ないときは何回か外れると届かなくなる

## 書き換えるツールと実行前の確認(0005 の 3-2)

2026-10-13、同じ環境(qwen3.5:4b・思考 ON・会話の上限 8192)。小さな Go のプロジェクトのコピーを作業フォルダにし、画面から試した。

| 頼んだこと | 動き |
|---|---|
| greet/greet.go のあいさつを日本語の「こんにちは、」にして | `read_file` で読んでから `edit_file`(1 行だけの置き換え)。確認で差分を見て「実行する」→ 書き換わり、変更後のコードを示して答えた |
| main.go を書き直して、Hi を表示するプログラムにして | **main.go ではなく greet.go を `edit_file` で直そうとした**(Hello 関数を変えれば済むと考えた)。理由「greet.go は変えないで。main.go だけを直して」で拒否 →「greet.go に関数を足すか、main.go で直接出すか」の2案を示して聞き返した |
| notes.txt の 1 行目を「最初の行」に書き換えて(2回目、理由なしで拒否) | **同じ書き換えをもう一度試した**(`edit_file` → エラー → `read_file` → `edit_file` で再び確認)。理由「書き換えたくない。やめて」で拒否したら、すぐに中断した |

- `write_file` より `edit_file` を選んだ(3 回とも)。書き換える前に `read_file` で読んでから、ファイルの中身のとおりに `old_string` を書けた(行番号を付けてしまうことは無かった)
- **拒否の理由が空だと、4B は同じことをもう一度試す**。理由を書けば、それに沿って止まる・聞き返す。拒否の理由の欄は大事
- 確認を待つ間は生成が止まっているので、GPU は空いている。会話の上限のメーターは、確認の前後で変わらない

## コマンドのツール(0005 の 3-3)

2026-10-13、同じ環境(qwen3.5:4b・思考 ON・会話の上限 8192)。テストが失敗する小さな Go のプロジェクト
(greet.go を「こんにちは、」にしたが、テストは「Hello, aibow!」を期待している)を作業フォルダにし、確認は全部「実行する」で答えた。

| 頼んだこと | 動き |
|---|---|
| テストを実行して | `list_files` → `run_command("go test ./...")`。失敗の出力と終了コード 1 を読んで、どのテストがなぜ失敗したかを答えた。「原因を調べます」と書いたが、そこで終わった(6.5 秒) |
| テストを実行して、失敗していたら原因を調べてコードを直し、もう一度テストを実行して確かめて | `list_files` → `run_command`(失敗)→ テストと greet.go を `read_file` → `edit_file` で「Hello, 」に戻す → `run_command`(成功)→ 原因と直したことを答えた。**ツール 6 回・17 秒・メーター 2,476 / 8,192** |
| ping -n 60 127.0.0.1 を run_command で実行して(5 秒後に停止) | 停止から終わるまで 0.1 秒。ping.exe も止まり、ここまでの出力が結果に残った |

- cmd.exe の書き方を間違えることはなかった(`go test ./...` は cmd.exe でもそのまま動く)。Linux のコマンド(ls・cat)を使う場面は今回なかった
- 「直して、もう一度確かめて」まで頼むと、読む → 直す → 動かすを最後まで回せた。「テストを実行して」だけだと、失敗を説明して止まる
- `edit_file` の `old_string` を数行にしたとき、直す必要のないコメントの行まで書き換えた(「name へのあいさつ」→「名前のいる挨拶」)。確認の差分で気づける
- 9B は Ollama に入っていなかったので比べていない

### 作業フォルダの名前で頼むと cd してしまう(0005 の後に直した)

ユーザーの報告:作業フォルダ `ytscroll` で「コミットして」と頼んだら、`cd ytscroll && git status` を実行して失敗した。

- 作業フォルダを `ytscroll` という git のリポジトリにして試すと、「コミットして」では 3 回とも `cd` しなかったが、
  **「ytscroll をコミットして」とフォルダの名前を書くと、3 回に 1 回 `cd ytscroll && git status` を書いた**(作業フォルダの下に ytscroll があると思った)
- 環境の説明に「Commands already run inside the working directory, so do not cd into it. "ytscroll" refers to the working directory itself.」を足し、
  `run_command` の説明にも「It already runs in the working directory; do not cd into it.」を足したら、同じ頼み方で 6 回とも `cd` しなかった(6 回ともコミットできた)
- 6 回のうち 1 回は、すでにリポジトリなのに `git init` から始めた(害は無いが、確認のカードで気づける)
