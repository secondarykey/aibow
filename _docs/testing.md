# アプリを起動して確かめる

最低限の確認(`gofmt` / `go test` / `wails3 build` / `go vet`)はトップの `AGENTS.md` にあります。
ここは、実際にアプリを起動して確かめるときの、どの環境でも同じ手順と確認する項目です。
環境ごとの手順と注意は、使っている環境のほうだけを読んでください。

- ユーザーの Windows 環境(worktree・CDP): [env-windows.md](env-windows.md)
- クラウドセッション(GUI の無い Linux・server モード・Playwright): [env-cloud.md](env-cloud.md)

## 起動

実際の生成は `_cmd/aibow` で `wails3 dev`(または `wails3 build` してから `wails3 task run`)で起動し、開いたウィンドウで送受信して確認します。

- 会話の DB は、試すときは `AIBOW_DB` を一時フォルダのファイルにする(ユーザーの `%APPDATA%\aibow\aibow.db` に試しの会話を混ぜない)
- `AIBOW_LOG_DIR` も一時フォルダにする(ユーザーの `%APPDATA%\aibow\logs` に試しのログを混ぜない)。exe(`wails3 build`)だけでなく、`wails3 dev` もファイルに書く
- `AIBOW_WINDOW` も一時フォルダのファイルにする(閉じるときにウィンドウの位置と大きさを書くので、ユーザーの `%APPDATA%\aibow\window.json` を書き換えないように)。
  一覧の開閉・幅・最後の会話は WebView2 の localStorage に覚えるので、WebView2 のデータフォルダも分けておく(Windows は [env-windows.md](env-windows.md))

## 確認する項目

次までを確認します。GPU や本物のモデルが無い環境では、llama.cpp の CPU 版と小さな GGUF(重みがランダムな極小モデルでもよい)で行います。

「読み込み → 生成 → 停止 → 2回目の送信で KV キャッシュが再利用される → モデルの切り替え → 壊れたモデルを選んだら元に戻る → 再起動しても会話が残る」

- compact は、会話の上限を小さくして(`AIBOW_HISTORY_TOKENS=1200` など)「truncate で薄くなる → summary で区切りが出る → none で止まる → 再起動しても要約が残る」を確認する。
  生成前の usage イベントのトークン数と、返事の統計のプロンプトのトークン数が一致することも見ておく(数え方がエンジンと同じであることの確認)
- Ollama の保存フォルダは、`manifests\registry.ollama.ai\library\<名前>\<タグ>`(目録 JSON)と `blobs\sha256-<ハッシュ>` を作れば模擬できます(`OLLAMA_MODELS` で指定)
- 重みがランダムなモデルでは出力される文章の中身は確認できないので、思考と答えの振り分けとツール呼び出しの読み取りは `format/qwen35_test.go` で確認します
- ツール呼び出し(0004)は「今何時? → get_current_time」「1234 × 5678 は? → calculate」「日付を調べてから計算(ツール2回)」と、枠(秒数・ツールの回数)とカードが再起動後も同じに出ることを確認する。
- MCP(0006)は、`settings.json` のサーバーで「ツールの一覧がプロンプトに入る → 確認のカードにサーバーの名前と引数が出る → 実行して結果をモデルが読む → アプリを閉じるとサーバーのプロセスが残らない」を確認する。
  設定ファイルは試しのものを `AIBOW_SETTINGS` で指定する(ユーザーの `%APPDATA%\aibow\settings.json` を書き換えない)。モデルなしでつなぎ方だけを見るなら `go test -v -run TestCommandServer ./mcp/client`。
  ほかのアプリと同じフォルダの uv のプロジェクトを `uv run` で起動すると、そのアプリの環境を作り直そうとしてしまうので、`UV_PROJECT_ENVIRONMENT` で環境を分ける([mcp.md](mcp.md) の「実例」)
  画面を通さずにモデルの振る舞いだけを見るときは、`aibow` パッケージを呼ぶ小さなプログラム(`engine.New` → `LoadModel` → `aibow.NewConversations` → `Send`)をリポジトリの外で作ると早い
- 作業フォルダとファイル・コマンドのツール(0005)は、小さなプロジェクトのコピーを作業フォルダにして確かめる(ユーザーのリポジトリで試さない)。
  「このフォルダに何がある?」「長いファイルの N 行目は?」(`offset` で続きを読む)、「〜を直して」(確認のカード → 実行する / 拒否と理由)、
  「テストを実行して、失敗していたら直して、もう一度確かめて」、確認待ちでの会話の切り替え・停止、再起動後のカード(拒否と出る)、長いコマンドの停止(子プロセスまで止まる)を見る
  - フォルダを選ぶダイアログは CDP では押せないので、`WorkDirBar` の `onChange` を呼んで選んだのと同じにする(ダイアログそのものは手で一度押して確かめる)
  - 画面を通さない小さなプログラムで試すときは、`Send` の emit で `confirm` イベントを受けたら `Conversations.Confirm` で答える(答えないと待ち続ける)
  - git のコミットを試すときは、作業フォルダのリポジトリに仮の `user.name` / `user.email` を設定する(ユーザーの名前でコミットしない)
- 要約の失敗(0002 の「使ってみて変えたこと」)は、返事の吹き出しの先頭に注意(三角のアイコン。赤ではない)が出て、理由・代わりに truncate したこと・対処が書いてあり、
  「途中まで書いた要約を見る」で失敗した要約の文が開けることを見る。要約が成功したら、ログの「要約: N 字 / M トークン(上限 …)」の行も見る。
  重みがランダムなモデルなら上限まで書き続けやすいので、会話の上限を小さくすれば失敗を起こせる
- 画面の機能([ui.md](ui.md)。長い返事の会話を1つ用意する)
  - スクロールして質問が上に隠れると右上に写しが出る・次の質問が上に来ると消える・押すと質問まで戻る。設定の「基本設定」でオフにすると出ない
  - 右下のボタンで「質問だけ」になる(読んでいた質問に枠)・質問を押すとそこへ飛ぶ・ボタンか Esc で元の位置に戻る・生成中に飛んでも次の文字で一番下へ引き戻されない・送信すると通常の表示に戻る
  - 要約中は「古い発言を要約しています…」だけが出て、押すと要約の文が開く
  - 会話の設定の画面の名前(Enter・欄を離れると保存、Esc で戻る)と ID のコピー・返事の「詳細」の発言の ID
  - 設定の画面のタブ(基本設定 / 会話)・明るさの3択(システムのときは OS の切り替えについていく。再起動の直後から選んだ明るさで描かれる)
