- **コマンドが無いとき**(2026-10-21、ユーザーと話した):今は確認のカードを許可したあとで、シェルの「見つからない」(cmd.exe は終了コード 9009 のはず・sh は 127)がそのままモデルに返り、モデルが立て直す。

## 裏で要約する

0002 の compact(要約)の改良版。2つ目の作業領域を作り、返事を書き終えたあとに、次に備えて要約しておく。
送信したときに要約を待つ時間をなくす(9B で 37.7 秒かかった例がある。`_docs/tuning.md`)。普通のモデルでは、会話の側の KV キャッシュを壊さない利点もある。
作業領域を2つ持つので VRAM を使う。「複数のモデルを同時に動かす」と関係する

## KV キャッシュの使い回しを良くする

2026-10-19、6-3 で見つけた(ユーザーと「記録だけして後で」と決めた)。関係する資料:`_docs/tuning.md` の「Cline からつないで比べる」「ファイルを読むツール」。

ツールのループの途中で前回の分を使い回せず、全部を読み直すことがある。原因は2つ。

1. **Cline が arguments の JSON を書き直して空白を詰める**(`["a", "b"]` → `["a","b"]`)ので、aibow-server が書式に戻した文字がモデルの書いた文字と変わる。
   案:返した呼び出しを id ごとに覚えておき(最近の数百件)、履歴で戻ってきたら値が同じかを確かめて、モデルが書いた元の文字を使う(ステートレスの API に、速さのためだけの小さな状態を持つことになる)
2. **トークンの分け方**:同じ文字列でも、生成したトークンの並びとトークンにし直した並びが違う(画面のアプリでも起きる。Granite 4.1 で日本語の引数でも見えた)。
   案:前回のトークン列を文字列に戻し、新しいプロンプトがその文字列で始まるなら、その部分は前回のトークンをそのまま使う(エンジンの変更)

今は読み直しが 6,000 トークンで 2〜3 秒なので困ってはいない

## 共有の再検討(アプリからの閲覧・プロジェクトの概念)

### 今の共有(0018・0031・0032 で作ったもの)

- **会話の共有**:会話ごとに「非公開(既定)/ 全員 / 指定した人・グループ(0031)」。会話の設定の画面の「共有」で決める。非公開から共有にするときだけ「ツールの結果も見えます」と確かめる
- **共有された側**:一覧の下の「共有された会話」の欄。開くと読むだけで、入力欄の代わりに「写して続ける」。写しはその時点のコピー(作業フォルダは写さない)
- **同じ会話に複数の人が書き込む形は無い**(管理者も含む。0018 の決定事項 2)
- **管理者が読む**:管理者は共有されていない会話も読めるが、書き込めない。全員の画面に「管理者が読めます」を常に出し、読んだら aibow-server のログに Notice を残す。
  人の会話を開く道は、管理の画面(0032)の「利用者」→ 人を選ぶ → その人の会話の一覧、だけ。**管理の画面はブラウザだけ**(0032 の決定事項 9)で、アプリでは管理者でも人の会話を開けない
- **共有の作業(プロファイルを配る)**:管理の画面の「配るプロファイル」で、全員か指定した人・グループに配る。受け取った人は読むだけで選べ、写して自分のものにできる
- **認可の判定の置き場所**:保存先(SQLite)の条件の1か所([_docs/conversations.md](conversations.md))
- **作らなかったもの**(0018 の「やらないこと」):組織の SSO・共同で書き込む・ログインしていない人に見せる共有のリンク

## aibow-server の中央の制御の残り

2026-10-22、ユーザーの要望。aibow-server の使い方をサーバーの側で決める仕組み。次は済んだ:サーバー全体で使えるモデルを管理者が決める・モデルの ID からサーバーの PC のパスを外す・
サーバーの PC の事情を変える口を管理者とサーバーの PC からだけにする(0018 の決定事項 5・8)、管理の画面(0032)、複数の人で GPU を分け合う(0023)。残りの候補:

- **作業領域や返事の上限の上限**:つないでくる側が大きな会話の上限を頼んでも、サーバーで抑える
- **順番待ちの優先度**
- **使われなければ自動で降ろす**(Ollama の `keep_alive` と同じ考え方)
- **server.json を画面で見る・変える**(2026-11-01、0032 の決定事項 10 で後回しにした):資料のフォルダ・MCP のサーバー・待ち受け・ログインなど、今は手で書くしかない設定を管理の画面に出すか。
  起動し直しが要るものの扱い(「起動し直すと切り替わります」を出す・画面から起動し直すか)と、画面で書き換えたときに手で書いた内容をどう守るかを考える

関係するところ:「複数のモデルを同時に動かす」(制限するか並べるかは裏表)

## パッケージの分け方

**分ける基準**:使う相手が現れたときに分ける(0005 の決定事項 11。使う相手がいないうちに分けると、外に見せる名前の線を推測で引くことになるため)。
これまでに分けたものは `AGENTS.md` の表(`store/`・`tool/`・`format/`・`engine/`・`models/`・`mcp/`・`api/`・`auth/`・`ui/`・`web/`・`genlog/`・`log/` など)。

残っている候補:ルートの `aibow` に、会話の仕組みと一緒に「手元に残る設定のファイル」がある(`settingsfile.go`(settings.json)・`toolprefs.go`(tools.json)・`mcpfile.go`(mcp.json)・
`workspaces.go`(workspaces.json)・`connectionfile.go`(connection.json))。どれも、会話を aibow-server に置く形でもその PC に残るもの(2026-10-14、Chat が気づいた)。
