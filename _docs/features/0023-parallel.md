## 目的

**aibow-server を複数の人で使っても、待ち時間と KV キャッシュの読み直しが人数分たまらないようにする**。

今は作業領域(llama.cpp のコンテキスト)が1つで、KV キャッシュも1本。生成は1つずつ(`api.Seat`)。
人(会話)が替わるたびに前の KV キャッシュは捨てられ、次のプロンプトを最初から読み直す(数千トークンで数秒)。0017 の 10-4 で「ほかの生成が終わるのを待っています」が出ることも確かめた。

```
今:     作業領域 32768 ─ KV キャッシュ1本 ─ 席1つ(1人ずつ)
0023:   作業領域 32768 ─ シーケンス0(16384)─ 会話 A の KV キャッシュ
                       └ シーケンス1(16384)─ 会話 B の KV キャッシュ   ← 同時に来たら1回の decode にまとめる
```

学ぶこと:

- **シーケンス**:llama.cpp は1つのコンテキストの中に、番号(seq_id)の付いた複数の KV キャッシュの列を持てる
- **バッチに混ぜる**:1回の decode に複数のシーケンスのトークンを混ぜると、GPU は1回の計算でまとめて進める。llama.cpp の server の `--parallel` の中身
- **連続バッチ(continuous batching)の入り口**:片方の返事が終わったら、その枠にすぐ次の人を入れる(全員が終わるのを待たない)
- **作業領域を分ける**:KV キャッシュの VRAM は合計で決まるので、シーケンスの数で割ると1人あたりの上限が小さくなる。会話の上限(0009)と compact(0002)とのつながり
- **ハイブリッドなモデルの状態**:Qwen3.5 は注意(attention)の層のほかに、前の状態を持ち運ぶ層(再帰の状態)を持つ。新しい発言を足すと KV キャッシュの再利用が 0 になる(0012 の 6-1)のは、これが原因の見込み(未確認。下の「調べること」)

## 調べて分かったこと(2026-10-25、Chat が yzma v1.29.1 のソースで確かめた)

- `llama.ContextParams` に `NSeqMax`(シーケンスの数の上限)・`KVUnified`(シーケンスで1つのバッファを分け合う)・`NRsSeq`(再帰の状態の巻き戻し用の控え。EXPERIMENTAL)がある
- `llama.NSeqMax(ctx)`・`llama.NCtxSeq(ctx)`(シーケンスあたりの大きさ)・`llama.BatchInit(nTokens, embd, nSeqMax)` がある
- シーケンスごとに KV キャッシュを扱う `llama.MemorySeqRm`・`MemorySeqCp`・`MemorySeqKeep`・`MemorySeqPosMax` などがある(今の engine は `MemorySeqRm` をシーケンス 0 にだけ使い、decode は `BatchGetOne`)
- なので、外部パッケージを足さずに作れる見込み

## 決定事項(ユーザーと決めたこと。2026-10-25)

1. **まず席を2つにする(シーケンス2本)**
   - 会話ごとに自分の KV キャッシュが残るので、2人が交互に使っても読み直しが減る
   - 2人が同時に来たら、2人分のトークンを1回の decode にまとめて進める
   - 2本で動いたら N 本(連続バッチ)に広げる。N 本はこの仕様では作らない
2. **作業領域の合計は今のまま(既定 32768)で、シーケンスの数で等分する**(2本なら1人 16384)
   - 1人あたりを今のままにして合計を増やす形・分け合う形(`KVUnified`)は使わない
3. **aibow-server だけに入れる**。デスクトップのアプリの中で動かす形(直接の形)は今のまま席1つ(使う人が1人なので)

## 決定事項(話の流れから Chat が決めて書いたこと。2026-10-25 にユーザーが確かめた)

4. **モデルは今のまま1つだけ**。「複数のモデルを同時に動かす」は VRAM 8GB では現実的でない(TODO の行のとおり)ので入れない
5. **シーケンスの数は aibow-server の起動の設定**(`server.json` と引数・環境変数。名前は Code が決める)。**既定は 1(今と同じ動き)**。画面からは変えない(全員の KV キャッシュに響くため。0015 の 8-4 の作業領域と同じ考え方)
6. **シーケンスの割り当ては会話ごと**(人ごとではない)。同じ人が2つの会話を交互に使っても、それぞれの KV キャッシュを使い回したい。空きが無ければ、一番長く使われていないものを捨てて使う
7. **Cline などの OpenAI 互換の口も同じ仕組みに乗る**。リクエストに会話の ID は無いので、プロンプトの頭が一番長く一致するシーケンスを選ぶ(llama.cpp の server と同じ考え方)。ブラウザ・アプリの会話も、同じ選び方でよければそろえる(Code が案を示す)
8. **学習用のログ**:生成のたびに、使ったシーケンスの番号・使い回したトークン数・同じ decode に混ざった数を Info で出す
9. **モデルの読み直し・層の数の変更は、全部のシーケンスの生成が終わってから**(今の席の中の読み直しと同じ。シーケンスは全部捨てる)

## 未決事項(Code は勝手に決めず、案を示してユーザーに確認する)

- **調べること(最初の段で、小さなプログラムで確かめる)**:
  - `NSeqMax` を 2 にしたとき、`n_ctx` がどう分かれるか(`NCtxSeq` が合計の半分になるか)・VRAM が今と同じか
  - Qwen3.5 の再帰の状態がシーケンスごとに持てるか・2本を1回の decode に混ぜて正しい返事になるか(1本ずつのときと同じ答えか)
  - 結果によっては、決定事項の 1 を「席は1つのまま KV キャッシュだけ2本」(同時には進めない)に下げることを相談する
- 1人あたり 16384 になると、会話の上限 + 返事の上限がそれを超える会話・プロファイルが出る。送信のときに断るか、上限をシーケンスの大きさに合わせて compact するか(今は「作業領域に収まるかを確かめるだけ」。0016 の決定事項 12)
- サンプラーをシーケンスごとに持つ方法(temperature などが会話ごとに違うため)。yzma の `Samplers`(EXPERIMENTAL)を使うか、自分で分けるか
- 片方が生成中に、もう片方が新しいプロンプトを読む(長いプロンプトの読み込みで、生成中の人の速さが落ちる)ときの分け方
- 速さの測り方(1本と2本のときの、トークン/秒と待ち時間)。`_docs/tuning.md` に記録する
- 画面の「ほかの生成が終わるのを待っています」の出し方(2本ともふさがっているときだけになる)

## 完了の条件

- aibow-server をシーケンス 2 で起動し、2人が同時に送ると、両方の返事が並んで流れて出る(待たされない)。返事はシーケンス 1 のときと同じ質(同じ設定・同じ乱数の種なら同じ答えになるかを確かめる)
- 2つの会話を交互に送ると、2回目からはそれぞれの KV キャッシュを使い回す(ログの使い回したトークン数で確かめる)
- 3つ目の会話が来たら、一番長く使われていないシーケンスを捨てて使う
- Cline(curl で同じ形のリクエスト)とブラウザの会話を同時に使っても壊れない
- シーケンス 1(既定)では、今と動きが変わらない。デスクトップのアプリ(直接・サーバー越し)も今のまま
