## 目的

**aibow-server を複数の人で使っても、待ち時間と KV キャッシュの読み直しが人数分たまらないようにする**。

今は作業領域(llama.cpp のコンテキスト)が1つで、KV キャッシュも1本。生成は1つずつ(`api.Seat`)。
人(会話)が替わるたびに前の KV キャッシュは捨てられ、次のプロンプトを最初から読み直す(数千トークンで数秒)。0017 の 10-4 で「ほかの生成が終わるのを待っています」が出ることも確かめた。

```
今:     作業領域 32768 ─ KV キャッシュ1本 ─ 席1つ(1人ずつ)
0023:   作業領域 32768 ─ シーケンス0(16384)─ 会話 A の KV キャッシュ
                       └ シーケンス1(16384)─ 会話 B の KV キャッシュ   ← 同時に来たら1回の decode にまとめる
```

学ぶこと:

- **シーケンス**:llama.cpp は1つのコンテキストの中に、番号(seq_id)の付いた複数の KV キャッシュの列を持てる
- **バッチに混ぜる**:1回の decode に複数のシーケンスのトークンを混ぜると、GPU は1回の計算でまとめて進める。llama.cpp の server の `--parallel` の中身
- **連続バッチ(continuous batching)の入り口**:片方の返事が終わったら、その枠にすぐ次の人を入れる(全員が終わるのを待たない)
- **作業領域を分ける**:KV キャッシュの VRAM は合計で決まるので、シーケンスの数で割ると1人あたりの上限が小さくなる。会話の上限(0009)と compact(0002)とのつながり
- **ハイブリッドなモデルの状態**:Qwen3.5 は注意(attention)の層のほかに、前の状態を持ち運ぶ層(再帰の状態)を持つ。新しい発言を足すと KV キャッシュの再利用が 0 になる(0012 の 6-1)のは、これが原因の見込み(未確認。下の「調べること」)

## 調べて分かったこと(2026-10-25、Chat が yzma v1.29.1 のソースで確かめた)

- `llama.ContextParams` に `NSeqMax`(シーケンスの数の上限)・`KVUnified`(シーケンスで1つのバッファを分け合う)・`NRsSeq`(再帰の状態の巻き戻し用の控え。EXPERIMENTAL)がある
- `llama.NSeqMax(ctx)`・`llama.NCtxSeq(ctx)`(シーケンスあたりの大きさ)・`llama.BatchInit(nTokens, embd, nSeqMax)` がある

- なので、外部パッケージを足さずに作れる見込み

## 段1 で分かったこと(2026-11-02、Code が確かめた)

リポジトリの外の小さなプログラムで、yzma(v1.29.1)を直接呼んで確かめた。Ollama の qwen3.5:4b / 9b(Q4_K_M)、RTX 4060(8 GB)、全部の層を GPU、作業領域 32768、`KVUnified` は使わない(既定も 0)。
答えは greedy(temperature 0)で 64 トークンずつ比べた。数の一覧は [_docs/tuning.md](../tuning.md) の「シーケンスを2本にする(0023 の段1)」。

- **作業領域は等分される**:`NSeqMax = 2` で `NCtx` は 32768 のまま、`NCtxSeq` が 16384 になる。シーケンス 0 に 16384 を超えて詰めると decode が 1(空きが無い)を返す。
  1本の上限は、合計ではなくシーケンスごとに効く
- **VRAM は変わらない**:作業領域の分は 4B で 1.58 → 1.62 GB、9B で 2.24 → 2.16 GB(測り方の誤差の範囲)。9B は全部の層を GPU にして、ほかのアプリの分と合わせて 8.0 GB でぎりぎり入った(1本でも同じ)
- **再帰の状態はシーケンスごとに持てる**:Qwen3.5 は llama.cpp で「ハイブリッド」(`ModelIsHybrid` が true)。2本を1回の decode に混ぜて進めても、
  返事は崩れない(どちらも意味の通る文で、片方の話がもう片方に混ざらない)。シーケンス 0 の続きだけを足して読ませても、シーケンス 1 には響かない
- **混ぜると答えが少し変わることがある(誤差。状態の混ざりではない)**:4B は B が 64 トークン全部一致、A は 19 トークン目から別の言い回しに分かれた。9B は A が 27、B が 20 トークン目から。
  - 理由:混ぜると1回に計算する行列の形が変わり、足し算の順番が変わる。A の最初の logits は、1本のときと混ぜたときで最大 0.54(4B)・0.55(9B)違った。同じ混ぜ方なら毎回同じ(差 0)
  - 分かれた位置は、1本のときの上位2つの差が 0.108(4B)しかない所だった。誤差で順位が入れ替わっただけ
  - 2本の作業領域で1本だけ使ったときは、1本の作業領域と全部一致した。シーケンスを丸ごと捨てて読み直しても全部一致した
  - なので、完了の条件の「同じ設定・同じ乱数の種なら同じ答えになるか」は**混ぜたときは成り立たない**(llama.cpp の server の `--parallel` も同じ)。質(意味の通る返事か)で確かめる
- **Qwen3.5 は途中から捨てられないが、丸ごとは捨てられる**:`MemorySeqRm(seq, 10, -1)` は false、`MemorySeqRm(seq, 0, -1)` は true(もう片方は残る)。
  一番長く使われていないシーケンスを捨てて使い直す(決定事項 6)は、丸ごと捨てるだけなので作れる
- **`NRsSeq`(再帰の状態の控え)は decode の回数分しか戻せない**:控えを N にすると、最後の N 回の decode まで戻せた(1 なら 1 トークン、16 なら 16 トークン)。
  そのかわり VRAM が増える(4B で 1 は +0.1 GB、16 は +2.2 GB)。新しい発言で数千トークン前から変わる(前の返事の思考が外れる)のは戻せないので、この仕様では使わない
- **速さ**(生成。64 トークン):

  | | 1本 | 2本を同時に(1本あたり) | 2本の合計 |
  |---|---|---|---|
  | 4B | 70 tok/s | 62 tok/s | 124 tok/s |
  | 9B | 41 tok/s | 37 tok/s | 75 tok/s |

  2人が同時に使っても、1人あたりの速さは 1 割ほどしか落ちない(GPU は1トークンずつだと手が余っている)
- **片方が生成中に、もう片方が新しいプロンプトを読むとき**(4B。1回の decode に、生成中の1トークンと、もう片方のプロンプトを混ぜた):

  | 混ぜたプロンプト | 0 | 63 | 127 | 255 | 511 |
  |---|---|---|---|---|---|
  | 1回の decode | 15.5 ms | 51 ms | 69 ms | 108 ms | 199 ms |

  プロンプトの1トークンあたり、生成中の人は 0.36 ms(255・511)〜0.42 ms(127)待たされる。区切りを小さくしても待たされる合計はほぼ同じで、細かく分かれるだけ。読む側は大きく区切るほど速い(511 で 2,600 tok/s・127 で 1,800 tok/s)

### 段1 の結果から:決定事項 1 は今のままでよい(案)

再帰の状態もシーケンスごとに持て、混ぜても返事は崩れないので、「席は1つのまま KV キャッシュだけ2本」に下げる必要はない。

### 未決事項の案(Code の案。ユーザーの確認を待つ)

1. **1本 16384 を超える会話**:送信のときに断る(今の確かめのまま)。aibow-server が見せる「作業領域の大きさ」を、1本あたりの大きさ(`NCtxSeq`)にする。
   今の `fixedContext` の確かめとエラーの文(「会話の上限か返事の上限を下げるか、…」)がそのまま効く。文に「シーケンスの数を減らして起動し直す」を足す。
   既定の会話の上限 8192 + 返事の上限 8192 = 16384 はちょうど入る。
   (もう1つの案「上限をシーケンスの大きさに合わせて黙って compact する」は、会話の設定と違う大きさで動くことになり分かりにくいので推さない)
2. **サンプラー**:自分で分ける(今の作りのまま、生成ごとにサンプラーのチェーンを作る)。混ぜた decode のあとは、`SamplerSample` に batch の中の位置を渡せば、その人の分の確率から選べる(段1 で確かめた)。
   yzma の `Samplers`(サンプリングを GPU でする。EXPERIMENTAL)は使わない
3. **片方が生成中に、もう片方が新しいプロンプトを読むとき**:llama.cpp の server と同じく、1回の decode に「生成中の人の1トークン + 新しいプロンプトの続き」を混ぜる。
   区切りは今の `batchSize`(512)のまま。上の表のとおり、区切りを小さくしても生成中の人が待たされる合計は変わらず、読む人が遅くなるだけなので
4. **会話と Cline の選び方をそろえる(決定事項 7)**:ブラウザ・アプリの会話も、Cline と同じ「プロンプトの頭が一番長く一致するシーケンス」で選ぶ。
   engine に会話の ID を渡す口が要らず(api・ui・api/client のどの道でも同じ)、compact でプロンプトの頭が変わったときも自然に読み直しになる。
   ただし「使える一致」で比べる:途中から巻き戻せないモデル(Qwen3.5)は、シーケンスの中身が丸ごとプロンプトの頭になっているときだけ使える(途中で違えば 0 とみなす)。
   こうしないと、システムの発言とツールの説明(1,000 トークンほど)が同じなだけの新しい会話が、ほかの会話のシーケンスを奪う。0 ばかりなら、空いているもの → 一番長く使われていないもの、の順
5. **速さの測り方**:上の段1 の数(engine を直接。混ぜない・混ぜる)と、段4 で aibow-server 越しに2人が同時に送ったときの「最初の文字までの時間」と「トークン/秒」を、シーケンス 1 と 2 で比べる。`_docs/tuning.md` に書く
6. **「ほかの生成が終わるのを待っています」**:シーケンスが全部ふさがっているときだけ出す(`Seat` の数を、シーケンスの数にする)。ブラウザの会話は今と同じく、送信の全体(ツールの確認待ちも)で席を持つ
7. **作り方(段2・段3)**:シーケンスが2本以上のときは、engine の中に decode を回す係(goroutine 1つ)を置く。`Generate` は今の形のまま、係に「このプロンプトをこのシーケンスで」と頼み、トークンを受け取る。
   係は、動いている生成を1回の decode にまとめて進める。シーケンス 1 のときは係を使わず、今の `Generate` のまま(動きを変えない)
