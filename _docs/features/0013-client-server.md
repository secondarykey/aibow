会話の共有(管理者は全部の会話を見られる、共有の作業を準備する、など)も視野に入れる。共有の部分は思いつきの段階(2026-10-19、ユーザー)。

## 決めたこと(ユーザーと決めた。2026-10-19)

- **別の exe にしない**:ブラウザに出すのに Wails v3 の Server Build(`-tags server`)は使わない(ビルドの時に切り替えるので別の exe になる)。デスクトップアプリのまま、Transport の差し替え(`AssetServerTransport`)でブラウザにも出す

## 切り方

| 形 | 頭(モデル) | 保存・共有 | エージェントループ | 手(ツール) | 例 |
|---|---|---|---|---|---|
| A | サーバー | 手元 | 手元 | 手元 | 自分用で GPU が別の機械 |
| B | サーバー | サーバー | サーバー | サーバー(隔離)か、手元(逆向きのつなぎ方) | ChatGPT・claude.ai |
| C | サーバー | サーバー | 手元 | 手元 | Claude Code(頭はサーバー、ループと手は手元) |

- A:`Generator` の HTTP 版を作れば済む。サーバー側は `aibow-api` がもうある(ステップ8)
- B:ループがサーバーにあるので、手元のツールを使うには、サーバーが手元のツールを呼ぶ逆向きのつなぎ方が要る。手元の PC はふつう外からつなげないので、手元からサーバーにつなぎに行く形などを工夫する
- C:デスクトップアプリが今のままループを回し、生成(`Generator`)と保存(`Store`)だけを HTTP でサーバーに頼む。逆向きのつなぎ方が要らない。会話はサーバーにあるので共有できる

**案:デスクトップは C、ブラウザは B(手元のツールなし)、保存先は1つ**(Chat が出し、ユーザーは OK。正式に決めるのはステップ9・10の仕様のとき)。
ブラウザはチャット・調べ物・共有の作業に使う。デスクトップで作った会話をブラウザで見る、もできる。
サーバーの上でツールを動かすのは、リポジトリをサーバーに置く「共有の作業」のときの選択肢で、作業ごとの隔離(サンドボックス)が要る(ステップ12。必要になったら)。

MCP はツールとデータを AI アプリにつなぐ規格で、どの形でも共有のツールに使えるが、モデルの置き場所や会話の保存は担わない。

## 共有で変わること

- **「誰の会話か」が保存の約束(`Store`)のほぼ全部に入る**。今の `Store` は全部が自分の会話という前提。`ListConversations()` は「この人が見られる会話」になる。持ち主・見られる人・管理者の区別。B / C の中で一番大きな作り直し
- **共有の作業は、設定のプロファイル化の延長**:システムプロンプト・モデル・使うツール・作業の場所をまとめたものに「誰が使えるか」を足したもの(Claude の Projects に近い)。
  ステップ7のプロファイル化は自分用で作るが、あとで管理者が作ってチームに配る形に育つ線で作る
- **モデルを選ぶ人が変わる**:GPU が1台なら、読み込めるモデルは同時に1つか2つ。組織では「モデルは管理者が用意し、利用者はプロファイルで選ぶ」形になりそう

## ブラウザに出す方法(2026-10-19。Chat が Wails のソースを読んで調べた)

詳しくは brender の `_docs/server-transport.md`。要点と、aibow に当てはめたこと:

- Server Build(`-tags server`)は別の exe になるので使わない。参考:Server Build のイベントの WebSocket は認証を通らず、送り先を1人に絞れない
- Transport の差し替え(`application.Options.Transport` の `AssetServerTransport`):`ServeAssets` で Wails が渡す配信を自前の HTTP サーバーに載せると、同じプロセスのまま、ブラウザからもバインディングを呼べる見込み(公式の例 `v3/examples/websocket-transport`)。
  aibow の Wails は v3.0.0-beta.26。読んだファイルは brender の beta.23 と同じ中身
- バインディングのメソッドの `ctx` は HTTP のリクエストから作られ、値が引き継がれる。手前の middleware で入れた利用者をメソッドの中で読める
- aibow で気をつけること:
  - `ChatEvent` は今 `app.Event.Emit` で流している(`_cmd/aibow/service.go`)。デスクトップのビルドには Wails のイベントをブラウザに送る仕組みが無いので、ブラウザには**自前の SSE** で流す。会話の中身が乗るので、ステップ10からは**その人にだけ**送る
  - 作業フォルダを選ぶダイアログ(`app.Dialog.OpenFile`、`service.go`)はブラウザでは使えない。ブラウザ(B)には手元のツールが無いので、ブラウザでは作業フォルダを出さない、で自然につながる
  - 登録したサービスのメソッドは全部ブラウザから呼べるようになる。ウィンドウからの呼び出しかどうかはヘッダーで見分けられていてブラウザも偽れるので、それで信用しない(brender のメモの「気をつけること 1」)

## ステップごとの論点(仕様を書くときに決める)

- **ステップ8(生成を aibow-api 越しに)**:トークン数(`CountTokens`)は OpenAI 互換 API の決まりに無いので独自の口が要る(llama.cpp の server には `/tokenize` がある)。
  サーバーを共有すると会話ごとに作業領域の大きさを変えられない(`EnsureContextSize`。0009 の会話の上限が「上限の確認」になる)。
  学習用に画面に出しているモデルに渡した文字列(`onPrompt`)をどう返すか。書式(テンプレート)を手元とサーバーのどちらで当てるか(今の `Generator` はサーバー側で当てる形)
- **ステップ9(ブラウザからも使う)**:`ChatEvent` と確認の往復(`Conversations.Confirm`)をネットワークで流す。画面で「ブラウザか」を判定する方法
- **ステップ10(ログイン・持ち主・保存をサーバーに・C)**:
  - ログインの方法(自前のアカウントか、組織の SSO(OIDC)か)
  - 人ごとのデータの分離。`Store` の HTTP 版
  - 手元に残る設定(`settingsfile.go` の settings.json・`toolprefs.go` の tools.json)を会話の仕組みから分ける(ファイルの先頭にそう書いてある)
  - **生成の口**:サーバーの機械では aibow がモデルを読み込んでブラウザに出すので、ほかの PC のデスクトップアプリ(C)に生成を出すのも同じプロセスになる(GPU のモデルは1つ)。
    0012 の「画面のアプリと aibow-api は同時に使わない」「画面のアプリの中で API を動かす(やらないこと)」は見直しになる(2026-10-19、Chat が気づいた)
  - GPU を複数人でどう使うか(順番待ちか、llama.cpp の並列処理か)
  - **決まり(固定・使えない)を守らせられる場所**(2026-10-19、ユーザーと話した。決まりの形はステップ7の 0014):本当に守らせられるのは、利用者が手を出せない場所で判定したときだけ。
    ブラウザ(B)はサーバーで判定するので全部守らせられる。デスクトップ(C)はループとツールが利用者の PC で動くので、ツールの禁止はデスクトップアプリが守る約束にとどまる。
    サーバーが確実に守らせられるのは、サーバーで行うこと(モデル・返事の上限など。システムプロンプトはサーバーが付け足す形にすれば守らせられる)。
    「絶対にコマンドを実行させない」が要る人はブラウザで使う
- **ステップ11(共有)**:認可(誰が何を見られるか)。管理者が全部の会話を見ることを利用者にどう知らせるか
- **ステップ12(必要になったら)**:サーバーの上でツールを動かすときの隔離、逆向きのつなぎ方
