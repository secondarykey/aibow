## 目的

aibow を**組織で使えるようにする**(最終目的)。学ぶためだけなら自分だけで良い。
会話の共有(管理者は全部の会話を見られる、共有の作業を準備する、など)も視野に入れる。共有の部分は思いつきの段階(2026-10-19、ユーザー)。

## 決めたこと(ユーザーと決めた。2026-10-19)

- 最終目的は組織で使うこと。なので、会話ごとサーバーに置く形(下の B)まで行く

- **別の exe にしない**:ブラウザに出すのに Wails v3 の Server Build(`-tags server`)は使わない(ビルドの時に切り替えるので別の exe になる)。デスクトップアプリのまま、Transport の差し替え(`AssetServerTransport`)でブラウザにも出す
- ブラウザに出す方法は **brender で先に試し、aibow はその形に合わせる**(brender で実装した。2026-10-19。下の「ブラウザに出す方法」)

## 切り方

| 形 | 頭(モデル) | 保存・共有 | エージェントループ | 手(ツール) | 例 |
|---|---|---|---|---|---|
| A | サーバー | 手元 | 手元 | 手元 | 自分用で GPU が別の機械 |
| B | サーバー | サーバー | サーバー | サーバー(隔離)か、手元(逆向きのつなぎ方) | ChatGPT・claude.ai |
| C | サーバー | サーバー | 手元 | 手元 | Claude Code(頭はサーバー、ループと手は手元) |

- A:`Generator` の HTTP 版を作れば済む。サーバー側は `aibow-api` がもうある(ステップ8)
- B:ループがサーバーにあるので、手元のツールを使うには、サーバーが手元のツールを呼ぶ逆向きのつなぎ方が要る。手元の PC はふつう外からつなげないので、手元からサーバーにつなぎに行く形などを工夫する
- C:デスクトップアプリが今のままループを回し、生成(`Generator`)と保存(`Store`)だけを HTTP でサーバーに頼む。逆向きのつなぎ方が要らない。会話はサーバーにあるので共有できる

**案:デスクトップは C、ブラウザは B(手元のツールなし)、保存先は1つ**(Chat が出し、ユーザーは OK。正式に決めるのはステップ9・10の仕様のとき)。
ブラウザはチャット・調べ物・共有の作業に使う。デスクトップで作った会話をブラウザで見る、もできる。
サーバーの上でツールを動かすのは、リポジトリをサーバーに置く「共有の作業」のときの選択肢で、作業ごとの隔離(サンドボックス)が要る(ステップ12。必要になったら)。

MCP はツールとデータを AI アプリにつなぐ規格で、どの形でも共有のツールに使えるが、モデルの置き場所や会話の保存は担わない。

## 共有で変わること

- **「誰の会話か」が保存の約束(`Store`)のほぼ全部に入る**。今の `Store` は全部が自分の会話という前提。`ListConversations()` は「この人が見られる会話」になる。持ち主・見られる人・管理者の区別。B / C の中で一番大きな作り直し
- **共有の作業は、設定のプロファイル化の延長**:システムプロンプト・モデル・使うツール・作業の場所をまとめたものに「誰が使えるか」を足したもの(Claude の Projects に近い)。
  ステップ7のプロファイル化は自分用で作るが、あとで管理者が作ってチームに配る形に育つ線で作る
- **モデルを選ぶ人が変わる**:GPU が1台なら、読み込めるモデルは同時に1つか2つ。組織では「モデルは管理者が用意し、利用者はプロファイルで選ぶ」形になりそう

## ブラウザに出す方法(2026-10-19。brender で実装した)

brender で実装し、ウィンドウの側も含めて動くことを確かめた。経緯は brender の `_docs/server-transport.md`、今の形は brender の Skill `brender-server-mode`。aibow のステップ9はこの形に合わせる。

> **2026-10-22 に変えた**(ステップ9の仕様 [0016-browser.md](0016-browser.md)):ステップ8で aibow-server がサーバー役になったので、ブラウザは aibow-server につなぐ形にした。
> 画面のアプリはブラウザに配らず、この節の Transport の差し替えは使わない。長い呼び出し・停止・SSE などの気づき(下の「aibow で気をつけること」)は 0016 でも使う。

```
ウィンドウ(WebView) ──wails://──→ Wails の配信 ──→ バインディング(ctx に利用者なし → 自分)
ブラウザ ──HTTP──→ 自前の http.Server(ログインの確認)
                    └ POST /wails/runtime → 守り → Wails の配信 ──→ バインディング(ctx に利用者・ブラウザの印)
```

brender の形(aibow でもそのまま使えるもの):

- **自作の Transport**:`*application.HTTPTransport` を埋め込み(ウィンドウの通り道はそのまま)、`ServeAssets(h)` で受け取った Wails の配信を自前のサーバに渡すだけ。
  **`WailsEventListener`(`DispatchWailsEvent`)を持たせない**(持たせるとウィンドウへのイベントが届かなくなる)。サーバモードでないときは Transport を nil(Wails の既定)にする
- **`POST /wails/runtime` の守り**(自前のサーバで、Wails の配信に渡す前に):
  - 通す `object` は 0(メソッドの呼び出し)と 10(取り消し)だけ。**Wails の決まった API はウィンドウ無しでも通り、`Application.Quit` でアプリが終わる・`Events.Emit` で好きなイベントを出せる**ため、ほかは 403 で断る
  - チャンクで分けた送り方(`x-wails-chunk-id`)は中身を確かめられないので断る。本文の上限は 64 MiB
  - ログインが要る設定で `ctx` に利用者が無ければ 401
  - `x-wails-window-*` のヘッダーを消し、`ctx` に**ブラウザからの印**を付ける(brender の `api.WithBrowser` / `api.FromBrowser`)。印を付けるのは自前のサーバだけなので偽れない。ヘッダーや `application.WindowKey` では判定しない
- **画面**:`@wailsio/runtime` の `setTransport()`(公式の差し替え口)で、ブラウザの呼び出しを `POST /wails/runtime` に送る。401 なら読み直してログイン画面へ。
  ブラウザかどうかは、サーバが `index.html` に差し込む印(brender は `window.__brender_server_mode`)で見分け、見た目の分かれ道(ウィンドウ操作・ダイアログなど)にだけ使う。API の呼び出しは分けない
- **エラー**:メソッドが error を返すと、Wails は 422 で `{"message": …}` を返す。権限のエラーも Wails が ERROR のログに出す
- **イベント**:デスクトップのビルドには Wails のイベントをブラウザに送る仕組みが無いので、ブラウザへは自前の SSE で送る(brender は Wails のイベントと SSE の両方へ配る `emit` を1つにしている)
- **登録したサービスのメソッドは全部ブラウザから呼べる**。ウィンドウを開く・サーバの機械の画面を使うメソッドは、ブラウザの印があれば断る。admin だけの操作は、サービスの手前ではなくメソッドの中(brender は `api` の層)で確かめる
- Wails の版:brender も aibow と同じ v3.0.0-beta.26 にした。画面の `@wailsio/runtime` は npm の版が Go の側と一致しないので `latest` のまま

aibow で気をつけること:

- **`ChatEvent`** は今 `app.Event.Emit` で流している(`_cmd/aibow/service.go` の `run`)。ブラウザには**自前の SSE** で流す。会話の中身が乗るので、ステップ10からは**その人にだけ**送る(brender の SSE は全員に送る作り)
- **送信は長い呼び出しになる**:`Send`・`Regenerate`・`Resend`・`Compact` は、生成が終わるまで返らない(停止ボタンは呼び出しの取り消し = `object` 10 で `ctx` を止める)。
  ブラウザからは、1回の送信が1本の長い HTTP のリクエストになる。自前のサーバに書き込みの時間の上限(`WriteTimeout`)を付けないこと(brender の自前のサーバは付けていない)。
  Wails は呼び出しが返ると `ctx` を取り消すので、呼び出しの後まで続く処理は `context.WithoutCancel` を使う(brender の `Workspace.CreateMovie`)
- **作業フォルダを選ぶダイアログ**(`app.Dialog.OpenFile`、`service.go`)はブラウザでは使えない。ブラウザ(B)には手元のツールが無いので、ブラウザでは作業フォルダを出さない、で自然につながる。ダイアログのメソッドはブラウザの印で断る
- メソッドの多くは `ctx` を受けていない(`ChatService` の公開メソッド 34 のうち `ctx` を受けるのは 6)。ステップ10で利用者を見分けるには、brender と同じく第1引数に `ctx` を足す

## ステップごとの論点(仕様を書くときに決める)

- **ステップ8(生成を aibow-api 越しに)**:トークン数(`CountTokens`)は OpenAI 互換 API の決まりに無いので独自の口が要る(llama.cpp の server には `/tokenize` がある)。
  サーバーを共有すると会話ごとに作業領域の大きさを変えられない(`EnsureContextSize`。0009 の会話の上限が「上限の確認」になる)。
  学習用に画面に出しているモデルに渡した文字列(`onPrompt`)をどう返すか。書式(テンプレート)を手元とサーバーのどちらで当てるか(今の `Generator` はサーバー側で当てる形)
- **ステップ9(ブラウザからも使う)**:`ChatEvent` と確認の往復(`Conversations.Confirm`)をネットワークで流す。画面で「ブラウザか」を判定する方法
- **ステップ10(ログイン・持ち主・保存をサーバーに・C)**:
  - ログインの方法(自前のアカウントか、組織の SSO(OIDC)か)
  - 人ごとのデータの分離。`Store` の HTTP 版
  - 手元に残る設定(`settingsfile.go` の settings.json・`toolprefs.go` の tools.json)を会話の仕組みから分ける(ファイルの先頭にそう書いてある)
  - **生成の口**:サーバーの機械では aibow がモデルを読み込んでブラウザに出すので、ほかの PC のデスクトップアプリ(C)に生成を出すのも同じプロセスになる(GPU のモデルは1つ)。
    0012 の「画面のアプリと aibow-api は同時に使わない」「画面のアプリの中で API を動かす(やらないこと)」は見直しになる(2026-10-19、Chat が気づいた)
  - GPU を複数人でどう使うか(順番待ちか、llama.cpp の並列処理か)
  - **決まり(固定・使えない)を守らせられる場所**(2026-10-19、ユーザーと話した。決まりの形はステップ7の 0014):本当に守らせられるのは、利用者が手を出せない場所で判定したときだけ。
    ブラウザ(B)はサーバーで判定するので全部守らせられる。デスクトップ(C)はループとツールが利用者の PC で動くので、ツールの禁止はデスクトップアプリが守る約束にとどまる。
    サーバーが確実に守らせられるのは、サーバーで行うこと(モデル・返事の上限など。システムプロンプトはサーバーが付け足す形にすれば守らせられる)。
    「絶対にコマンドを実行させない」が要る人はブラウザで使う
- **ステップ11(共有)**:認可(誰が何を見られるか)。管理者が全部の会話を見ることを利用者にどう知らせるか
- **ステップ12(必要になったら)**:サーバーの上でツールを動かすときの隔離、逆向きのつなぎ方

## ロードマップの外の行との関係

- 「ほかのモデルの書式」「画像を読む」は、ネットワークを越えるデータの形(書式をどちらで当てるか・`Message` に画像が入る)を変える。ステップ 7〜9 の合間に入れるとよい
- 「裏で要約する」「KV キャッシュの使い回し」は、サーバーで複数人を並列に扱う仕組み(llama.cpp の複数のシーケンス)の小さい版。先にやると学びがつながる
- ほかの行(会話の検索・worktree・MCP の OAuth・ツールの信頼の続き・今の組の中の compact・ログの続き)は境界を越える形をほとんど変えないので、後でよい。ログの続きの「クライアント/サーバー構成のログ」はステップ10のころに考える
