## 目的

組織で aibow-server を使うと、だれがどれだけ GPU を使っているかが分からない(2026-11-01、ユーザーの要望)。
**利用者ごとの使用量を記録して、管理者が把握できるようにする**。上限をかけるかは、記録を見てから決める(今回は作らない)。

学ぶこと:

- **ローカルLLMの「使用量」とは何か**:クラウドの API と違って料金は無い。限られているのは GPU の席(`api.Seat` は1つ)で、だれかが長く使うと全員が待つ。
  だから主に見る数字は「GPU を使った秒数」にする
- **KV キャッシュと使用量**:プロンプトのトークン数には、KV キャッシュを使い回した分も入っている。実際に計算したのは「プロンプト − 使い回した数」。
  同じ会話を続けると使い回しが効いて軽く、毎回最初から読み直す使い方(ステートレスの API で履歴を書き換えるなど)は重い、が数字で見える
- **1か所で包む**:生成が通る2本の道(OpenAI 互換の口・ブラウザの会話)の両方に書き足さず、aibow-server が engine を渡すところで包む(デコレータの形)

## 今の作り(2026-11-01、Chat がコードを読んで確かめた)

- aibow-server の生成の道は2本。どちらも同じ engine の `Generate` を呼び、`engine.GenerateStats` が返る
  - OpenAI 互換の口(`api/chat.go` の `complete` / `stream`):Cline など・aibow-server につないだアプリ(アプリのエージェントループと compact の要約も、1回ずつこの口に来る)
  - 画面用の口(`ui/serverhost.go` → `conversation.go` / `compact.go`):ブラウザの会話と、その要約
- `_cmd/aibow-server` は同じ `eng` を `api.New(eng, …)`(`main.go`)と `ui.NewServerHost(eng, …)`(`browser.go`)に渡している
- `GenerateStats` にはプロンプトのトークン数・使い回した数・秒数・生成のトークン数・秒数・画像のトークン数・エンコードの秒数・終了理由がある。
  OpenAI 互換の口は `usage` としてクライアントに返しているが、保存はしていない(ログの1行だけ)
- 呼んだ人は ctx にある(`auth.UserFrom`・`aibow.WithUser`・`ui.Caller`)。ログインなしの形では利用者 `local`

## 決定事項

ユーザーと決めたこと(2026-11-01):

1. **aibow-server の生成1回ごとに1行を記録する**。対象は aibow-server だけ(アプリの中で動かす1人の形は記録しない)。会話の返事・ツールのループの1回・要約、のどれも1回と数える
2. **数字は全部残し、画面で主に見せるのは「GPU の秒数」と「生成トークン数」**
3. **会話の中身(発言の文章)は記録に写さない**。記録するのは数字と、だれ・いつ・どのモデルか、だけ。会話そのものは今までどおり server.db に残る
   (中身を写すと、会話を消しても残り、管理者が読める範囲の決まり(0018)の外で中身が見えるため)
4. **記録は消さずに残す**。会話や利用者を消しても残す。大きくなって困ったら、あとで「n 日(例:90 日)より前の記録を消す」機能を足す(今回は作らない)
5. **上限は今回は作らない**。記録を見てから決める
6. **見られる人:管理者は全員の分、本人は自分の分**

話の流れから Chat が決めて書いたこと(ユーザーに確認してもらう):

7. **1行に持つもの**:時刻・利用者の ID と名前(消された人の分も読めるように、名前を写す)・道(ブラウザ / アプリ / それ以外の API。下の未決事項 1)・会話の ID(分かるときだけ)・モデルの ID・
   プロンプトのトークン数・使い回した数・生成のトークン数・画像のトークン数・プロンプトの秒数・生成の秒数・エンコードの秒数・順番待ちの秒数(分かるときだけ)・終了理由。
   **GPU の秒数 = プロンプトの秒数 + 生成の秒数 + エンコードの秒数**(モデルの読み込みの秒数は入れない。読み込みは会話をした人のせいとは限らないため)
8. **会話の ID と利用者の ID は外部キーにしない**(ただの値として持つ)。会話や利用者を消しても行が消えないように(決定事項 4)
9. **保存は server.db に表を1つ足す**(DB の版 20。`usage` は 0009 のメーターの `aibow.Usage` と紛らわしいので、表の名前は `generation_log` などにする。名前は Code が決めてよい)
10. **書く位置**:`_cmd/aibow-server` で engine を包む「記録付きの engine」を作り、`api.New` と `ui.NewServerHost` の両方にそれを渡す。
   `Generate` が終わったら、ctx から呼んだ人を読んで1行書く。会話の仕組み(ルートの `aibow`)と `api` / `ui` の生成の道は変えない(変えるのは、道や会話の ID を ctx で運ぶのに要る分だけ)
11. **書けなくても生成は止めない**(記録のためのもので、使えるかどうかには関わらない。Warn のログを出す。0031 の「最後に使った日」と同じ考え方)。失敗した生成(エラー)も、秒数が使われていれば記録する。停止した生成(cancel)も記録する
12. **呼んだ人が ctx に無いとき**は、利用者を空にして記録し、Warn のログを出す(どの道で抜けているかを見つけるため)
13. **見る場所**:
    - 管理者:管理の画面(0032)に「使用量」のタブ。期間(今日・7日・30日)を選び、利用者ごとに回数・GPU の秒数・生成トークン数を並べる。人を選ぶと、モデルごと・日ごとの内訳
    - 本人:設定の「アカウント」のタブに、自分の今日・7日・30日の回数・GPU の秒数・生成トークン数
    - ログインなしの形(利用者 `local` だけ)では、管理の画面の「使用量」だけを出す(サーバーの PC から開いた画面。0032 の決定事項 4 と同じ線)
14. **集計は SQL で行う**(日ごとの合計の表は作らない。行が増えて遅くなったら、索引か集計の表を考える)

## 決めたこと(段2・段3)

Code が決めたこと(2026-11-01):

24. **全員の分を見られる人**:ログインが要る形では、ログインした管理者だけ(利用者のタブと同じ線)。サーバーの PC の上から開いた管理者でない人には、管理の画面に「使用量」を出さず、口も 403 で断る
    (モデル・ツールのタブはサーバーの PC の事情なので見せるが、使用量は人の情報なので)。ログインなしの形では、サーバーの PC の上(127.0.0.1)からの呼び出しだけを通す
25. **口**:全員の分は `GET /aibow/admin/usage?days=N`(利用者ごと)と `GET /aibow/admin/usage/user?id=<ID>&days=N`(1人のモデルごと・日ごと)。
    自分の分は `GET /aibow/auth/usage`(今日・7日・30日)で、ブラウザ(cookie)と画面のアプリ(アプリ用のトークン。`api/client` の `MyUsage`・`ChatService.MyUsage`)の両方から呼ぶ。
    期間は今日を含めた日数(1〜366)、日の区切りはサーバーの PC の時刻
26. **表に出す数字**:回数・GPU の秒数・生成トークン数(決定事項 2)。要約の回数・プロンプトのトークン数(使い回した数)・画像のトークン数・順番待ちの秒数は、行のバルーンに出す。
    利用者ごとの表は GPU の秒数の多い順。消された人は記録に写した名前と「消した人」の印、今いる人は今の表示名で出す

確かめたこと(2026-11-01、一時フォルダの server.json で aibow-server を起動):

## 決めたこと(段1)

ユーザーと決めたこと(2026-11-01、Code が案を示した):

15. **道は3つ**:ブラウザ(`browser`)/ アプリ(`app`。OpenAI 互換の口に `aibow` 欄がある)/ それ以外の API(`api`。Cline・curl など)。
    見分け方は受け付けたときのログ(`logAccepted`)と同じ。API キーとアプリ用のトークンは分けて残さない(アプリかどうかは `aibow` 欄で分かるため)
16. **要約は返事と分けて記録する(ブラウザもアプリも)**:1行に用途(`purpose`:`reply` 返事 / `summary` 要約)を持つ。ツールのループの1回は返事。
    アプリの要約は、`api/client` が `aibow` 欄の `purpose`・`conversation` で知らせる(会話の ID もアプリから分かるようになった)
17. **画面はまず表だけで作る**:管理の画面は期間(今日・7日・30日)と利用者ごとの表、人を押すとモデルごと・日ごとの表。アカウントのタブは今日・7日・30日の3行の表。グラフは見てから決める
18. **ログインなしの形(127.0.0.1・`login: false`)の OpenAI 互換の口は、利用者 `local` の分として記録する**(保存の口 `/aibow/store/` がこの形で `local` を使うのと同じ線)。
    決定事項 12 の「利用者を空にして Warn」は、ログインが要る形で人が分からないとき(作りの抜け)だけになる

Code が決めたこと(2026-11-01):

19. **付箋は新しいパッケージ `usage` に置く**:「だれが・どの道で・何のために」を、生成を呼ぶ側が ctx に付け(`usage.WithRoute`・`WithPurpose`・`WithWait`)、記録付きの engine が読む。
    (はじめは、メーターの `aibow.Usage` と紛らわしいので `genlog` という名前にした。役割が読みにくいので、2026-11-08、ユーザーの指示で `usage` に変えた。メーターの `aibow.Usage` はそのまま)
    会話の仕組み(ルートの `aibow`)・`api`・`api/client`・`ui`・`store` のどれからも使うので、何にも依存しない小さなパッケージにした(engine は会話のことを知らない約束なので、engine には置かない)。
    付ける場所:道は HTTP の口(`api` の `handleChat`・`ui.Handler`)、用途と会話は会話の仕組み(`generate`・`generateSummary`)と、`aibow` 欄を読んだ `api`
20. **順番待ちの秒数**:OpenAI 互換の口はリクエスト(= 生成1回)ごと、ブラウザの会話は送信ごと(ツールのループで何回も生成する)。送信の待ちは、その送信の最初の生成の行にだけ書く(`usage.TakeWait` が1回だけ返す)。分からない行は NULL
21. **書かない生成**:失敗して GPU の秒数が 0(モデルが無い・ほかの生成の途中など、生成まで行かなかった)は書かない。途中で失敗した生成は終了理由 `error` で書く。
    時刻は生成を始めた時刻、モデルは始めたときに読み込んでいたモデル(生成は席の中なので入れ替わらない)。だれかは `auth.UserFrom`(API キー・ログイン)、無ければ `aibow.UserOf`(ブラウザの local)の人で、名前は server.db から写す
22. **大きさ(未決事項 4 を測った)**:1行は索引込みで **約 400 バイト**(ID・利用者・会話の UUID の文字列が大きく、2つの索引にも入るため。1万行で 4.0 MB)。
    10人が1日 200 回なら1日 0.8 MB、1年で約 290 MB(Chat の見積もり 100 MB の約 3 倍)。書き込みは1行約 9 ms(生成1回は数秒なので、生成の後に同じ流れで書く)。
    30日・1万行の利用者ごとの集計は約 30 ms。困ったら「n 日より前を消す」(やらないこと)か、ID を短くする
23. **server.db は aibow-server の `main` が開く**(以前は `startBrowser` の中)。記録付きの engine を、OpenAI 互換の口とブラウザの会話の両方に渡すため
