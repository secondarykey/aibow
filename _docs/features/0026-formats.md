## 目的

**2つ目の書式として Gemma 4 を手で書き、Qwen3.5 と並べて使えるようにする**。あわせて、3つ目以降の書式も同じ形で足せるよう、2つで使う部品を切り出す。

手元の `_cmd/aibow/models/gemma-4-E4B-it-Q4_K_M.gguf` は `general.architecture = gemma4` で、今は一覧に出ても「このモデルの書式には未対応です」で使えない。

学ぶこと:

- **書式は「区切りの文字」だけでなく、会話の形そのものが違う**:Qwen3.5 はツールの結果を user の発言にするが、Gemma 4 は model の発言の中に入れる。思考の ON / OFF も、返事の書き出しで切り替えるか、システムの印で切り替えるかで違う
- **ツール呼び出しの書き方の流儀**:XML 風(Qwen3.5)・JSON(Qwen3 など)・独自の型つきの書き方(Gemma 4)。値に型があるかで、aibow の「引数の持ち方」が変わる
- **2つ目の実装が来て初めて、共通にできる部分が分かる**(0005 の決定事項 11 の「使う相手が現れたら分ける」)
- 同じ質問で Qwen3.5 と Gemma 4 を比べる(速さ・答え・ツールの使い方)

## 調べて分かったこと(2026-10-30、Chat が調べた)

出典:手元の GGUF の `tokenizer.chat_template`(18,810 文字。GGUF の先頭を読んで取り出した)と、Google の [Gemma 4 Prompt Formatting](https://ai.google.dev/gemma/docs/core/prompt-formatting-gemma4)。

GGUF の情報:`general.architecture = gemma4`・`general.quantized_by = Unsloth`・`tokenizer.ggml.add_bos_token = True`(bos 2・eos 106)・推奨のサンプリング `temp 1.0 / top_k 64 / top_p 0.95`・作業領域の上限 131,072・ファイルの大きさ約 5.0 GB。

| | Qwen3.5 | Gemma 4 |
|---|---|---|
| 会話の区切り | `<\|im_start\|>role\n … <\|im_end\|>\n` | `<\|turn>role\n … <turn\|>\n`(役は system / user / **model**)。先頭に bos |
| 思考の ON / OFF | 返事の書き出しを `<think>\n`(ON)か `<think>\n\n</think>\n\n`(OFF)にする | **システムの発言の先頭に `<\|think\|>` を入れる**(ON)/ 入れない(OFF)。ON ならシステムの発言が無くても作る |
| 思考の出力 | `<think> … </think>` | `<\|channel>thought\n … <channel\|>` |
| 前の思考 | 最後のユーザーの発言より後(ツールのループの途中)だけ残す | 同じ(公式の文書も「ツールの呼び出しの間の思考は消さない」) |
| ツールの説明 | システムに `# Tools` と JSON と英語の指示文 | システムに `<\|tool>declaration:名前{description:…,parameters:{…}}<tool\|>`。**JSON ではない独自の書き方**(文字列は `<\|"\|>…<\|"\|>` で囲む・キーは**アルファベット順**・型は `STRING` など大文字)。指示文は無い |
| ツールの呼び出し | `<tool_call><function=…><parameter=…>値</parameter>…`(値は文字列) | `<\|tool_call>call:名前{キー:値,…}<tool_call\|>`。**値に型がある**(文字列は `<\|"\|>…<\|"\|>`、数・true/false はそのまま、`{}` `[]` も)。テンプレートはキーをアルファベット順に並べ直して書く |
| ツールの結果 | **user の発言**の中に `<tool_response>…</tool_response>` | **model の発言の中のまま**、呼び出しのすぐ後に `<\|tool_response>response:名前{value:<\|"\|>…<\|"\|>}<tool_response\|>`。**結果にツールの名前が要る** |
| 結果のあと | 新しい `<\|im_start\|>assistant` から書く | 同じ model の発言の続きを書く(思考 ON なら `<\|channel>thought\n` から) |
| 止める | `</tool_call>` の後に `<tool_response>` を書き始めたら | **`<\|tool_response>` を止める印にする**(公式の文書の「追加の停止シーケンス」)。モデルはそこで止まり、aibow が `response:…<tool_response\|>` を続けて書く |
| 画像 | (別の話) | `<\|image\|>` などの印がある(この仕様では作らない) |

- 思考を切ったとき、大きいモデル(26B・31B)は思考を書いてしまうことがあり、空の思考 `<|channel>thought<channel|>` を入れると落ち着く、と公式の文書にある。E4B については書いていない
- 手元の GGUF のテンプレートは Unsloth が量子化したときのもの。Google が配っている元のテンプレートと同じかは**未確認**
- Tokenize は `addSpecial=true` で呼んでいる(`engine/engine.go`)。Gemma 4 は `add_bos_token = True` なので、テンプレートどおり文字で bos を書くと bos が2つになるおそれがある

## 決定事項(ユーザーと決めたこと。2026-10-30)

1. **ツールの引数の値は、書式によらない形にそろえる**。文字列はそのまま、数・真偽・null・配列・オブジェクトは JSON の文字で持つ(`tool.Arg.Value`)。プロンプトに書くときは、書式がツールの定義の型を見て書き直す
   - 公式のテンプレートも、呼び出しをキーの並べ替えまでして書き直しているので、それに合わせる
   - 会話の途中でモデルを Qwen3.5 と Gemma 4 で替えても、前の呼び出しを新しい書式で書ける
   - OpenAI 互換の口(`api/tools.go`)の `arguments` の JSON も、この形から作る
   - Qwen3.5 は値をいつも文字列で書くので、文字列の値は今と同じ。数などは「型に合う文字ならそのまま JSON の値」になる(今の `CheckArgs` の変換と同じ考え方)。保存済みの会話を読めること・Qwen3.5 の期待値のテストが今のまま通ることを確かめる
2. **正とするテンプレートは、手元の GGUF の中のもの**。空白と改行の1文字まで合わせる(今の Qwen3.5 と同じ作り方)。Google の文書の例と食い違わないかも確かめる
3. **作るのは、会話・思考・ツール呼び出しまで**。画像・音声の印は作らない(「画像を読む」の行で別に考える)

## 決定事項(話の流れから Chat が決めて書いたこと。2026-10-30 にユーザーが確かめた)

### Gemma 4 の書式

4. Gemma 4 の書式は `format/gemma4.go` に手で書き、`general.architecture = gemma4` で選ぶ。Jinja を動かす汎用の形は作らない(書式は自分で書く方針のまま)
5. **ツールの結果にツールの名前を持たせる**:`format.Message` に名前(ツールの結果のときだけ)を足し、会話の仕組みがそのツールの結果の元の呼び出しから入れる。名前が無いとき(古い会話)は、直前の返事の呼び出しと順番で組にする
6. ツールの結果は、文字の結果1つとして `response:名前{value:<|"|>…<|"|>}` で書く(テンプレートの「結果が文字のとき」の形)
7. 生成は `<|tool_response>` が出たら止める(公式の停止シーケンス)。aibow が結果を続けて書くので、次の送信で KV キャッシュの頭がそろう
8. 思考を切ったときに空の思考を入れるかは、書式の中の1か所で決める。E4B では入れない(公式の文書は大きいモデルだけに勧めている)
9. **bos は2つにしない**。書式は bos を文字で書かず、トークン化(`addSpecial`)に任せる。テストの期待値は、テンプレートの出力から bos を外して比べる(Code が確かめて決める。未決事項)
10. 呼び出しを読むときは、Qwen3.5 と同じくコードブロックの中の `<|tool_call>` は呼び出しと見ない。ただし Gemma 4 の呼び出しは行の頭とは限らない(思考の直後や答えの続きに書く)ので、行の頭の決まりは使わない
11. 書式が崩れた呼び出し(閉じていない・値が読めない など)は、今と同じく `Raw` と `Error`(正しい書き方の例つき)を持たせてモデルに返す

### 作業中に決めたこと(段1。2026-10-30、Code が決めた。決定事項 1 を形にするための細部)

### 段2で分かったこと(2026-10-30、Code が調べた)

期待値の仕組みは `format/testdata/gen_expected.py <書式の名前> <GGUF>` の1つにし、会話は `format/testdata/cases.json` で共通にした(作り方は `_docs/tools.md` の「期待値の作り方」)。
スクリプトを作り直したあと、Qwen3.5 の期待値9件は1バイトも変わらなかった。型のある引数のケース(`typed_args`)を足し、Qwen3.5 の書式は段1の形のまま一致した(整数・数・配列・オブジェクト・型に合わない ` 5`)。Gemma 4 の期待値は11件。

**テンプレートの違い(未決事項)**:手元の GGUF と、Google の配っている元のテンプレート(`google/gemma-4-E4B-it` の `chat_template.jinja`。2026-07-09 版)を比べた。違いは2つだけ:

- 元のテンプレートの先頭のコメント(出力には出ない)
- 呼び出しの `arguments` が**文字列**で渡されたとき:GGUF(Unsloth)は外側の `{}` を外してそのまま書き、元のテンプレートはエラーにする。aibow は引数をいつもオブジェクトで渡すので、aibow の出力は同じになる

ほか:GGUF の eos は `<turn|>`(106)で、Google の `tokenizer_config.json` は `<eos>`。llama.cpp は GGUF の eos で止まるので、返事の終わり(`<turn|>`)で止まる。

**bos(未決事項・決定事項 9)**:Qwen3.5 の GGUF は `add_bos_token = False` で bos のトークンも無い。Gemma 4 は `add_bos_token = True`(`<bos>`、2)で、テンプレートも先頭に `bos_token` を書く。
aibow のトークン化は `addSpecial=true`(`engine/engine.go` の `tokenize`)なので、書式が `<bos>` を文字で書くと2つになる。期待値はテンプレートの出力から先頭の bos を1つ外して作った(スクリプトが `add_bos_token` を見て外す)。
実際に bos が1つだけになるかは、段3でモデルを読み込んでトークンを数えて確かめる

**Google の文書と比べて**:食い違いは見つからなかった(答えはツールの結果の後ろ、`<|tool_response>` で止める、ツールの呼び出しの間の思考は消さない。bos には触れていない)

**段3で Gemma 4 の書式を書くときに気をつけること**(テンプレートの動き。決定事項 2 のとおり、このまま合わせる):

- **ツールを呼んだ返事の答えの文は、ツールの結果の後ろに置かれる**(`two_calls_then_next_question`:`…<tool_response|>調べます。今日は…`)。モデルは答えの文を呼び出しの前に書くので、次の送信のプロンプトはモデルが書いた順と違い、そこから先は KV キャッシュを使い回せない。どれだけ困るかは段5で測る
- ツールの結果の後ろの返事は、同じ model の発言の続きとして区切りなしにつながる(`調べます。` + `今日は…`)。答えは前後の空白を落とす
- 返事の書き出し:思考 ON なら `<|turn>model\n` だけで、モデル自身が `<|channel>thought\n` から書く。ツールの結果の後ろで思考 ON なら `<|channel>thought\n` まで書いてある(読み取りの始まりの状態が、プロンプトの終わり方で変わる)。思考 OFF でツールの結果の後ろなら、何も足さない
- 思考は `<|channel>thought\n` + 思考 + `\n<channel|>`(Qwen3.5 と違い、前後の空白を落とさない)。最後のユーザーの発言より前の返事の思考は入れない
- ツールの結果も前後の空白を落とさない(`52.142857142857146\n` のまま)
- ツールの説明:引数はキーの名前の順、型は大文字。`type` が配列(`["boolean", "null"]`)だと、Python のリストの見た目がそのまま出る(`['BOOLEAN', 'NULL']`)。properties の無い object の引数は `properties:{}` が付く。MCP のサーバーの定義には配列の型がよくあるので、このまま合わせる
- 呼び出しの引数もキーの名前の順。文字列は `<|"|>…<|"|>`、数・真偽はそのまま、オブジェクトのキーは引用なし(`{n:2,sort:<|"|>name<|"|>}`)。型に合わない ` 5` は文字列で書かれる

**Qwen3.5 の真偽の書き方(新しい未決事項)**:Qwen3.5 のテンプレートは配列・オブジェクトでない値を Python の `str()` で書くので、真偽は `True` / `False`。段1の aibow は JSON のまま `true` と書く(決定事項 22)。
そのため真偽の引数のケース(`typed_args_boolean`)は、今は Gemma 4 だけにしている(下の 26 で、段3でテンプレートどおりにする)

### 段3で決めたこと・分かったこと(2026-10-30、Code)

`format/gemma4.go` を書き、Gemma 4 の期待値11件と Qwen3.5 の期待値11件(真偽のケースを Qwen3.5 でも試すようにした)が1文字まで一致した。ツールの結果に名前が無いとき(順番で組にする)も同じになる。
まだ本物のモデルで生成していない(段5で確かめる)。

27. **`Format.NewParser` は `Prompt` を受け取る**(`NewParser(p Prompt)`)。Gemma 4 は、ツールの結果の後ろで思考 ON なら、プロンプトが `<|channel>thought\n` まで書いてあるので思考の途中から読み始める。それを知るには、プロンプトの終わり方が要るため

    aibow のクライアントは tool の発言に `name` も付けて送る(崩れた呼び出しの結果には `id` が無いため)
29. aibow のクライアントが `tool_call_id` を付ける順が、崩れた呼び出しがあると1つずれていた(崩れた呼び出しの分の場所を取っていなかった)のを直した。今までは書式が `id` を読まなかったので表に出ていなかった
30. Qwen3.5 は、決定事項 26 の真偽に合わせて、null もテンプレートどおり `None` で書き、モデルが書いた `None` を null として読む(同じ「Python の str()」の決まりなので)
31. 未対応のエラーの文は、Gemma 4 を足すと「Qwen3.5 だけです」が間違いになるので、段4を待たずに対応している書式を一覧から出すようにした(決定事項 14。`format.Supported`)
32. 2つで使う部品は `format/parts.go` に出した(`partialSuffix`・`partialSuffixAny`・`insideCodeFence`・`brokenCall`。決定事項 12)。思考の切り分けは Qwen3.5(`</think>` を待つ)と Gemma 4(`<|channel>` から `<channel|>` まで)で形が違うので、共通にしなかった
