## 目的

会話の入力欄に、**ファイルを選ぶ・ドロップ・貼り付け**でファイルを読み込み、その中身についてモデルに質問できるようにする。
読み込めるのは**テキストのファイル**(どのモデルでも)と**画像**(画像を読めるモデルだけ)。画像の読み込みは「ファイルを読み込む」の中の1つとして作る。

学ぶこと:

- **画像もトークンになる**:画像エンコーダー(mmproj)が画像を「画像トークン」の埋め込みにし、文字のトークンと同じ列でモデルが読む。1枚で数百〜千トークン以上使う。ツールではなくモデル自身の機能
- **書式は「場所の印」だけを書く**:画像の中身はプロンプトの文字列に入らない。文字列とトークン列が1対1でなくなる(チャンクの列になる)
- **KV キャッシュと画像**:画像は文字ではないので、前回と同じかを「トークンの比較」ではなく「画像の ID(ハッシュ)」で比べる
- **compact と添付**:ファイルや画像は重いので、会話の上限をすぐ使う。要約でどう扱うか
- テキストのファイルは、モデルから見ればただの文字:会話の仕組みが発言に展開するだけで、書式もエンジンも変わらない(画像との違い)

## 調べて分かったこと(2026-10-30、Chat が調べた)

### cgo なしで使えるか → 使える

- yzma の `pkg/mtmd` は `pkg/llama` と同じ仕組み(`jupiterrider/ffi`。土台は purego)で DLL を呼ぶ。C のコンパイラは要らず、`CGO_ENABLED=0` のまま使える
- 呼ぶ相手は `mtmd.dll`。ユーザーの `_cmd/aibow/lib\` にもう入っている(llama.cpp の配布物に含まれる)。`mtmd.Load(lib のパス)` で読む
- Go の外部パッケージは増えない(yzma の中のパッケージを1つ多く使うだけ)

### 画像の流れ(yzma の `examples/vlm`)

```
mmproj.gguf を読む(mtmd.InitFromFile。読み込んだ本体のモデルを渡す)
画像のバイト列 → Bitmap(mtmd.BitmapInitFromBuf。jpg・png などは llama.cpp 側で読む)
プロンプトの文字列(画像の場所に印 <__media__>)+ Bitmap の列 → チャンクの列(mtmd.Tokenize)
   チャンク = 文字のトークン列 / 画像(画像トークン数 n_tokens と位置の数 n_pos を持つ)
チャンクを順に読ませる(mtmd.HelperEvalChunks。画像は画像エンコーダーで埋め込みにしてから decode)
あとは今と同じく1トークンずつ生成
```

- 画像の場所に `mtmd.DefaultMarker()`(`<__media__>`)を書けば、mtmd がそこを「始まりの印 + 画像の埋め込み + 終わりの印」に置き換える。
  Qwen 系(projector の種類 qwen2vl / qwen25vl / qwen3vl)は始まり `<|vision_start|>`・終わり `<|vision_end|>` を mtmd が足す。
  公式テンプレートの `<|vision_start|><|image_pad|><|vision_end|>` の3つまとめてを `<__media__>` に置き換える形になる(Gemma 4 も mtmd に対応がある:`<|image>` … `<image|>`)
- 画像のトークン数は、エンコードしなくても数えられる:`BitmapInitFromBuf(..., placeholder=true)` は縦横だけを持つ Bitmap を作り、Tokenize すれば画像トークン数が分かる
- 画像のトークン数の上限は `ContextParams.ImageMaxTokens` で決められる(既定は -1 = mmproj の値)。mmproj は `UseGPU` で GPU / CPU を選べる
- Ollama は画像の部品を、目録の中で mediaType `application/vnd.ollama.image.projector` の層として持つ(Ollama のソースの `server/model.go`)。今の aibow の目録の読み取り(`models/models.go`)は `application/vnd.ollama.image.model` だけを見ている

### テキストのファイル

- Go の標準ライブラリには Shift_JIS を読む部品が無い(`golang.org/x/text` が要る)。UTF-16 は BOM があれば標準の `unicode/utf16` で読める

### 未確認(段1で Code が確かめる)

- Qwen3.5 の mmproj の projector の種類(GGUF の `clip.projector_type`)。qwen3vl 系なら上の印のとおり。違えば印が変わる
- ユーザーの Ollama の qwen3.5:4b / 9b に projector の層があるか、llama.cpp で読めるか(Ollama の独自形式のこともある)
- 1枚の画像が何トークンになるか(大きさごと)・エンコードにかかる時間・mmproj の VRAM。9B(7.9 / 8.2 GB)では GPU に載らない見込み
- Qwen3.5 は M-RoPE(画像の位置を縦横で持つ)なので、画像のチャンクはトークン数と位置の数が違う。`BatchGetOne`(位置を自動で振る)と混ぜて大丈夫か。だめなら文字のチャンクも位置を指定して読ませる

2. **画像は、まず Qwen3.5 だけ**。mmproj は Ollama の目録の projector の層から見つける(models フォルダの GGUF の横の mmproj・Gemma 4 は今回は作らない)
3. **読み込んだファイルは会話の DB の別テーブルに保存する**(画像もテキストも同じテーブル。種類・名前・形式・ハッシュ・バイト列)。aibow-server では server.db に入り、会話の持ち主・共有の決まり(store の SQL の1か所)がそのまま効く。`store/remote` も同じ口で運ぶ
4. **要約(compact の summary)では、画像は「[画像]」、テキストのファイルは「[ファイル: 名前]」の文字に置き換えて渡す**。truncate は今のまま、ファイルの付いた発言も丸ごと捨てる
5. **テキストのファイルは、読み込んだファイルとして保存し、プロンプトを作るときに会話の仕組みが発言の頭へ「ファイル名 + 中身」の文字として展開する**。書式は何も知らない。画面の吹き出しには中身を出さず、ファイル名の札だけを出す
6. **会話の上限に入らないテキストのファイルは、読み込んだときにトークン数を数え、入らなければ「○○ トークンで、残りは △△ です」と出して付けない**(黙って切らない)。大きいものは作業フォルダの `read_file`(範囲を指定して読める)へ案内する
7. **文字コードは UTF-8(BOM ありも)と、BOM のある UTF-16 だけ**。それ以外は「UTF-8 で保存し直してください」のエラー。外部パッケージは足さない

### 段1(2026-10-31。画像の確かめ)

リポジトリの外の試しのプログラム(yzma v1.29.1 の `pkg/mtmd`・llama.cpp はユーザーの `_cmd/aibow/lib`)で、Ollama の qwen3.5:4b / 9b を読んで測った。
GPU は RTX 4060(8 GB。デスクトップなどで 3 GB 前後を使っている状態)。

**mmproj と Ollama の目録**

- qwen3.5:4b / 9b とも、目録に mediaType `application/vnd.ollama.image.projector` の層がある(4b は 644 MB、9b は 879 MB)。
  中身は llama.cpp の普通の mmproj の GGUF(`general.architecture = clip`・`general.type = mmproj`・BF16)で、`mtmd.InitFromFile` でそのまま読めた(Ollama の独自形式ではない)
- projector の種類(`clip.projector_type`)は **`qwen3vl_merger`**。印は `<__media__>`(`mtmd.DefaultMarker()` と `mtmd.GetMarker` が同じ)。
  mtmd がその前後に `<|vision_start|>`・`<|vision_end|>` を足す(下の「チャンク」で文字のトークン数から確かめた:印の前の文字のチャンクは `<|im_start|>user\n` の 4 トークンだけ)
- 本体の GGUF は `qwen35.rope.dimension_sections = [11, 11, 10, 0]`(M-RoPE)。`mtmd.DecodeUseMRope` は true

**画像のトークン数**(`clip.vision.patch_size = 16` × `spatial_merge_size = 2` なので、32 ピクセル四方で 1 トークン)

| 画像 | トークン数 | 位置の数(`n_pos`) | 縦横(トークン) |
|---|---|---|---|
| 256×256 | 64 | 8 | 8×8 |
| 768×768 | 576 | 24 | 24×24 |
| 1024×768 | 768 | 32 | 32×24 |
| 1920×1080 | 2,040 | 60 | 60×34 |
| 3000×4000 | 4,015 | 73 | 55×73(mmproj の上限で縮めた) |
| 1920×1080(`ImageMaxTokens = 256`) | 252 | 21 | 21×12 |

- 位置の数は縦横の大きいほう(`max(nx, ny)`)。トークン数と位置の数が違う(768 トークンが 32 位置)
- 数えるだけなら placeholder の Bitmap(`BitmapInitFromBuf(…, placeholder=true)`)で 1 ミリ秒未満。mmproj を読み込んでいることが要る
- 既定(`ImageMaxTokens = -1`)では 1 枚 4,000 トークンほどまで使う。会話の上限の既定(8,192)の半分。`ImageMaxTokens = 256` でも、赤い四角と青い丸を答えられた

**時間と VRAM**(1024×768・768 トークン)

| | mmproj を GPU | mmproj を CPU |
|---|---|---|
| 4B(全部の層を GPU)のエンコード / decode | 0.27 秒 / 0.29 秒 | 8.5 秒 / 0.4 秒 |
| 9B(32 層のうち 24 層を GPU)のエンコード / decode | 0.5〜0.7 秒 / 0.66 秒 | 11.4 秒 / 0.9〜1.0 秒 |

- エンコードは GPU で CPU の 15〜30 倍速い。decode(埋め込みを KV キャッシュに入れる)は文字 768 トークンを読ませるのと同じくらい
- VRAM:4B の mmproj を GPU に載せると約 0.7 GB 増える(本体 2.6 GB・作業領域 8,192 で 0.8 GB)。エンコード中の増えは 0.1 GB ほど。
  9B の mmproj は約 0.9 GB(BF16)。9B は 24 層 + mmproj(GPU)+ 作業領域 8,192 で、ほかの 3 GB と合わせて 7.6 GB に入った
- mmproj の読み込みは 0.5〜1 秒(GPU)

**M-RoPE の位置と BatchGetOne**

- 画像のチャンクを読ませたあと、KV キャッシュの位置の最大(`MemorySeqPosMax`)は**画像の始まりの位置のまま**(画像のマスの位置は時間の成分 t = 始まりの位置)。
  なので、画像のあとの文字を `BatchGetOne` の位置の自動(位置の最大 + 1)で読ませると、位置がずれる(正しくは 61 のところが 37 になった。答えは偶然合ったが、logits は 0.8 ずれた)。
  **画像より後ろの文字は、位置を自分で書く**(`batch.Pos`。1 トークンに 1 つでよい。文字は llama.cpp が M-RoPE の4つに広げる)。
  helper(`HelperEvalChunks`)は文字のチャンクも位置を書いて読ませるので、最後のチャンクが文字なら、そのあとの生成は自動の位置でも合う
- 画像のチャンクを helper を使わずに読ませる形も確かめた:`EncodeChunk` → `GetOutputEmbd`(トークン数 × `ModelNEmbdInp`)→ 埋め込みの batch(`Embd` と、
  位置を `ImageTokensGetDecoderPos` で 1 トークンに4つ。並びは **t・y・x・z の列ごと**(`pos[i]`・`pos[n+i]`・`pos[2n+i]`・`pos[3n+i]`))を 512 トークンずつ decode。
  helper と最後の logits が**完全に一致した**(差 0.00000。t・x・y の並びにすると 1.7 ずれる)。yzma には helper の「チャンク1つだけ読ませる」(`mtmd_helper_eval_chunk_single`)が無いので、
  KV キャッシュの使い回しで途中のチャンクから読ませるにはこの形が要る
- `MemorySeqRm` に渡すのは**位置**(トークン数ではない)。今のエンジンの `reuseCache` はトークン数を位置として渡しているので、画像の後ろで切るときは位置に直す

**KV キャッシュの使い回し(チャンクで比べる)**

- 1 回目(画像 + 質問)→ 答え → 2 回目(同じ画像の会話の続き)で、チャンクの列を比べ(文字はトークン、画像は ID)、同じところまでを読み直さずに続きだけ読ませた:
  828 トークンのうち 805 を使い回し、続きは 0.05 秒(最初から読ませると 0.60 秒)。答えは同じ(「Blue」)
- 画像の ID(`BitmapGetId`・`InputChunkGetId`)は、helper で読んだ Bitmap なら中身のハッシュ(16 進 64 文字)が最初から入っている。比べるのはこれ(か `File.Hash` を `BitmapSetId` で入れる)
- KV キャッシュで使うマスの数はトークン数(位置の数ではない)。作業領域が足りるかはトークン数で数える

### 段3(2026-10-31。会話の仕組みと画面)

- 会話の仕組み(`files.go`):画像は中身の先頭の印で決める(`imageFormat`。PNG・JPEG・GIF・BMP。BMP はヘッダーのファイルの大きさも見て「BM」で始まるテキストと見分ける)。
  WebP は llama.cpp(stb_image)が読めないので、画像だと分かったうえで「PNG か JPEG で保存し直してください」のエラーにした(決定事項 9 の例に WebP があったが、読めないため)。

- 要約は「[画像]」。画像を読めないモデル・書式は `engine.ErrNoVision` で見分けられるエラーにし、メーターは出さない(会話を開くのは止めない)。送るときは保存する前に止まる

- aibow-server 越し(`api/client`)は、画像の付いたプロンプトを黙って画像なしで送らないよう、`ErrNoVision` で断るようにした(段4で送れるようにした)
