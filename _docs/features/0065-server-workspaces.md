## 目的

aibow-server の資料のフォルダは、配布プロファイルで**フォルダを1つだけ**選べる(`ProfileRules.Folder`)。
アプリのワークスペース(0035)は、フォルダを複数持ち(メイン・書ける / 読むだけ・説明)、ファイルのツールは引数 `folder` でフォルダを選べる。
資料のフォルダも同じ形にして、**「サーバーのワークスペース」**として扱う(例:「規程」「過去の議事録(読むだけ)」「下書き(書ける)」を1つの組にして配る)。

これは段1(ブラウザだけ)。アプリから使う段2の土台にもなる(段2は会話がサーバーのワークスペースを持つ形にする見込みなので、先にサーバーにワークスペースという形を作っておく)。

学ぶこと:

- **同じ形を2か所で使う**:ファイルのツールはもともと複数のフォルダを扱える(`tool.FilesIn`)。ブラウザ側で1つに絞っているところ(`toolFolders` の `tool.Single`)を外すだけで、ツールの中は変わらない。形をそろえると、作るところが小さくなる
- **設定ファイルの形を変えるときの移し方**:前の形(`folders`)を読めるまま、新しい形(`workspaces`)へ移す。手で書いたファイルを黙って壊さない

## 今の作り(2026-11-25、Chat がコードを読んで確かめた)

- `server.json` の `folders` は「名前 → 絶対パス」の表(`config.ServerFile.Folders`)。起動のときに名前が空でないか・絶対パスか・フォルダがあるかを確かめる(`checkFolders`)。
  管理の画面の「資料のフォルダ」のタブで、足す・パスを変える・消すができ(`ui/serverconfig.go`。名前は変えられない)、`config.SaveServerFile` が `folders` の鍵だけを差し替えて書き戻す。その場で効く(`Conversations.SetFolders`)
- 配布プロファイルの決まり `ProfileRules.Folder`(名前)で1つ選ぶ。効くのは配っていて、その人にまだ配られているときだけ(`Profile.GrantedFolder`)。写したプロファイルには写さない(`profile.go`)。
  選べるのは管理者だけ(`ui.checkFolder`)。選んでいるプロファイルがあるフォルダは消せない(`store.SQLite.ProfilesUsingFolder`。`json_extract(rules, '$.folder')`)
- ブラウザの会話では、`workDir` が資料のフォルダのパス、`toolFolders` が `tool.Single(workDir)`(名前はパスの末尾・メイン・書ける)。
  モデルへの環境の説明はパスを見せず名前だけ(`prompt.go` の `environment`。「a shared folder on the server」。0024 の決定事項 32)。
  フォルダが複数のときの説明 `foldersEnvironment` は**パスも書く**(アプリのワークスペース用)
- ブラウザには `run_command` を出さない(`ui.forBrowser`)。worktree・git はアプリだけ。`${workdir}` の MCP のサーバーは、資料のフォルダのある会話で、フォルダごとに1つ起動する(0024 の決定事項 8・33)
- 画面:入力欄の上の `FolderBar`(名前だけ・押せない)、会話の設定の画面・プロファイルの画面の「資料のフォルダ」、管理の画面の「資料のフォルダ」のタブ(`ServerFolders`)

### server.json の形と移し方

8. **新しい鍵 `workspaces`(配列)に書く**。1つのワークスペースは名前とフォルダの組:
   ```json
   "workspaces": [
     { "name": "社内規程", "folders": [
       { "name": "規程", "path": "D:\\share\\rules", "main": true, "writable": true },
       { "name": "議事録", "path": "D:\\share\\minutes", "description": "2024 年からの議事録" }
     ] }
   ]
   ```
   フォルダの欄はアプリの `config.WorkspaceFolder` と同じ(`path`・`name`・`main`・`writable`・`description`)で、型もそれを使う(`config.ServerWorkspace{Name, Folders []WorkspaceFolder}`)。ID・worktree は持たない
9. **確かめること**(起動のときと、画面から書く前):ワークスペースの名前が空でなく重ならない、フォルダが1つ以上でメインがちょうど1つ、フォルダの名前はアプリと同じ決まり(`checkFolderName`。ワークスペースの中で重ならない)、
   パスは絶対パスでフォルダがある(今の `checkFolders` と同じ)、説明は 100 文字まで(`folderDescriptionMax`)
10. **前の形 `folders` も読む**。`folders` だけが書いてあれば、1つの資料のフォルダを「同じ名前のワークスペース・フォルダ1つ(名前は資料のフォルダの名前・メイン・書ける)」として読む(今と同じ動き。0024 の決定事項 5 で書けるため)。
    起動のログ(Notice)で「server.json の folders を、サーバーのワークスペースとして読みました。管理の画面で保存すると workspaces の形で書き直します」と知らせる。
    **管理の画面で最初に保存したときに `workspaces` を書き、`folders` の鍵を消す**(`SaveServerFile`。ほかの鍵はそのまま。`.bak` は今と同じく残る)。起動のときには書き換えない(手で書いたファイルを起動だけで変えない)。
    `folders` と `workspaces` の両方が書いてあれば起動のエラーにする(どちらが正しいか分からないため。直し方を文に書く)
11. **配布プロファイルの決まりは `ProfileRules.Workspace`(名前。json は `workspace`)にする**。名前で引くのは今の `Folder` と同じ(ワークスペースの名前は変えられない。0061 と同じ)。
    server.db の配布プロファイルの決まりは、マイグレーションで `$.folder` を `$.workspace` に移す(名前は決定事項 10 で同じになる)。`ProfilesUsingFolder` は `ProfilesUsingWorkspace` に。

3. **フォルダが1つのときの環境の説明の名前は、ワークスペースの名前ではなくフォルダの名前**(`Working directory: "規程" (a shared folder on the server)`)。
   ファイルのツールがパスの先頭に付けた名前を見分けるのはフォルダの名前なので、モデルに見せる名前をそろえた。前の形から移したものは、フォルダの名前 = 資料のフォルダの名前なので今と同じ
4. **前の形から移すとき、資料のフォルダの名前がモデルの呼ぶ名前に使えない形(/・\・: を含む)なら、フォルダの名前だけはフォルダ名にする**(ワークスペースの名前はそのまま。配布プロファイルが名前で選ぶため)
5. **ワークスペースの名前の重なりは、大文字と小文字だけの違いも重なりとみなす**(フォルダの名前と同じ)
6. **ブラウザの会話では Git のツール(`git_status`・`git_diff`)も出さない**(`ui.noCommand` と `BuiltinTools`・`ToolStates`。`browserHides`)。
   今まではフォルダがリポジトリなら出ていた(0041 で足したとき、ブラウザで外していなかった)。決定事項 5 のとおりにした
7. **書いたときのログ(決定事項 23)は「サーバーのワークスペース 社内規程 のフォルダ 規程 に書きました: write_file a.md(bob の会話 …)」**。ワークスペースは、書くたびに会話を引いて決める(書くことはまれなので)
8. 画面に返すワークスペースの一覧は `ServerWorkspaces`(以前の `Folders` の置き換え)。入力欄の上の吹き出しもこれで引く。管理の画面の一覧は server.json の並び(名前の順に並べ替えない)
