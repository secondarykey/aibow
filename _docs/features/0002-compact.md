## 目的

今は会話が長くなっても対策がなく、全部の発言を毎回モデルに渡している。作業領域(コンテキスト)を超えるとエラーになるか、生成が途中で止まる。
会話が長くなったら、モデルに渡す履歴を上限に収める仕組み(compact)を作る。方式は2つ作って比べる。

- **捨てる**:古い発言から順に、モデルに渡すのをやめる
- **要約**:古い部分をモデル自身に要約させ、「要約 + 最近の発言」を渡す

学ぶこと:

- 「記憶」はアプリが管理していて、長い会話では何かを諦めないと収まらないこと
- 2つの方式の違い(捨てると内容が完全に消える / 要約は内容が残るが、待ち時間がかかり、要約の質に左右される)
- 要約を作ること自体にも、トークンと時間を使うこと

## 決定事項

### 上限の持ち方を「会話の上限 + 返事の上限」に変える

今はアプリ全体の設定が「コンテキスト長」(`n_ctx`、既定 16384)で、返事の上限(`max_tokens`)は会話ごとの設定になっている。
ユーザーが気にするのは「会話をどれだけ続けられるか」なので、それを直接設定させ、作業領域の大きさは aibow が計算する。

```
会話の上限(設定する)    8192   ← compact の基準。メーターもこの値に対して出す
+ 返事の上限(設定する)  8192
= 作業領域(内部で確保) 16384   ← エンジンの SetContextSize に渡す値
```

- **会話の上限と返事の上限は、どちらもアプリ全体の設定にする**(返事の上限を会話ごとの設定から移す)。作業領域の大きさが常に一定になり、VRAM の使用量も読みやすい
- どちらかを変えたら、作業領域を `会話の上限 + 返事の上限` で作り直す(今の `SetContextSize` を使う。モデルは読み直さない)
- 画面の設定には、計算した作業領域の大きさ(トークン数)も表示する
- 環境変数:`AIBOW_CTX` をやめ、会話の上限用の `AIBOW_HISTORY_TOKENS`(既定 8192)を足す。`AIBOW_MAX_TOKENS`(既定 8192)はアプリ全体の返事の上限の初期値にする。
  `AIBOW_CTX` が設定されていたら、使われなくなったことをログと画面のお知らせで伝える
- すでに保存されている値の引き継ぎ:保存済みの `n_ctx` があれば、`会話の上限 = n_ctx − 返事の上限`(最低 2048)とする。
  返事の上限の初期値は、保存済みの「新しい会話の既定の設定」の `max_tokens`。会話ごとの `max_tokens` は以後使わない(JSON に残っていても無視してよい)

#### プロファイルに向けて

TODO.md にある「プロファイル」(モデル・上限・性格などに名前を付けて切り替える)を、あとで足す予定。
会話の上限・返事の上限は、モデル・GPU の層数と同じ「作業領域に関わる設定」として、1つの塊(構造体)にまとめておく。プロファイルを作るときに、この塊をそのまま中に移せるように。
今のアプリ全体の設定は「名前のない既定のプロファイル」という位置づけ。

### 方式の選び方

- 会話ごとの設定に `compact`(`none` / `truncate` / `summary`)を足す。画面の会話の設定で切り替えられる。同じ会話で切り替えて比べられるように
- 新しい会話の既定は `summary`
- `none` のときに会話の上限を超えたら、生成する前に「会話の上限を超えました。compact を有効にするか、会話の上限を増やしてください」と伝えて止める

### 数え方

- エンジンに「文字列のトークン数を数える」機能を足す(`Generator` interface にも)。モデルが読み込まれていないと数えられない
- 判断に使うのは、実際にモデルに渡す文字列(チャットテンプレートを当てたもの。要約を入れる場合は要約込み)のトークン数。それが会話の上限以下なら収まっている
- **トークン数を保存して判断に使わない**。モデルが変わると同じ文章でもトークン数が変わる(プロファイルでモデルが切り替わることもある)。毎回、今のモデルで数え直す

### 捨てる(`truncate`)

- モデルに渡す直前に、古い発言から順に外して、会話の上限に収める。DB の発言は消さない
- 外すのは「ユーザーの発言とその返事」の組ごと。モデルに渡す履歴が、返事から始まらないようにする
- 最新のユーザーの発言は必ず残す。それだけで上限を超えるなら、エラーで伝える
- 保存しない。毎回その時点の上限とモデルで計算し直す(上限やモデルが変わっても自動で合う)

### 要約(`summary`)

- **いつ**:
  - 自動:送信のとき、モデルに渡す文字列が会話の上限を超えるなら、返事を生成する前に要約する
  - 手動:画面の「今すぐ要約」ボタン。上限を超えていなくても実行できる(Claude Code の `/compact` と同じ)。要約できる古い発言が無ければ、そう伝える
- **何を要約するか**:最近の発言は、会話の上限のおよそ半分までそのまま残す。それより古く、まだ要約に入っていない発言を「前回の要約」と一緒に要約し直す(要約を積み重ねる)
- **作り方**:同じモデル・同じ作業領域で、本番の返事の前に生成する。思考はオフ、temperature は低め(0.3 程度)、上限は 1024 トークン程度。
  要約の指示は日本語で、「人名・決めたこと・ユーザーの好みや前提・未解決の問いを残す」「指定の文字数以内」などを含める。指示の文面は Code が案を作り、ユーザーが確認する
- **モデルへの渡し方**:システムプロンプトの後ろに「これまでの会話の要約」として付ける(システムプロンプトが空でも、要約があれば system を作る)。その後ろに、要約に入っていない発言を並べる
- **失敗したとき**:要約が作れなかった(答えが出ずに終わった、停止された、エラー)ときは、要約を保存せず、その回だけ `truncate` と同じ方法で収めて返事を生成する。画面に理由を出す
- 要約を作っている間は、画面で分かるようにする(要約の文が流れてくる様子が見えるとよい)。停止ボタンで止められる

### 保存

- マイグレーションで `compactions` 表を足す

```
compactions
  id               TEXT PRIMARY KEY   -- UUIDv7
  conversation_id  TEXT REFERENCES conversations(id) ON DELETE CASCADE
  upto_message_id  TEXT               -- この発言(を含む)までを要約した
  summary          TEXT               -- 要約の文。前回までの要約も含んだ、積み重ねた結果
  model            TEXT               -- 要約を作ったモデル
  stats            TEXT               -- 要約前後のトークン数・かかった秒数など(JSON。記録用で、判断には使わない)
  created_at       TEXT
```

- モデルに渡すときに使うのは、その会話の最新の要約だけ。古い要約も消さずに残す(画面の区切りに使う)
- 保存するのは「どの発言までか」と「要約の文」だけ。会話の上限に依存する値は保存しない

### 画面

- **メーター**:今の会話がモデルに渡す文字列で、会話の上限を何トークン使っているか(例 `5,210 / 8,192`)。会話を開いたときと送信のあとに更新する
- **区切り**:要約した位置に「― ここまでを要約しました ―」を出し、開くと要約の文を読める
- **薄い表示**:モデルに渡していない発言(要約に入った発言、`truncate` で外れた発言)は薄く表示する
- **今すぐ要約**ボタン(`summary` のとき)
- 「モデルに渡した文字列」の表示に、要約が入った形が出る(学習用。今の表示のままでよい)
- ログに、compact したこと(方式、前後のトークン数、かかった秒数)を出す

### 要約の指示の文面

system:

```
あなたは会話の要約係です。「前回までの要約」と「その続きの会話」を、1つの要約にまとめ直してください。
この要約は、このあと会話を続けるときに、これまでの会話の代わりとしてアシスタントに渡されます。

必ず残すこと:
- 出てきた人名・物の名前・数値
- 決まったこと・合意したこと
- ユーザーの好みや前提・条件(「〜は使わない」「〜で答えてほしい」など)

書き方:
- 日本語の箇条書きで、800字以内
- 挨拶や言い回しは省き、事実だけを書く
- 会話に無いことを付け足さない
- 要約だけを出力する(「以下が要約です」などの前置きは書かない)
```

user:

```
## 前回までの要約
(なし)

## その続きの会話
ユーザー: …
アシスタント: …
```

モデルに渡すときは、system の後ろに `# これまでの会話の要約(古い部分は省略されています)` の見出しと要約を付ける。

### そのほか

- `compact` が空の会話(この機能より前に作った会話・保存済みの「新しい会話の既定」)は `summary` として扱う
- 「今すぐ要約」で要約する範囲は、自動と同じ規則(最近の発言を会話の上限の半分まで残す)。会話が短くて要約できる古い発言が無ければ、そう伝える
- 要約中の停止ボタンは要約だけを止め、その回は `truncate` で返事を生成する(仕様の「失敗したとき」のとおり)。
  Wails の `cancel()` は送信全体を止めるので、要約専用の `ChatService.StopSummary()` を用意する。返事の生成中の停止ボタンは今までどおり送信全体を止める
- 要約が上限トークン数で途中で切れた回も失敗として扱う(切れた要約は保存しない)
- 要約したい部分が作業領域に入りきらないときは、古い方から何回かに分けて要約を積み重ねる
- 会話の上限・返事の上限・モデル・GPU の層数は `WorkspaceSettings` にまとめる(プロファイルに移す塊)
- `n_ctx` から引き継いだ値は、起動時にその場で `history_tokens` / `reply_tokens` として保存する
  (保存しないと、あとで返事の上限だけ変えたときに n_ctx から計算し直されてずれるため)

### 実装中に決めたこと(Code の判断。変えたければ相談)

- `none` で上限を超えるとき・最新の発言だけで上限を超えるときは、ユーザーの発言を**保存せずに**止める(返事の無い質問を残さないため)
- 要約を作るときの presence penalty は 0(箇条書きの「- 」や人名を繰り返し書けるように)
- 要約を作るときにモデルに渡した文字列は、設定パネルの「モデルに渡した文字列」には出さない(そこは返事のときの文字列のまま)
- `truncate` / `summary` の会話を開いたときのメーターは「次の送信でモデルに渡す内容」(truncate は外したあと、summary は最新の要約 + 要約に入っていない発言)。
  summary で上限を超えていれば赤くなり、次の送信で要約が動く
- 保存したユーザーの発言は `user` イベントで画面に送り、画面は ID を付けておく(送信したばかりの発言も、外れたら薄く表示するため)
- 確認中に、UTF-8 として正しくない文字列を llama.cpp のトークン化に渡すとプロセスごと落ちることが分かったので、U+FFFD に置き換えるようにした
