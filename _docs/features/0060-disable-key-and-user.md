# 0060: API キーを消す・期限を付ける、利用者を無効にする

- 状態: ✅ 完了(2026-11-24。管理の画面を実際のブラウザで操作する確認も 2026-11-24 に済んだ)
- ロードマップ: ロードマップの外(aibow-server と組織で使う。0017 の 10-1・10-2 の続き)
- 決めた日: 2026-11-23(Chat でユーザーと決めた。Chat がコード(`auth/keys.go`・`auth/auth.go`・`auth/sessions.go`・`auth/tokens.go`・`auth/links.go`・`store/users.go`・`store/migrate.go`・`_cmd/aibow-server/users.go`・`admin.go`)を読んで、今の作りを確かめた)
- 前提: 0017(利用者・ログイン・API キー)、0018(管理者)、0019(アプリ用のトークン)、0022(パスワードを決めるリンク)、0031(利用者の管理の画面)

## 目的

管理者が、利用者の API キーを**消す**(作り直さずに止める)・**期限を付ける**ことと、利用者を**消さずに止める(無効にする)**ことをできるようにする。

学ぶこと:

- **「消す」と「止める」を分ける**:利用者を消すと会話・プロファイルも消える。止めるだけなら、印を1つ足して、入口(認証)で断ればよい。データには触らないので、戻すのも印を外すだけ
- **認証の入口を数える**:aibow-server に「誰か」を伝える道は、パスワードのログイン・セッション(cookie)・アプリ用のトークン・API キー・パスワードを決めるリンクの5つ。止めるときは全部で断る必要がある(1つでも漏れると止まらない。今の「パスワードの再設定」は API キーを止めていない)
- **期限の持ち方**:セッション(最後に使ってから 30 日・延びる)・アプリ用のトークン(10 日で固定)と同じく、期限は「いつまで」の時刻で保存し、使うときに今と比べる

## 今の作り(2026-11-23、Chat がコードを読んで確かめた)

- API キーは1人1本。`api_keys` 表(版 8)に `user_id`(主キー)・`id`(キーの SHA-256)・`created_at` だけを持つ。**期限の列は無い**
- `Keys.User`(keys.go)は、頭が `aibow_` なら `UserByAPIKey` で持ち主を引くだけ。期限も利用者の状態も見ない
- キーを止める方法は「作り直す」(`renewKey`。コマンド `user key`・管理の画面 `POST /_aibow/admin/users/{name}/key`)だけ。**消すだけの操作は無い**
- `users` 表に**無効の印は無い**。止めたいときは、消す(`DeleteUser`。会話なども消える)か、パスワードの再設定(`user passwd`。`DeleteUserSessions` でセッションとアプリ用のトークンを消す)しかない。
  **再設定しても API キーは使えたまま**
- 期限の考え方はもうある:セッション(`Sessions.User`。切れたら ErrNoSession)、アプリ用のトークン(`appTokenUser`。切れたら ErrTokenExpired で、401 の code は `token_expired`)
- 管理の画面の一覧(`adminUser`)は、API キーがあるか(`key`)だけを返す。画面には「API キーあり」の絞り込みがある(AdminView.tsx)

## 決定事項

### ユーザーと決めたこと

1. **API キーを消せるようにする**(作り直さずに止める)。管理の画面とコマンドの両方から
2. **API キーに期限を付ける**。作るときに **30 日・90 日・1 年・無期限** から選ぶ。**既定は 90 日**(Cline などに貼ったまま忘れて使い続けるのを防ぐため。2026-11-23 にユーザーが選んだ)
3. 期限が切れた API キーは、違うキーとは分けて断る(アプリ用のトークンの `token_expired` と同じ考え方。code は `key_expired`)
4. **利用者を無効にできるようにする**。無効の間は、ログイン・セッション・アプリ用のトークン・API キーをすべて断る。**会話・プロファイル・API キーは残す**ので、有効に戻せば元どおり
5. 無効の利用者がログインしようとしたとき、**パスワードが合っていたときだけ**「この利用者は無効にされています」と出す。間違っていれば今までどおり「名前かパスワードが違います」(どの名前がいるかを探られないように。2026-11-23 にユーザーが選んだ)

### 話の流れから Chat が決めて書いたこと(2026-11-24、ユーザーに確認して、このまま進めることにした)

**API キーの期限と消す**

6. `api_keys` に `expires_at TEXT NOT NULL DEFAULT ''` を足す(版 23)。**空は無期限**。今あるキーは空のまま(無期限)になる
7. `auth.Store` の `SetAPIKey` に期限(`expires time.Time`。ゼロ値なら無期限)を足す。キーを消す `DeleteAPIKey(ctx, user) error` を足す(無ければ ErrUserNotFound ではなく、消すものが無いことを返す。画面は「API キーはありません」と出す)
8. `UserByAPIKey` は、持ち主と一緒にキーの期限も返す(形は Code に任せる。例:`APIKeyOwner(ctx, id) (User, time.Time, error)`)。`HasAPIKey` は、あるかと期限を返す形に変えてよい(一覧に期限を出すため)
9. `Keys.User` で、期限が過ぎていれば新しいエラー `ErrKeyExpired` を返す(キーは**消さない**。管理の画面で「期限切れ」と見えるように残し、作り直すか消すのは管理者が決める)。
   文は「API キーの期限が切れました。管理者に作り直してもらってください」。`RequireKey` は 401・code `key_expired` で返し、ログには `ErrTokenExpired` と同じ形で警告を書く
10. コマンド:
    - `aibow-server user key <名前> [日数]` … 日数は `30`・`90`・`365`・`0`(無期限)。省けば 90。それ以外の数は断る(選べるのは画面と同じ4つ)。表示に期限(「期限: 2027-02-21 まで」/「期限: 無期限」)を足す
    - `aibow-server user unkey <名前>` … API キーを消す
11. 管理の画面の口:
    - `POST /_aibow/admin/users/{name}/key` に JSON `{"days": 30|90|365|0}` を受ける(本文が無ければ 90)。返事に `expiresAt`(無期限なら省く)を足す
    - `DELETE /_aibow/admin/users/{name}/key` … API キーを消す
12. 管理の画面:
    - `adminUser` に `key_expires_at`(無期限か、キーが無ければ省く)を足す
    - 詳細の API キーの欄に、期限(「2027-02-21 まで」「無期限」「期限切れ」)と「消す」のボタンを足す。消すのは確認を挟む
    - 作る・作り直すときに期限を選ぶ(30 日・90 日・1 年・無期限。最初は 90 日)。選び方の見た目は未決事項 1
    - 絞り込み「API キーあり」は、期限切れのキーも含めたままにする(行に「期限切れ」と出す)
13. ログ:キーを作ったとき(期限も書く)・消したとき・期限切れで断ったときに書く(今の `renewKey` の Noticef と同じ形。キーそのものは書かない)

**利用者を無効にする**

14. `users` に `disabled INTEGER NOT NULL DEFAULT 0` を足す(版 23 に同居)。`auth.User` に `Disabled bool` を足し、`userColumns`・`scanUser` で読む
15. `auth.Store` に `SetDisabled(ctx, id, disabled bool, at time.Time) error` を足す(`SetAdmin` と同じ形)
16. 断る場所(認証の入口、全部):
    - `Sessions.check`(ブラウザのログインとアプリのログインで共通):パスワードが合ったあとで、無効なら `ErrUserDisabled`(決定事項 5)
    - `Sessions.User`(セッション):無効なら `ErrNoSession` と同じ扱いでセッションを消す
    - `Keys.appTokenUser`(アプリ用のトークン):無効なら `ErrUserDisabled`
    - `Keys.User`(API キー):無効なら `ErrUserDisabled`
    - `Sessions.LinkUser`・`UseLink`(パスワードを決めるリンク):無効なら `ErrUserDisabled`(リンクからパスワードを決めるとそのままログインになるため)
17. `ErrUserDisabled` の文は「この利用者は無効にされています。管理者に問い合わせてください」。HTTP では、ログインの口は今の ErrLogin と同じ status、Bearer の口(`RequireKey`)は 401・code `user_disabled`。
    アプリは `token_expired` と同じように画面に出せればよい(アプリの側で特別な扱いは足さない。文をそのまま出す)
18. 無効にしたときは、その人のセッションとアプリ用のトークンを消す(`DeleteUserSessions`)。パスワードを決めるリンクも消す。**API キーは消さない**(有効に戻せば同じキーがまた使える。決定事項 4)
19. **自分自身と `local`(ログインなしの形の利用者)は無効にできない**。管理者を無効にするのは許す(管理者が一人もいなくなっても止めない、0018 の決定事項 16 と同じ考え)
20. 無効の利用者の会話・プロファイル・共有はそのまま。配ったプロファイル・共有した会話も、ほかの人からは今までどおり見える。共有の相手の候補にも今までどおり出す
21. コマンド:`aibow-server user disable <名前>`・`aibow-server user enable <名前>`。`user list` に「無効」を出す
22. 管理の画面の口:`POST /_aibow/admin/users/{name}/disabled` に JSON `{"disabled": true|false}`。`adminUser` に `disabled` を足す
23. 管理の画面:詳細に「無効にする」/「有効に戻す」のボタン(無効にするのは確認を挟む。確認の文に「ログイン中の画面とアプリは切れます。会話と API キーは残ります」)。
    一覧の状態の列に「無効」を出し、絞り込みに「無効」を足す。並べ替えの「状態」は無効を最後にする
24. ログ:無効にした・有効に戻した(誰が)と、無効の利用者を断ったとき(警告)を書く

## やらないこと

- 利用者そのものに期限を付ける(○月○日で自動で無効にする)。必要になったら backlog に書く
- API キーを1人に複数本持たせる・キーに名前を付ける
- 期限が近いキーを本人や管理者に知らせる(メールなど)
- 期限切れのキーを自動で消す
- 本人が自分の API キーを作る・消す(今どおり管理者とコマンドだけ)

## 作ったときに決めたこと(2026-11-24、Code)

- store と auth の形:`SetAPIKey(ctx, user, id, at, expires)`・`DeleteAPIKey`(無ければ `auth.ErrNoAPIKey`)・`APIKeyOwner(ctx, id) (User, time.Time, error)`(`UserByAPIKey` を置き換えた)・
  `HasAPIKey(ctx, user) (bool, time.Time, error)`。選べる日数は `auth.KeyTTLs`、期限の計算は `auth.KeyExpires`(コマンド・管理の API・画面で同じ4つ)
- 無効にしたときにセッション・アプリ用のトークン・リンクを消すのは、`store.SetDisabled` の中で印と同じトランザクションにした(決定事項 18。消し損ねて入れる時間を作らないため)。
  それでも入口(決定事項 16)では印を見て断る(消し損ねたときの備え。テストは印だけ付いた保存先で確かめる)
- `Keys.User` は、無効と期限切れが重なったときは無効のほうを返す(作り直してもらっても使えないため)。`ErrUserDisabled` のときは、ログに名前を書けるよう持ち主も返す
- ブラウザのログインで無効の人を断ったときは、パスワードは合っていたので、続けて間違えた回数(5 回で 15 分止める)には数えない
- 無効の人の詳細には、パスワードの欄(再設定のリンク)を出さない(リンクは断られるため)。自分には「状態」の欄を出さない(決定事項 19)
- 画面の言葉は決定事項 23 のまま「無効にする」/「有効に戻す」にし、`_docs/ui.md` の言葉の表に足した
  (0050 の「ボタンの文字は名詞」に合わせるなら「無効化」/「有効化」。元に戻せることが言葉で分かるよう、決定事項のままにした)
- 管理の API の `POST …/key` は、本文が無ければ 90 日(以前の呼び方のまま使えるように)
- デスクトップのアプリは、無効にされてトークンが消えると、今までの 401 と同じくログインの画面に戻る(「ログインの期限が切れました」の1行)。ログインすると「この利用者は無効にされています」が出る(決定事項 17 のとおり、アプリの側で特別な扱いは足していない)

## 完了の条件

1. 管理の画面とコマンドで、API キーを期限付き(30 日・90 日・1 年・無期限。既定 90 日)で作れ、詳細と `user list` で期限が見える
2. 期限の過ぎたキーで呼ぶと、401・code `key_expired` で断られる。違うキーは今までどおり `invalid_api_key`
3. API キーを消すと、そのキーはすぐ 401 になる。今あるキー(期限の列が空)は無期限として使える
4. 利用者を無効にすると、ブラウザ・アプリはすぐ切れ、ログイン・アプリのログイン・API キー・パスワードを決めるリンクがすべて断られる。パスワードが合ったときだけ「無効にされています」と出る
5. 有効に戻すと、前と同じ API キーと、会話・プロファイルがそのまま使える
6. 自分自身と local は無効にできない
7. テスト:auth(期限切れのキー・無効の利用者を5つの入口で断る・パスワードが違うときは ErrLogin のまま)と store(版 23 の移行・SetDisabled・DeleteAPIKey)
