# 0015: 画面のアプリの生成を aibow-server 越しにする(aibow-api を aibow-server に)

- 状態: 🔧 作業中
- ロードマップ: ロードマップ2 ステップ 8(クライアント/サーバー構成の A)。TODO の「ロードマップの外」の「モデルを扱う画面」も、この仕様の最後の段(8-4)に入れる
- 決めた日: 2026-10-21(Chat でユーザーと決めた)
- 前提: 0012(OpenAI 互換 API・`aibow-server`)、0014(会話ごとのモデル・モデルごとの GPU の層数)、0009(会話ごとの作業領域・`TryLimits`)、0013(クライアント/サーバー構成の検討メモ)

## 目的

画面のアプリが、生成を手元の `engine` ではなく、HTTP で `aibow-server` に頼めるようにする。
会話の仕組みから見ると、生成の口 `Generator`(interface)の相手が、手元かネットワークの先かが変わるだけにする。

```
使わないとき(今と同じ。既定)
  aibow.exe [ 画面 → 会話の仕組み → engine → llama.cpp → GPU ]
  ※ HTTP は一切出てこない。ポートも開かない

使うとき(AIBOW_SERVER_URL を書いたとき)
  aibow.exe [ 画面 → 会話の仕組み → Generator の HTTP 版 ] ──HTTP──→ aibow-server.exe [ engine → llama.cpp → GPU ]
              (つなぎに行くだけ。待ち受けない)                         (127.0.0.1:8089 で待ち受ける)
```

学ぶこと:

- **標準の API に無いものを、どこにどう足すか**:OpenAI 互換の API はステートレスで、生成に要るものしか決まっていない。
  aibow の画面が使っているもの(トークン数・モデルに渡した文字列・生成の時間・崩れたツール呼び出し・モデルの切り替え)を、標準の形を壊さずに足す線を引く
- **ネットワークを越えても KV キャッシュの使い回しは変わらない**こと:サーバーは前回のトークン列を覚えていて、今と同じ書式で同じ文字列になれば使い回せる。
  そのためには、会話 → JSON → 会話 の往復で1文字も変わらないこと(0012 の 6-2 で引数について確かめたこと)が要る
- **作業領域を誰が決めるか**:手元では会話ごとに作り直していた(0009)が、サーバーを共有すると「1人の都合で作り直すと、ほかの人の KV キャッシュが消える」。サーバーが決めた大きさの中で使う形に変わる
- 直接とHTTP越しで、同じ会話の待ち時間・使い回しを比べる

## 決定事項(ユーザーと決めたこと。2026-10-21)

1. **直接動かす形を残し、環境変数 `AIBOW_SERVER_URL` で切り替える**
   - 空(既定)なら今のまま:アプリの中で llama.cpp を動かす。**HTTP のサーバーもクライアントも出てこない**
   - 書けば HTTP 越し:アプリは llama.cpp を読み込まず、GPU も使わない。生成・モデルの一覧と切り替え・GPU の層数をサーバーに頼む
   - **どちらの形でも、画面のアプリは HTTP のサーバーを立てない**(つなぎに行くだけ。待ち受けるのは別の exe の `aibow-server`)。AGENTS.md の方針のまま。ブラウザに出すためにアプリがサーバーを立てるかは、ステップ9の仕様で決める
   - 変わらないもの:会話の仕組み(エージェントループ・compact・ツール・MCP・実行前の確認)と会話の保存(SQLite)はアプリの中のまま。保存をサーバーに置くのはステップ10
2. **会話ごとのモデル(0014 の 3)は、aibow-server がリクエストの `model` を見て、違えば読み直す**
   - 0012 の決定「`model` は見ない」を変える。`/v1/models` は、サーバーで使えるモデルの一覧を全部返す
   - 知らない名前のときは今のまま(読み込み中のモデルを使い、Info のログを出す)。Cline などがおかしな名前を送ってきても動くように
   - 読み直しは順番待ちの席の中で行う(生成と取り合わない)
3. **作業領域の大きさは、サーバーが起動のときに決めた大きさで固定**(今の `-ctx` / `AIBOW_SERVER_CTX`。既定 32768)
   - クライアントは作り直しを頼めない。HTTP 版の `EnsureContextSize` は「会話の上限 + 返事の上限 ≤ サーバーの作業領域」を確かめるだけで、入らなければ理由と対処(会話の上限を下げる / aibow-server の `-ctx` を上げる)を書いたエラーにする
   - 0009 の会話ごとの上限は「上限の確認」になる。`TryLimits` の VRAM の確認は、サーバーの起動(と読み直し)のときに移る
4. **「モデルを扱う画面」はステップ8の最後の段(8-4)にする**(仕様はこのファイル1つ)
   - 8-0〜8-3 でモデルの一覧・切り替え・層の数をサーバーに置く土台を作り、その上に画面を作る(先に作ると作り直しになるため。2026-10-20 に決めたこと)

### 名前と設定ファイル(2026-10-21 に追加で決めた)

18. **`aibow-api` を `aibow-server` に名前を変える**(8-0 の最初に、動きは変えずに名前だけ変える)
    - ステップ8でモデルの一覧・切り替え・層の数を持ち、ステップ10では保存やログインも持つ見込みなので、「OpenAI 互換 API の exe」より「aibow のサーバー」が役に合う
    - 変えるもの:exe とフォルダ(`_cmd/aibow-server`)・ログ(`aibow-server_<日付>.log`)・環境変数(`AIBOW_API_PORT` → `AIBOW_SERVER_PORT`、`AIBOW_API_CTX` → `AIBOW_SERVER_CTX`)・ドキュメント・deploy の `BUILD_INFO_FILES`
    - 古い環境変数を見つけたら、使われなくなったと注意を出す(アプリが `AIBOW_CTX` をやめたときと同じやり方)
    - **パッケージの `api/` はそのまま**。exe の aibow-server が `api`(OpenAI 互換の層)を載せる形(aibow-mcp と `mcp/server` の関係と同じ)。Cline の設定は URL だけなので変わらない
    - 0012 は経緯の記録なので書き換えず、「aibow-server に名前を変えた(0015)」と書き足すだけにする
19. **aibow-server の設定ファイルを、ステップ8の中(8-0)で入れる**
    - 8 で層の数を覚えるファイルを作り、8-4 で画面から置き場所を足し、ステップ10で待ち受けのアドレスやログインの設定が増えるため。後から入れると、ファイルが2つになるか作り直しになる
    - **手で書く設定と、画面が書く値を分ける**(アプリの `settings.json` と `tools.json` と同じ分け方)。手で書く設定:ポート・作業領域・最初のモデル・llama.cpp とモデルの場所。画面が書く値:モデルごとの GPU の層数(下の 9)・8-4 で足す置き場所
    - **強さの順は「引数 > 設定ファイル > 環境変数 > 既定」**(アプリの「環境変数は初期値で、決めて保存した値が優先」と同じ考え方)
    - 置き場所の既定は `%APPDATA%\aibow\`、引数の `-config` で変えられる。アプリのファイルと重ならない名前にする(名前と書き方は Code が決める)
    - **Code が決めた(2026-10-21、8-0)**:手で書くほうは `server.json`(欄は `port`・`ctx`・`model`・`lib`・`modelsDir`。知らない欄は書き間違いとしてエラー)、
      aibow-server が書くほうは `server-models.json`。`-config` は手で書くファイルのパスを指し、書くほうのファイルはその隣に置く。
      引数に `-lib`・`-models` も足した(llama.cpp とモデルの場所も「引数 > 設定ファイル > 環境変数 > 既定」にそろえるため)
20. **アプリのつなぎ先は、アプリの `settings.json` に書ける**ようにし、環境変数 `AIBOW_SERVER_URL` も使える(settings.json が優先)。
    settings.json は「その PC でどう起動するか」を手で書く場所(AGENTS.md)で、つなぎ先はそれにあたる。上の 1 の「`AIBOW_SERVER_URL` が空なら」は「settings.json にも環境変数にも書いていなければ」と読む

## 決定事項(話の流れから Chat が決めて書いたこと。ユーザーに確かめてもらう)

### 線の引き方

- **環境の説明(システムプロンプトの「Environment」。OS と `run_command` のシェル)は、ツールを動かす側が書く**(2026-10-21、ユーザーと決めた)。
  8 では手元の会話の仕組みが書くので今のまま。サーバーがシステムプロンプトを付け足すようになったとき(ステップ10)に、サーバーの OS を書かないようにする。
  コマンドが無いときの扱い(今は、シェルの「見つからない」の出力と終了コードをそのまま結果としてモデルに返す)は変えない。良くする案は TODO の「コーディングエージェントとして洗練する」

5. **書式(チャットテンプレート)はサーバーで当てる**(今の `aibow-server` のまま)。書式はモデルに付いていくものなので、モデルを持つ側で当てる。
   TODO の「ほかのモデルの書式」もサーバーの側だけで済み、ステップ10の決まり(システムプロンプトの付け足しなど)もサーバーで守らせられる
6. **標準の形は変えず、aibow 専用の欄と口を足す**
   - Cline などから見た `/v1/models`・`/v1/chat/completions` の形は今のまま(Cline から今までどおりつながること)
   - 専用の欄は、aibow のクライアントが頼んだときだけ返す(モデルに渡した文字列は長いので、毎回は返さない)
   - 専用の口は `/v1/` とは分けたパスに置く(標準の口と見分けられるように)。名前は Code が決める
7. **足すもの**(画面のアプリが `Generator` と `ChatService` で使っているのに、今の aibow-server が出していないもの):
   - **トークン数を数える口**(`CountTokens`。メーターと compact の判断に使う。OpenAI の決まりに無い)。書式を当てた文字列のトークン数を返す
   - **モデルに渡した文字列**(`onPrompt`。学習用に画面に出しているもの)。生成の前に返す(ストリーミングなら最初の塊)
   - **生成の記録**(`GenerateStats`):今の `usage` のトークン数に加え、プロンプトの読み込みと生成の秒数・細かい終了の理由(`eos` / `stop` / `length` / `context` / `cancel`)
   - **崩れたツール呼び出し**(`format.ToolCall` の `Raw` / `Error`):今は答えの後ろに文字として足しているだけなので、aibow 自身のループが「エラーとしてモデルに返して直させる」をできない。
     返すときも、**履歴で送り返すときも**(次のプロンプトには `Raw` をそのまま入れるため)専用の欄で運ぶ
   - **読み込み中のモデルの情報**(`engine.ModelInfo`)・**モデルの一覧**(`models.Entry`)・**明示的に読み込む口**(送信の前の `ModelLoader.LoadModel`。読み込み中のお知らせとログのため)・**GPU の層数を変える口**
8. **会話 → JSON → 会話 の往復で1文字も変えない**(KV キャッシュを今と同じだけ使い回すため)
   - 思考(`Message.Thinking`)は `reasoning_content`、思考のオン・オフは `chat_template_kwargs.enable_thinking`(0012 で決めた形)
   - ツールの定義(`tool.Def`)を JSON Schema にするとき、引数の順番を保つ(書式はツールの説明を書いた順にプロンプトに入れるため。aibow-server は書いた順に読む)
   - ツールの引数は 6-2 の形(モデルが書いた文字のまま)で運ぶ
9. **GPU の層数は、サーバーの PC に覚える**(「その PC の人が決めること」なので)
   - aibow-server の手元のファイル(JSON)に、モデルごとに覚える。aibow-server は DB を読まない(0012 のまま)。ファイルの名前と場所は Code が決める
   - まだ覚えていないモデルは、今と同じく `AIBOW_GPU_LAYERS`(または既定)の値
   - HTTP 越しのとき、画面の「基本設定」の層の数はサーバーの口を呼ぶ。アプリの DB の `model_gpu_layers` は使わない(消さない。直接の形に戻したときに使う)
10. **HTTP 版の `Generator` は `api/client` パッケージにする**(`mcp/client` と並べる形)。`api` と同じく、ルートの `aibow`(会話の仕組み)を import しない。
    標準の `net/http` で書く(外部パッケージを足さない)。`Info()` は呼ばれる回数が多いので、最後に知った値を持っておき、読み込み・生成・一覧のたびに取り直す(細かい作りは Code が決める)
11. **画面のアプリの、エンジンを直接呼んでいるところ**(`ChatService` の `Models`・`SwitchModel`・`SetGPULayers`・`TryLimits`・`AppSettings` の層の数・起動のときのモデルの読み込み)は、
    直接と HTTP 越しの2つの実装を持つ「モデルを扱う係」にまとめ、`ChatService` はどちらかを呼ぶだけにする(8-4 の画面も、どちらの形でも同じに見せるため)
12. **HTTP 越しのとき、アプリは起動のときにモデルを読ませない**。サーバーは起動のときに `-model` のモデルを読み込んでいる。会話のモデルが違えば、送信の前に読み直す(0014 の 3 と同じ)
13. **サーバーにつながらないとき**:アプリは起動する。モデルの一覧・送信のときに、理由と対処(「aibow-server を起動してください。つなぎ先: …」)を出す。サーバーが起動したら、アプリを起動し直さずに使えるようにする
    - **黙って直接の形に切り替えない**(どちらで動いているか分からなくなるため。下の「やらないこと」)
14. 0012 の「画面のアプリと aibow-server は同時に使わない」は、「**直接の形のときは**同時に使わない(VRAM に2つ載らない)。HTTP 越しのときはアプリが GPU を使わないので同時に動かせる」に変える。
    Cline と画面のアプリを同時につないだときは、今の順番待ちのまま(KV キャッシュは取り合うので、使い回しが減る。ログで見える)
15. 8 では待ち受けは `127.0.0.1` だけのまま(同じ PC の aibow-server につなぐところまで)。`AIBOW_SERVER_URL` にほかの PC のアドレスを書けばつながる作りにはしておくが、ほかの PC から使うことは確かめない

  - **確かめた(2026-10-21、8-0。RTX 4060 8GB、ほかのアプリが VRAM を使っている状態)**:4B から 9B への読み直しは 5.8 秒で成功し、32 層全部を GPU に載せられた(VRAM の使用 7.9 / 8.2 GB)。

    層の数を減らして速くなるかは、8-3 で比べる(`POST /aibow/gpu-layers` で 9B の層の数を覚えさせられる)
