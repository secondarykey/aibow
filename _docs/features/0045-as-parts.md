## 目的

**使う相手が現れた**:ユーザーが作っている Wails 製の「構造を持つメモ帳」に、スキルを元にした AI の編集を足したい。
メモ帳のユーザーを aibow-server に依存させたくないので、メモ帳が **MCP のサーバー**になり、Claude Desktop・Claude Code・aibow のアプリなどからメモを読んで編集してもらう形が、前の相談で有力な案として出た。
ただし、AI とのやり取りを相手(クライアント)の画面で行うのか、メモ帳の中で行うのかはまだ決まっていない(2026-11-09)。
どちらになっても使える部品(ツールの形・当て方・差分)を先に整え、確認のしかたは決まってから足す。

**使う側で決まったこと(2026-11-11 に追記)**:

- AI とのやり取りは相手(クライアント)の画面で行う(メモ帳の中にチャットの画面は持たない)
- メモ帳が MCP のサーバーを作る時期は決まっていない。作業の順番の 1・2(`Replace`・`UnifiedDiff` の公開と `Custom`)は aibow だけで閉じているので、それを待たずに進めてよい
- **部品は、特定の使い手に合わせて作らない**。使う側の事情(データの持ち方・画面・保存のしかた)はここに書かず、aibow の形は「自分のツールを持つアプリなら誰でも使える」ことで決める(2026-11-11、ユーザーの指示)

そのとき、メモ帳が aibow の `tool` と `mcp/server` を import して、次をそのまま使えるようにする。

- ツールの形(`tool.Tool`・`Def`・`CheckArgs`)と、MCP のツールへの変換・時間の上限・失敗を isError で返す仕組み(`mcp/server`)
- 書き換える前の確認(差分を見せる・見せたものと同じかを確かめてから実行する)
- `edit_file` の当て方(1か所に決まらなければエラー・字下げのずれを合わせる)と差分の作り方

学ぶこと:

- **公開する名前の線を引く**:今まで aibow の中だけで使っていた関数を外に見せると、変えにくくなる。何を見せて何を隠すかを、実際の使い手(メモ帳)を見て決める
- **ライブラリの「差し込み口」**:サーバーの作り方を決め打ちにせず、ツールの一覧・名前・確認のしかたを使う側が渡せるようにする(依存の向きは変えない)

## 決定事項(案。ユーザーと決めること)

1. **`mcp/server` に、外からツールを渡す口を足す**。`Options` に次を足す
   - `Name`:サーバーの名前(MCP の serverInfo.name)。空なら今までどおり `aibow-mcp`
   - `Instructions`:クライアントに渡す説明。空なら今までどおり(フォルダの説明)
   - `Custom []tool.Tool`:決めたら、**組み込み・フォルダのツールの代わりに、これだけを出す**。組み込みも出したいときは、使う側が `append(tool.Builtin(), …)` で足す
   - 「足す」ではなく「代わりに」にするのは、メモ帳に `read_file` や `run_command` が混ざると、モデルがメモ帳の外のファイルを触ろうとするため
2. **確認のしかたは保留**(下の未決事項 1)。AI とのやり取りを相手(Claude などのクライアント)の画面で行うかどうかが、まだ決まっていないため(2026-11-09、ユーザーの指示)
   - 2026-11-11:やり取りは相手の画面で行うと決まった(上の「使う側で決まったこと」)。残るのは確認の場所だけ(未決事項 1)
3. **`edit_file` の当て方を、ファイルによらない関数として公開する**(`tool` パッケージ)
   - `tool.Replace(text, old, new string) (Replaced, error)`:`Replaced` は置き換えた後の全体・行番号・字下げを合わせたか。1か所に決まらない・見つからない・同じ、は決まったエラー(`errors.Is` で見分けられる)
   - エラーの文は「ファイル」「read_file」に触れない言い方にし、`edit_file` はそれに自分の文(パスと read_file の案内)を足して返す。モデルに見える文は今と変わらない
   - CRLF を合わせる処理も `Replace` に入れる
4. **差分を作る関数を公開する**:`tool.UnifiedDiff(name, before, after string) string`(今の `unifiedDiff`。大きすぎれば空)
5. **書き換えるかどうかの印を、確認と分ける**:今は「`Confirmable` でないツール = 読むだけ(readOnlyHint)」としている。
   メモ帳の「変更の案を溜める」ツールは、確認は要らないが読むだけでもない。そこで任意の interface `tool.Hinted`(`ReadOnly() bool` など)を足し、あればそちらを使う
   - 確認を自分の側で受け持つ使い手(未決事項 1 の (c))では、ツールが**全部** `Confirmable` でなくなる。今の `mcpTool` のままでは、書き換えるツールにも readOnlyHint が付く。(c) を許すなら、これは任意ではなく要る
6. **使い方の見本を置く**:`mcp/server` に `Example`(自分のツールを1つ持つサーバーを作って標準入出力で動かす)を足し、`_docs/mcp.md` に「ほかのアプリから使う」の節を書く
   - 画面のアプリは標準入出力を持たないので、Streamable HTTP でつなぐ使い手もいる(未決事項 2)。`_docs/mcp.md` の節には、`New` の返す `*mcp.Server` を SDK の `mcp.NewStreamableHTTPHandler` で包む形も書く

## やらないこと

- エージェントのループ(`agent.go`)・`api/client`・`engine`・`format` を部品にすること(会話・保存・aibow-server との結び付きが強い。メモ帳の側には要らない形にした)
- `tool` を別のモジュール(`tool/go.mod`)に分けること。同じモジュールのまま import してもらう(使わないパッケージ(yzma・sqlite)はビルドに入らない)
- `tool` の依存(`aibow/log`→wenteasy/log・`aibow/git`・`internal/proc`・`golang.org/x/net`)を切り離すこと。メモ帳から見ると増えるが、cgo は要らず、重くない
  - ログは `SetLogger` を呼ばなければ `slog.Default()` に出るので、使う側のログにそのまま混ざる(0008)
  - **Go の版は依存より重い**:aibow の `go.mod` は `go 1.27.0`。import したアプリの `go.mod` も 1.27 以上になる。aibow の側で下げる理由は無いので、使う側が受け入れる。`_docs/mcp.md` の「ほかのアプリから使う」に書いておく
- メモ帳の側の設計(ノードの ID・ツールの一覧・スキル・画面)。それはメモ帳のリポジトリで決める
- 版の約束(semver で公開 API を守る、など)。当面はユーザー自身のメモ帳だけが使い手なので、壊したらメモ帳を直す

## Code の見直し(2026-11-10。案。まだ決めていない)

作りのチェックのついでに、今の `mcp/server`・`tool` のコードと MCP の SDK(v1.8.0)のソースに照らして読んだ。
上の決定事項(案)は書き換えていない。ここの案を採るかは、ユーザーと決める。

### 見直したほうがよい箇所

1. **「読むだけ」の印の既定(決定事項 5)**:今は、確認の要らないツール(`Confirmable` でないもの)にはすべて readOnlyHint が付く(`mcp/server/server.go` の `mcpTool`)。
   メモ帳の「変更の案を溜める」ツールは、何も宣言しなければ「読むだけ」と名乗ってしまう。作業の順番でも `Custom`(2)が `Hinted`(3)より先。
   - 案:`Custom` で渡したツールは、`tool.Hinted` で宣言したときだけ「読むだけ」にする(既定は付けない)。組み込みは今のまま
   - 今もある例:`update_plan` は予定を書き換えるが、確認が要らないので「読むだけ」が付いている。決定事項 5 を入れるときに一緒に直せる
2. **外から渡したツールの定義を、どこで確かめるか(決定事項 1)**:SDK の `Server.AddTool` は、引数の定義(`Def.Parameters`)が空か、`type` が `object` でないと **panic する**。
   同じ名前のツールを足すと、黙って後のものに置き換わる(`featureSet.add`)。`New` はエラーを返さない形なので、メモ帳の起動が落ちる・ツールが1つ消える、が起きる。
   - 案:`Custom` を渡したときは、名前が空・重なる・定義が読めないことを先に確かめて、エラーで返す。`New` の形を変えないなら、確かめる関数(`Options.Check() error` など)を別に用意する
3. **`Custom` とほかの欄の関係(決定事項 1)**:`Custom` を渡したとき、`WorkDir`・`Folders`・`Fetch` を無視するのか、一緒に渡したらエラーにするのかを決める。
   クライアントに渡す説明(`instructions`)はフォルダから作っているので、無視するなら「`Instructions` が空なら何も出さない」まで書く
4. **使える引数の定義の範囲を、使い方の説明に書く(決定事項 6)**:引数は `tool.CheckArgs` が確かめるが、見るのは `properties` の直下の `type` と `required` だけ。
   入れ子の中身・`enum`・最小値などは確かめないので、メモ帳のツールが JSON Schema に書いても効かない。
   - 案:`_docs/mcp.md` の「ほかのアプリから使う」に、効く範囲と、それ以外はツールの `Run` で自分で確かめることを書く
5. **確認の口 (b) は、今ある型を使える(未決事項 1)**:`tool/ask.go` に、聞く関数の型 `tool.Ask`(`Preview` を渡して `Answer` を受け取る)がある。
   `Options.Confirm` をこの型にすれば、新しい型は要らない。足すのは、見せた差分と同じかを実行の直前に確かめる処理(MRTR の `requestState` と同じ役目)
6. **`Replace` のエラーから、数を取り出せるようにする(決定事項 3)**:今の `edit_file` は「N か所あります」のように、文の中に数とパスを埋めている(`tool/write.go` の `plan`)。
   `errors.Is` で見分けるだけだと、`edit_file` が今と同じ文を作れない(完了の条件 3)。何か所あったかを持つエラーの型にする(`errors.As` で取り出す)

### 確かめて、問題なかったこと

- **HTTP でつなぐ(未決事項 2)**:SDK に `mcp.NewStreamableHTTPHandler` があり、`*mcp.Server` をそのまま包める。確認(MRTR)が見るクライアントの能力は、リクエストごとの `_meta` からも読む作り
  (`ServerRequest.ClientCapabilities`)なので、ステートレスの HTTP でも動く見込み。**実際につないでは確かめていない**
- **localhost で待ち受けるときの守り**:SDK の HTTP の口は、DNS リバインディングの保護が既定で有効(`DisableLocalhostProtection` で外せる)。メモ帳の側で外さなければ足りる
- **import できるか**:ルートにタグ(v0.9.0 まで)がある。`tool` が使う `internal/proc` は、外のモジュールから間接的に使える(直接 import できないだけ)。
  メモ帳の側は Go 1.27 以上が要る(標準の `uuid` を使っているため)
- **未決事項 3(`tool/textedit` に分けるか)**:分けないほうをすすめる。メモ帳は `mcp/server` を使う時点で `tool` を import するので、分けても依存は減らない
