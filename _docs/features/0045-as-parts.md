## 目的

**使う相手が現れた**:ユーザーが作っている Wails 製の「構造を持つメモ帳」に、スキルを元にした AI の編集を足したい。
メモ帳のユーザーを aibow-server に依存させたくないので、メモ帳が **MCP のサーバー**になり、Claude Desktop・Claude Code・aibow のアプリなどからメモを読んで編集してもらう形が、前の相談で有力な案として出た。
ただし、AI とのやり取りを相手(クライアント)の画面で行うのか、メモ帳の中で行うのかはまだ決まっていない(2026-11-09)。
どちらになっても使える部品(ツールの形・当て方・差分)を先に整え、確認のしかたは決まってから足す。

そのとき、メモ帳が aibow の `tool` と `mcp/server` を import して、次をそのまま使えるようにする。

- ツールの形(`tool.Tool`・`Def`・`CheckArgs`)と、MCP のツールへの変換・時間の上限・失敗を isError で返す仕組み(`mcp/server`)
- 書き換える前の確認(差分を見せる・見せたものと同じかを確かめてから実行する)
- `edit_file` の当て方(1か所に決まらなければエラー・字下げのずれを合わせる)と差分の作り方

学ぶこと:

- **公開する名前の線を引く**:今まで aibow の中だけで使っていた関数を外に見せると、変えにくくなる。何を見せて何を隠すかを、実際の使い手(メモ帳)を見て決める
- **ライブラリの「差し込み口」**:サーバーの作り方を決め打ちにせず、ツールの一覧・名前・確認のしかたを使う側が渡せるようにする(依存の向きは変えない)

## 決定事項(案。ユーザーと決めること)

1. **`mcp/server` に、外からツールを渡す口を足す**。`Options` に次を足す
   - `Name`:サーバーの名前(MCP の serverInfo.name)。空なら今までどおり `aibow-mcp`
   - `Instructions`:クライアントに渡す説明。空なら今までどおり(フォルダの説明)
   - `Custom []tool.Tool`:決めたら、**組み込み・フォルダのツールの代わりに、これだけを出す**。組み込みも出したいときは、使う側が `append(tool.Builtin(), …)` で足す
   - 「足す」ではなく「代わりに」にするのは、メモ帳に `read_file` や `run_command` が混ざると、モデルがメモ帳の外のファイルを触ろうとするため
2. **確認のしかたは保留**(下の未決事項 1)。AI とのやり取りを相手(Claude などのクライアント)の画面で行うかどうかが、まだ決まっていないため(2026-11-09、ユーザーの指示)
3. **`edit_file` の当て方を、ファイルによらない関数として公開する**(`tool` パッケージ)
   - `tool.Replace(text, old, new string) (Replaced, error)`:`Replaced` は置き換えた後の全体・行番号・字下げを合わせたか。1か所に決まらない・見つからない・同じ、は決まったエラー(`errors.Is` で見分けられる)
   - エラーの文は「ファイル」「read_file」に触れない言い方にし、`edit_file` はそれに自分の文(パスと read_file の案内)を足して返す。モデルに見える文は今と変わらない
   - CRLF を合わせる処理も `Replace` に入れる
4. **差分を作る関数を公開する**:`tool.UnifiedDiff(name, before, after string) string`(今の `unifiedDiff`。大きすぎれば空)
5. **書き換えるかどうかの印を、確認と分ける**:今は「`Confirmable` でないツール = 読むだけ(readOnlyHint)」としている。
   メモ帳の「変更の案を溜める」ツールは、確認は要らないが読むだけでもない。そこで任意の interface `tool.Hinted`(`ReadOnly() bool` など)を足し、あればそちらを使う
6. **使い方の見本を置く**:`mcp/server` に `Example`(自分のツールを1つ持つサーバーを作って標準入出力で動かす)を足し、`_docs/mcp.md` に「ほかのアプリから使う」の節を書く

## やらないこと

- エージェントのループ(`agent.go`)・`api/client`・`engine`・`format` を部品にすること(会話・保存・aibow-server との結び付きが強い。メモ帳の側には要らない形にした)
- `tool` を別のモジュール(`tool/go.mod`)に分けること。同じモジュールのまま import してもらう(使わないパッケージ(yzma・sqlite)はビルドに入らない)
- `tool` の依存(`aibow/log`→wenteasy/log・`aibow/git`・`internal/proc`・`golang.org/x/net`)を切り離すこと。メモ帳から見ると増えるが、cgo は要らず、重くない
- メモ帳の側の設計(ノードの ID・ツールの一覧・スキル・画面)。それはメモ帳のリポジトリで決める
- 版の約束(semver で公開 API を守る、など)。当面はユーザー自身のメモ帳だけが使い手なので、壊したらメモ帳を直す

## 未決事項

1. **確認をどこでするか**(決定事項 2。**保留**:そもそも AI とのやり取りを相手の画面で行うか、メモ帳の中で行うかが決まってから決める。2026-11-09、ユーザーの指示)
   - (a) MRTR のまま(Claude などのクライアントが聞く)。クライアントが elicitation に対応していないと、書き換えるツールは断られる(0007 の決定事項 6)。Claude Desktop・Claude Code がどこまで対応しているかは **未確認**
   - (b) `Options.Confirm` を足し、メモ帳が自分の画面で聞く。どのクライアントからでも同じに動き、確認がメモ帳の中に残る
   - (c) aibow は何もしない。メモ帳のツールは「変更の案」を溜めるだけ(確認の要らないツール)にし、適用はメモ帳の画面で押す。aibow の変更は 1・3〜6 だけで済む
2. **メモ帳とクライアントのつなぎ方**:Windows の画面のアプリは標準入出力を持たない(aibow-mcp を別の exe にした理由と同じ)。
   メモ帳が Streamable HTTP で待ち受けるか、aibow-mcp のような小さな exe を別に作ってメモ帳に話しかけるかは、メモ帳の側で決める。
   `New` は `*mcp.Server` を返すので、aibow の側はどちらでも変えずに済む見込み(SDK の HTTP の口で包めるかは作るときに確かめる)
3. `Replace` を `tool` に置くか、小さな別のパッケージ(`tool/textedit` など)に分けるか。分ければ、メモ帳は差分と当て方だけを `pkg/diff` 以外の依存なしに使える
