## 目的

サーバーモードのアプリで、配布プロファイルで配られたサーバーのワークスペースのフォルダを、ファイルのツールで読み書きできるようにする。
同じ会話をアプリで開いてもブラウザで開いても**同じフォルダ**を使う形になり、0064 で「知らせるだけ」にした取り違え(サーバーのフォルダのつもりで手元のファイルを触る)が無くなる。

学ぶこと:

- **同じ部品を、つなぎ方だけ替えて使う**:アプリの組み込みのツールは、もともと aibow の中の自作の MCP サーバー(`mcp/server`)にメモリ内のつなぎ方でつないでいる(`mcp/client/local.go`。0007 の 5-4)。
  サーバーのワークスペースは、同じサーバーを aibow-server の中に立て、**つなぎ方を Streamable HTTP に替える**だけ。ツールの中・差分の確認(MRTR)・`folder` の引数・読むだけは変わらない
- **ステートレスな確認の往復**:書く前の差分はサーバーが作り、確認の答えは「同じ引数 + 答え + 合言葉」で送り直す(`mcp/server/confirm.go`)。サーバーは往復の間に何も覚えない。会話の履歴を毎回送り直すのと同じ考え方
- **信頼の境目**:アプリは、自分が立てた(aibow-server の)サーバーの差分を信頼し、呼ぶ前の確認を出さない(`tool.SelfConfirming`)。サーバーは、API キーで「誰か」を確かめ、配布プロファイルで「使ってよいか」を確かめる

## 今の作り(2026-11-26、Chat がコードを読んで確かめた)

- サーバーモードのアプリは、会話の仕組み(エージェントループ)を**アプリの中で**動かし、生成は `api/client`、保存は `store/remote` で aibow-server に頼む。ツールはアプリの中で動く
- アプリの組み込みのツールは `client.NewLocal`(`mcp/client/local.go`)が、フォルダの組ごとに `mcp/server` をメモリ内で立てて渡す。名前に前置きを付けず、グループは組み込み、書き換えるツールは `tool.SelfConfirming`(呼ぶ前に聞かず、サーバーが差分を送ってきたときに1回だけ聞く)
- `mcp/server` は `Options.Folders` でフォルダの組を受け取り、書き換えるツールの差分をサーバーで作って `_meta` の Preview で送る(MRTR)。`Options.Instructions` を決めないと、フォルダから作った説明(パスを含む)を渡す
- `mcp/client` は url の MCP サーバーに Streamable HTTP でつなぎ、ヘッダー(`headers`)を付けられる。`settings.json` のサーバーは `tool.SelfConfirming` にしない(名乗りを偽れるため)
- aibow-server のブラウザの会話は、`Conversations` の `noWorkDir` のときに `serverWorkspaceOf`(`Profile.GrantedWorkspace`)でワークスペースを引き、`toolFolders` に全部のフォルダを渡す。`run_command`・Git のツールは `ui.noCommand`(`browserHides`)で外す
- アプリは配布プロファイルの決まり(`rules.workspace`・`share`・`withdrawn`)を受け取っている(0064)が、フォルダの組(名前・印・説明)は知らない
- aibow-server の口:`/_aibow/store/` は API キーが要る形なら `keys.RequireKey` と `keyUser` で持ち主を決める。道は `routes` の前置き(`/_aibow/ui/`・`/_aibow/auth/`・`/_aibow/store/`・`/_aibow/admin/`)で分ける

## 決定事項(ユーザーと決めたこと。2026-11-26)

1. **方式は「aibow-server にサーバーのワークスペースの MCP の口を作り、アプリはその会話のときだけ組み込みとしてつなぐ」**。ファイルのツール専用の口を新しく作る案・送信ごとサーバーに任せる案は選ばなかった
2. **どのワークスペースを使うかは、今と同じく会話の配布プロファイルで決まる**(`GrantedWorkspace`。会話ごとに選ばない)。アプリの入力欄の上は、`WorkspaceBar` の代わりにブラウザと同じ `FolderBar` を出し、0064 の知らせは出さない
3. **サーバーのワークスペースの会話では、アプリの手元のワークスペースのファイルのツール・`run_command`・Git のツール・`${workdir}` を使う MCP のサーバーを出さない**(0065 の決定事項 4・5 の「混ぜない」)。
   `${workdir}` を使わない手元の MCP のサーバー(`settings.json`)は今のまま使える

## 決定事項(話の流れから Chat が決めて書いたこと。2026-11-26)

着手の前に、ユーザーにこのとおりでよいかを確かめる。

### aibow-server の口

4. **口は2つ。新しい前置き `/_aibow/workspaces` を `routes` に足す**(`-base` の下にも載る。`mount` は今のまま)
   - `GET /_aibow/workspaces`:その人に使えるサーバーのワークスペースの一覧。名前と、フォルダの名前・メイン・書ける / 読むだけ・説明だけを返す(**パスは返さない**。0065 の `ui.ServerWorkspaces` と同じ中身)
   - `/_aibow/workspaces/{name}/mcp`:そのワークスペースの MCP の口(Streamable HTTP。`mcp.NewStreamableHTTPHandler` で `mcp/server` を包む)
5. **守り**:API キーが要る形なら `keys.RequireKey` と `keyUser`(`/_aibow/store/` と同じ)。要らない形(127.0.0.1 だけでログインなし)ならログインなしの形の利用者。
   キーが無い・違うなら 401、そのワークスペースを使えないなら 403(文は「サーバーのワークスペース『名前』は使えません(配布プロファイルで配られていないか、配布をやめました)」)。知らない名前も 403(あるかどうかを漏らさない)
6. **「使える」の決め方は、その人に配られている(`Share` があり `Withdrawn` でない)配布プロファイルのどれかが、そのワークスペースを選んでいること**。
   会話ごとには確かめない(MCP のつながりはワークスペースごとに1つで、会話をまたいで使うため)。アプリは会話のプロファイルの `GrantedWorkspace` が名前と同じときだけつなぐので、決まりはブラウザと同じになる。
   判定は呼び出しのたびに行う(配布をやめたら、次のツールの実行から 403)
7. **MCP のサーバーの設定**:`Folders` はそのワークスペースのフォルダ全部(パス・メイン・書ける・説明)。`Instructions` は空でない短い文に決め、**パスを入れない**(アプリは環境の説明を自分で書く。決定事項 11)。
   `Fetch` は渡さない(fetch はアプリの手元の組み込みのものを使う)。コマンドのツールは出さない(`run_command` は `mcp/server` が `Folders` で出すなら、外す仕組みを `mcp/server` に足す。Code が今の作りを見て決める)。Git のツールも出さない
8. **管理の画面でフォルダを変えたら、次のツールの実行から新しい組になる**(ブラウザと同じ。0065)。SDK のセッションが前の組を持ち続ける作りなら、サーバーは組が変わったセッションを捨てて作り直させる(方法は Code が SDK v1.8.0 の作りを見て決め、経過に書く)。
   ワークスペースを消したら 403
9. **書いたときのログ**(0065 の決定事項 23 にそろえる):Notice に「サーバーのワークスペース 社内規程 のフォルダ 規程 に書きました: write_file a.md(bob、アプリから)」。会話は分からないので書かない(決定事項 6)。
   つないだ・切れた・断った(401・403)は Info / Warn に1行

### アプリの側

10. **つなぎ方は `client.NewLocal` と同じ扱いの「サーバーのワークスペースのツール」**(`mcp/client` に、つなぎ先が HTTP の版を足す)。名前に前置きを付けない・グループは組み込み・書き換えるツールは `tool.SelfConfirming`
    (aibow-server は利用者が `serverUrl` で選んだ自分の組織のサーバーなので信頼する。`settings.json` のサーバーとは扱いを分ける)。
    つながりはワークスペースの名前ごとに1つ、要る最初のときにつなぎ、アプリを閉じるかつなぎ先を替えるまで残す。切れたら次の送信でつなぎ直す(`remoteTool.broken` と同じ)。
    API キーは `api/client` の今のキーを毎回のリクエストで読む(ログインし直しても替わるように)
11. **モデルへの環境の説明は、ブラウザと同じ形にする**(0065 の決定事項 13 と経過 3:フォルダが1つなら `Working directory: "規程" (a shared folder on the server)`、複数なら `foldersEnvironment` の `onServer`)。
    フォルダの名前・印・説明は `GET /_aibow/workspaces` で引く(送信のたびに引く。軽いので覚えておかない)。アプリでも**サーバーのパスを見せない**
12. **会話の設定は変えない**。手元のワークスペース(`Workspace`)・worktree を会話に保存していても、その値は残し、サーバーのワークスペースが使える間は使わない(ブラウザの `IgnoreWorkDir` と同じ考え方)。
    配布をやめた・ワークスペースが消えたら、手元のワークスペースに戻すのでなく、ファイルのツールの無い会話になる(勝手に手元のフォルダを使わない)
13. **ツールの一覧(入力欄の上の「この会話のツール」・設定の画面)も、出さないものを外す**(ブラウザの `forBrowser` と同じ決まり。`run_command`・Git のツール・`${workdir}` の MCP)
14. **確認のカードはフォルダの名前を出し、パスは出さない**(サーバーの Preview のまま。0065 の決定事項 15)
15. **入力欄の上の `FolderBar` の吹き出し**(フォルダの名前と読むだけの印)も `GET /_aibow/workspaces` で引く

### 古いアプリ・古いサーバー(0054)

16. **新しいアプリ + 古い aibow-server**:`GET /_aibow/workspaces` が 404 なら、サーバーのワークスペースは使えないとみなし、今(0064)の動き(手元のワークスペースと知らせ)のままにする。
    知らせの文に「aibow-server を新しくすると、アプリからも使えます」を足す。止めはしない(0054 の決定事項 3)
17. **古いアプリ + 新しい aibow-server**:何も変わらない(古いアプリは口を呼ばず、0064 の知らせが出る)
18. **ブラウザは変えない**(ブラウザの会話は今のまま aibow-server の中でメモリ内につなぐ。新しい口はアプリ用)

## やらないこと(先回りしない)

- 会話ごとにサーバーのワークスペースを選ぶ・手元のワークスペースと混ぜる(0065 と同じ)
- アプリで、サーバーのワークスペースの `run_command`・worktree・git
- `${workdir}` を使う MCP のサーバーを、サーバーのワークスペースのメインのフォルダで動かすこと(サーバーの PC でもアプリの PC でも)
- aibow-server の MCP のサーバー(`server.json` の `mcpServers`)をアプリから使うこと(ブラウザとアプリで出るツールが少し違うのは残る)
- 新しい口を Claude Code など aibow の外のクライアントに案内すること(使えてしまうが、使い方は書かない。必要になったら別に考える)
- 会話ごとの使える / 使えないの判定(決定事項 6)
