# 0006: MCP クライアント(既製の MCP サーバーのツールを使う)

- 状態: 🔧 作業中
- ロードマップ: ステップ 4
- 決めた日: 2026-10-14(Code のセッションでユーザーと相談して決定)
- 前提: 0005(作業フォルダ・確認・`tool` パッケージ)、0004(ツール呼び出し・エージェントループ)

## 目的

aibow を MCP のクライアントにし、既製の MCP サーバー(まずは公式の filesystem サーバー)のツールを、組み込みのツールと同じようにモデルに使わせる。
自作のサーバーはステップ5(そこで aibow をつなぎ直し、ステップ3のツールを MCP 経由に置き換える)。

MCP(Model Context Protocol)は、ツールやデータを AI アプリにつなぐための決まりごと。中身は JSON-RPC 2.0 のメッセージのやり取りで、
ローカルでは「クライアントがサーバーを子プロセスとして起動し、標準入出力で1行ずつ JSON を送り合う」(stdio のトランスポート)。

学ぶこと:

- MCP のツールの定義(`tools/list` の `name` / `description` / `inputSchema`)は、0004 の `tool.Def`(名前・説明・JSON Schema)とほぼ同じ形だということ。
  モデルから見ると、組み込みのツールと MCP のツールに違いは無い(違うのは「実行がどこで起きるか」だけ)
- 送受信される JSON-RPC のメッセージの実物(ログで見る)。どの版の MCP で話したか
- 2026-07-28 版の MCP はステートレスになった(最初の挨拶 `initialize` が無くなり、毎回のリクエストが版と能力を持つ。`server/discover` で前もって確かめられる)。
  LLM が「覚えていないので毎回全部渡す」のと同じ考え方。古い版のサーバーとは、SDK が版を取り決めて話す
- ツールの定義もトークンを使うこと。既製のサーバーはツールが多く(filesystem は 13 個)説明も長いので、会話の上限にどれだけ響くか
- 遠くのツールは中身が見えないので、組み込みのツールのように差分で確認できない(引数で確認するしかない)こと

## 決定事項(ユーザーと決めたこと)

1. **公式の Go SDK(`github.com/modelcontextprotocol/go-sdk`)を使う**。外部パッケージは5つ目になる。使うのは MCP をつなぐパッケージだけ(`AGENTS.md` の外部パッケージの一覧に足す)。
   プロトコルを自分で書かないぶん、送受信したメッセージをログに出して、何が起きているかを見えるようにする
2. **つなぐのは既製のサーバー**。まず公式の filesystem サーバー(`@modelcontextprotocol/server-filesystem` を `npx` で動かす。3-1・3-2 の組み込みのツールと同じことをするので比べやすい)
3. **MCP のツールは全部、実行前に確認する**(読むだけのツールも)。サーバーやツールを信頼して確認を省く仕組みは後で作る(`TODO.md` のロードマップの外に記録)
4. **サーバーの登録は設定ファイル `settings.json` の `mcpServers` の欄**。aibow にはこれまで設定ファイルが無かったので、ここで作る
5. **url で指定するサーバー(Streamable HTTP)にもつなぐ**(2026-10-14、ユーザーと決めた。最初は「やらないこと」に入れていた)。
   イントラの中で動いているサーバーにつなぐのが目的。認証は、API キーなどを `headers` で送るところまで。
   **OAuth(ブラウザでのログイン)は、まだやっていない**(2026-10-14、ユーザーと決めた。「やらない」ではなく、あとで入れるかもしれないもの。`TODO.md` のロードマップの外に記録)

## 決定事項(話の流れから Code が決めて書いたこと。ユーザーの確認待ち)

### 設定ファイル

- **線の引き方**:画面で変える設定は今までどおり DB(`app_settings` / `conversations.settings`)。手で書く設定・その PC でどう起動するかの設定はファイル。
  今ある設定はファイルに移さない。最初の欄は `mcpServers` だけ
  - 理由:サーバーの起動のしかた(`npx` のパスなど)は「その PC の設定」で、会話のデータとは性格が違う。
    `TODO.md` のクライアント/サーバー構成の B(会話ごとサーバーに置く)で DB がサーバーに移っても、これは手元に残るもの
  - 「この会話でどのサーバーを使うか」を作るなら、それは会話の設定なので DB(未決事項 2)
- 置き場所は `%APPDATA%\aibow\settings.json`(DB と同じフォルダ)。`AIBOW_SETTINGS` で変えられる(`_docs/usage.md` の表に足す)
- ファイルが無ければ MCP を使わない(エラーにしない)。JSON が壊れている・欄の形が違うときは、アプリは起動し、理由をログと画面のお知らせに出す
- 読むのは起動したときだけ。変えたらアプリを起動し直す
- 形は多くのツールで使われている `mcpServers` に合わせる(`command` / `args` / `env`)。`args` の中の `${workdir}` は会話の作業フォルダに置き換える

```json
{
  "mcpServers": {
    "filesystem": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "${workdir}"]
    }
  }
}
```

### サーバーの起動と終了

- 作業フォルダはサーバーの起動の引数で渡す(`${workdir}`)。MCP の Roots(クライアントがフォルダを伝える仕組み)は 2026-07-28 版で非推奨になり、
  「設定かツールの引数で渡す」のが新しいやり方のため
- そのため **`${workdir}` を使うサーバーは、作業フォルダごとに1つ起動する**。使わないサーバーは1つだけ起動して、全部の会話で共有する。
  `${workdir}` を使うサーバーは、作業フォルダを決めていない会話には出さない
- 起動するのは、そのサーバーが要る最初の送信のとき(アプリの起動を遅くしないため)。起動したら、アプリを閉じるまで残す。落ちていたら次の送信で起動し直す
- プロセスのカレントフォルダは作業フォルダにする(`${workdir}` を使うサーバーだけ)
- サーバーのエラー出力(stderr)は、サーバーの名前を付けてログに出す
- アプリを閉じたら、サーバーのプロセスも(`npx` から起動された node まで)残さない

### ツール

- `tools/list` の結果を `tool.Tool` にして、組み込みのツールと一緒に `Conversations.toolsFor` で渡す。`inputSchema` をそのまま定義の引数にする。名前と説明はサーバーが返したまま(英語)
- 実行は `tools/call`。結果の `content` のうち文章(text)をつないで結果にする。文章以外(画像など)は「(画像は渡せません)」のように種類だけ書く。`isError` はエラーの結果にする
- 結果が長いときは 8,000 文字で切って、切ったことを書き添える(`read_file` と同じ。その後の「入らない結果はエラーで返す」は今までどおり)
- 時間の上限は、呼び出し 60 秒・起動 60 秒(初回の `npx` はパッケージをダウンロードするため)。停止ボタンで止まる(SDK に context の取り消しを渡す)。数は試して直してよい
- **引数の型の変換を広げる**:Qwen3.5 の書式では値が文字列で届く。今の `CheckArgs` は `integer` / `number` だけを変換するが、filesystem サーバーには
  真偽値(`dryRun`)・文字列の配列(`paths`)・オブジェクトの配列(`edits`)がある。`boolean` / `array` / `object` も JSON Schema の型を見て変換する(書き方は「調べてから決めること」)

### 確認・保存・画面

- 確認のカードには、サーバーの名前・ツールの名前・引数(JSON を整えて)を出す。差分は作らない
- 保存する呼び出しに、サーバーの名前を足す(空なら組み込み。古い会話はそのまま読める)
- ツールのカードに、どのサーバーのツールかを出す(見た目は Code が案を示す)

### 学習用のログ

- サーバーの起動(コマンド・かかった時間)・取り決めた MCP の版とサーバーの名前・ツールの数と定義のトークン数
- 送受信した JSON-RPC のメッセージ(長いものは切る)

### 実装で決めたこと(Code が決めた)

- パッケージは `mcpclient/`(SDK の `mcp` と重ねない)。会話の仕組みは `RemoteTools`(`Start` / `Tools`)の interface だけを見る。`tool` には「外で実行するツール」の印 `tool.Remote`(`Server()`)を足した
- `settings.json` の読み込みはルートの `settingsfile.go`(`aibow.LoadSettingsFile`)。画面で変える設定の `appsettings.go` と並べて、置き場所の違いが分かるように
- 子プロセスまでまとめて止める仕組み(3-3 のジョブオブジェクト・プロセスグループ)を `tool` から `internal/proc` に移し、MCP のサーバーでも使う
- サーバーの起動は送信の最初(会話の上限を確かめる前。MCP のツールの定義も上限に数えるため)。メーターの計算などでは起動しない(最初の送信の前のメーターには MCP のツールが入らない)
- **Roots には対応していないと名乗る**(空の `ClientCapabilities`)。SDK の既定は「対応している」と名乗るが、filesystem サーバーはクライアントが Roots に対応していると Roots のフォルダを引数のフォルダの代わりに使うため
- ~~組み込みのツールと名前が重なった MCP のツールは、仮に出さない~~(未決事項 1 で、サーバーの名前を前に付けることにした)
- 確認の内容(`tool.Preview`)にサーバーの名前と引数(整えた JSON)を足した。保存する結果(`ToolResult`)にサーバーの名前を足した(呼び出しの `ToolCall` は書式から読み取ったものなので変えない)
- 画面:ツールのカードの名前の前に、サーバーの名前を小さな枠で出す。確認のカードは、差分の代わりに引数の JSON を出す
- 閉じるときの待ち時間は 2 秒(標準入力を閉じてから、サーバーが自分で終わるのを待つ)。サーバーはまとめて並行に止める
- ログの1行は 400 文字まで
- **起動の上限をサーバーごとに変えられる**(`startupTimeout`。秒。書かなければ 60 秒)。初回の uv で 60 秒を超えたため(ユーザーと決めた)
- **起動できなかったお知らせに、サーバーのエラー出力の最後の行を添える**(ユーザーと決めた)。リリース版はログが見えず、お知らせだけでは原因が分からなかったため。時間切れなら `startupTimeout` の延ばし方を書く
- **url のサーバー(決定事項 5)**:`url` と `headers` を書く。`type` は書かなくてよい(`command` か `url` で決まる。`stdio` / `http` / `streamable-http` は読んで確かめる。`sse` はエラー)。
  `command` と `url` の両方はエラー。`${workdir}` は使えない(書くとエラー)ので、作業フォルダに関係なく1つのつながりを共有する
  - つなぎっぱなしの GET(standalone SSE)は開かない(使う知らせが無いため。イントラのプロキシで困りにくい)
  - `headers` はログに出さない
  - つながりが切れたことは、ツールの呼び出しの失敗で分かる。サーバーが答えた JSON-RPC のエラーならそのまま、それ以外(SDK が付ける -32003 / -32004 / -32005 を含む)なら一覧から外し、次の送信でつなぎ直す(stdio のサーバーにも同じ扱いをする)

### 調べた結果(調べてから決めること の答え)

- SDK は v1.8.0。間接の依存は `google/jsonschema-go`・`segmentio/encoding`(と `segmentio/asm`)・`yosida95/uritemplate`・`golang.org/x/oauth2`・`golang.org/x/sync`・`golang.org/x/time`。`CGO_ENABLED=0` でビルドできた。SDK の `go.mod` は Go 1.25
- メッセージのログは SDK の `LoggingTransport`(`write:` / `read:` の行を書く)を、1行ずつログに出す `io.Writer` で包んだ
- Windows で `exec.Command("npx", …)` はそのまま動いた(`cmd /c` は要らない)。閉じた後に node は残らなかった(npx が起動した node 2 つが消えた)
- filesystem サーバーは相対パスも受け付けた(カレントフォルダを作業フォルダにしているため)。作業フォルダの中の絶対パスも受け付けた
- 配列・オブジェクト・真偽値の引数:Qwen3.5 の公式テンプレートは、履歴に書き戻すときに配列・オブジェクトを `tojson`、それ以外を文字列にする(真偽値は Python の `True` / `False`)。`CheckArgs` もその形で読む
- **filesystem サーバー(secure-filesystem-server 1.0.0)は 2025-11-25 版で話した**。SDK が `server/discover`(2026-07-28 版)を送り、「Method not found」で返されると、古い版の挨拶(`initialize`)に戻った。ツールは 14 個(使わなくなった `read_file` も入っている)。起動に 10.6 秒(ほとんどが npx)
- テストの偽物のサーバー:SDK でサーバーを作り、`NewInMemoryTransports` でプロセスを起動せずにつなぐ。本物の子プロセスは、テストの実行ファイル自身を MCP のサーバーとして起動して確かめる(こちらとは 2026-07-28 版で話した)
- SDK は `inputSchema` を `map[string]any` で渡すので、サーバーが書いたキーの順は残らない(JSON にし直すと名前の順)。モデルが読むのには困らない
