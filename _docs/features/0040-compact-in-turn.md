## 目的

compact(0002)は組(ユーザーの発言 + その返事・ツールの呼び出しと結果)ごとに外す・要約し、最新の組は必ずそのまま渡す。
そのため、1回の送信の中でツールの結果と思考が積み重なると、今の組だけで会話の上限を使い切り、結果を切るか止めるしかない。
0037 の試し(2026-11-03)では、4B・会話の上限 8,192 で「直してテストを通す」課題を 16 回試し、10 回がテストを動かす前に上限の残りが尽きた
(`_docs/tuning.md` の「予定を頼む1行と、read_file を小さくする」。場所を取っていたのは大きい検索結果と、ループの間プロンプトに残る思考)。
**今の組の中で、古い一歩の結果と思考を省略して続けられるようにする**。

ことば:組の中の「**一歩**」= 返事1つ(思考・ツールの呼び出し)と、その呼び出しの結果。今の組は「ユーザーの発言 → 一歩 → 一歩 → …」と並ぶ。

学ぶこと:

- **コンテキストの編集(tool result clearing)**:実際のエージェントが長い作業で使うやり方。「何をしたか(呼び出し)」は残し、「その時に読んだ中身(結果)」は要れば読み直せるので捨てる
- **KV キャッシュとの付き合い方**:プロンプトの途中を変えると、そこから後ろは読み直しになる。少しずつ縮めるより、水位を決めてまとめて縮めるほうが読み直しが少ない
- **思考はどこまで要るか**:ループの途中の思考は「何のために呼んだか」を覚えておくためのもの。古い一歩の思考を捨てても、呼び出しと予定が残れば続けられるか

## 今の作り(2026-11-05、Chat がコードを読んで確かめた)

- `checkFits`・`turnTokens`(compact.go):最新の組(とシステム・ツールの説明)が上限に入るかを、ループの2回目からの生成の前に見て、超えたら止める
- `fitResult`(agent.go):新しい結果を足すと超えるときは、残りの 3/4 に入る長さで切る。1行も入らなければエラーの結果にして、次の生成はツールを外して答えさせる(`noRoomLeft`)
- `promptMessages`(今は prompt.go):保存した発言をモデルに渡す形にする。`passFrom` がこれを呼び、予定(`withPlan`)を足して数える。送信・メーター・truncate の位置探し・要約の前後の数え方はどれも `passFrom` を通る
- Qwen3.5 の書式(format/qwen35.go)は、最後のユーザーの発言より後ろの返事(= ループの途中)だけ `<think>` を残す。今の組の思考は全部プロンプトに残る
- KV キャッシュはループの途中ではほぼ全部使い回せている。途中を変えると、そこから後ろを読み直す(4B で 3,600〜5,900 トークンが 1.3〜2.1 秒。tuning.md)

## 決定事項(ユーザーと決めたこと。2026-11-05)

1. **縮めるのは、古い一歩のツールの結果と思考**:結果は短い札に置き換え、その一歩の返事の思考は空にして渡す。ツールの呼び出し(名前と引数)は残す。
   モデルに今の組を要約させる形は採らない(4B に要約させる待ち時間と質の不安。古い組の要約は 0002 の summary がしている)
2. **水位でまとめて縮める**:今の組が会話の上限の **3/4 を超えたら、1/2 まで** 古い一歩から順に縮める(上限 8,192 なら 6,144 を超えたら 4,096 まで)。縮めるたびに縮めた一歩から後ろの KV キャッシュが使えなくなるので、回数を減らす
3. **縮めたことを保存する**:発言に「省略した」印(`StoredMessage.Elided`。messages 表に列を足す)を保存する。
   上限で止まったあとに「続けて」と送っても、前の組が元の長さに戻らない(戻ると truncate なら組ごと外れ、summary なら大きな組を要約することになる)。メーター・次の送信も同じ形で数える。
   DB の結果の文と思考は消さない(画面には全部残す。0011 の Excluded と同じく「モデルに渡す形」だけを変える)

## 決定事項(話の流れから Chat が決めて書いたこと。2026-11-05 にユーザーが確かめた)

4. **どの方式で動くか**:compact が truncate か summary の会話だけ。none は「何もしない」なので今のまま止める
5. **縮めないもの**:最新の 2 歩(今まさに使っている結果と、その一つ前)・ユーザーの発言・ツールの呼び出し(引数)・札より短い結果(およそ 200 文字以下。エラーや update_plan の結果など)。
   予定は update_plan の呼び出しの引数に残るので、縮めても消えない
6. **札の文**(日本語。今の `cutResult` に合わせる):`(省略:会話の上限を空けるため、この結果はもう渡していません。元は約 N 文字。要るときは、もう一度呼んでください)`
7. **順番**:新しい結果を足す前に、足すと水位を超えるなら先に縮める → それでも入らなければ今の `fitResult`(切る)→ それでも駄目なら今の `noRoomLeft`。ループの2回目からの生成の前の `checkFits` の前にも同じことをする
8. **組み立てる場所**:`promptMessages` で、印の付いた tool の発言は札に、印の付いた一歩の assistant は思考を空にして渡す。`passFrom` を通るので、送信・メーター・truncate・要約の前後の数え方が同じ内容で数える(plan.go の予定と同じ置き方)。
   印は一歩の単位で付ける(返事と、その呼び出しの結果の全部)
9. **要約(summary)に渡すとき**は今のまま(結果は先頭 200 文字にしている。`summaryMessages`)。縮めた結果も同じ扱い
10. **同じ呼び出しの繰り返し(0028)は変えない**。縮めた結果をモデルが読み直すのは正しい動きで、0028 は「続けて同じ呼び出し」だけを見るので、間に別の一歩があれば当たらない
11. **ログ**(Info):縮めた一歩の数・前後のトークン数・うち思考と結果がそれぞれ何トークン減ったか(どちらが効いたかを tuning.md に書けるように)
12. **画面への知らせ**:compact イベントを使い回し、`Method` を `elide` にして「古いツールの結果 N 件を省略して渡しました(X → Y トークン)」を今の compact の知らせと同じ場所に出す
13. **aibow-server 越し・ブラウザでも同じに動く**(会話の仕組みの中の話なので)。印は `store/remote`(`/aibow/store/`)でも運ぶ。OpenAI 互換の口(Cline など)は会話を持たないので関係しない

## 作業中に決めたこと(Code。2026-11-06 にユーザーが確かめた)

- 水位で比べる「今の組」は `turnTokens`(システムプロンプトとツールの説明を含む。`checkFits` と同じ数え方)。結果を足す前は、足す結果も入れて数える
- 印は一歩の全部(返事と結果)に付け、札にするかは渡すとき(`elideForModel`)に長さで決める(短い結果は印があってもそのまま)。何も減らない一歩(思考が空で、結果も短い)は印を付けない
- 印は外さない(画面で戻すのは「やらないこと」)。会話の方式を none に変えたあとも、縮めた形で渡す(none は「新しく縮めない」で、付いた印はそのまま効く)
- 会話を写す(`CopyShared`)ときは印も写す(`AddMessage` が印ごと入れる。Excluded と同じ)
- 知らせの文は、札にした結果が 0 件(思考だけを空にした)のときは「古い一歩の思考を省略して渡しました(X → Y トークン)」にする。見た目は要約の知らせ(`compact-note`)の、注意の色ではない版
- 未決事項の1つ目(カードの印)は、作って見せる形として、省略して渡した結果のカードの見出しに小さな札「省略して渡した」を付けた(押さなくても見える。説明はマウスを載せたときに出す)。
  付くのは保存した印から作る表示なので、送信の途中では付かず、会話を開き直すと付く(送信の途中は吹き出しの中の知らせで分かる)
