## 目的

`tool` パッケージのツール(ファイルの読み書き・コマンド)を MCP のサーバーとして出すプログラムを Go で作り、aibow をそれにつなぎ直す。

イメージ(2026-10-14、ユーザーと確かめた):

```
今:        aibow.exe [ LLM(頭)+ 会話の仕組み + ツール(手) ]
ステップ5: aibow.exe [ LLM(頭)+ 会話の仕組み ] ⇄ MCP ⇄ aibow-mcp.exe [ ツール(手) ]
                                                         ↑ Claude Code などほかのクライアントからもつなげる
```

- 外に出すのは**ツール(手)だけ**。LLM(頭)を外に出すのはステップ6(OpenAI 互換 API)の役目
- aibow は `settings.json` に書いた自作サーバーを、要るときに子プロセスとして起動し、閉じるときに止める(0006 で作った仕組みのまま)
- クライアント/サーバー構成(TODO.md)との関係:ステップ5は「手(ツール)をどこで動かすか」を切り離す土台、ステップ6は「頭(モデル)をサーバーに置く」(A の形)の土台

学ぶこと(ステップ4の反対側):

- `tools/list`・`tools/call` を受けて答える側の作り。版の取り決め(`server/discover` に答える / 古い版の `initialize`)
- 標準出力は通信に使うので、ログは標準エラー出力に書くこと(aibow はそれをサーバーの名前を付けてログに出す)
- サーバーの側からユーザーに確認を求める仕組み(下の論点 B)
- 自作サーバーと自作クライアントがつながることで、両方の作りが正しいことを確かめる。同じツールを 4B と Claude で使い比べる

## 仕様に入れること(読んでいて気づいたこと。Chat が書いた)

- **時間の上限**:`run_command` は 120 秒だが、MCP のツールの呼び出しはクライアント側で一律 60 秒(`mcp/client/remote.go` の `callTimeout`)。
  サーバーごとに書けるようにする(`settings.json` の `callTimeout` など)か、別のやり方にする
- **停止**:停止ボタンで、サーバーの中の `run_command` の子プロセスまで止まること(`internal/proc` を使う)。
  止める知らせ(`notifications/cancelled`)が SDK でサーバーの処理の context まで届くかは未確認
- **作業フォルダ**:起動の引数で受け取る(`${workdir}`。0006 と同じ)。サーバーの中でも `os.Root` で外に出られない
- **外部パッケージ**:SDK(`go-sdk`)を使う場所が `mcp/` の下(`mcp/client`・`mcp/server`)になる。`AGENTS.md` の一覧と構成の表を直す
- 自分で作るサーバーなので、ツールの引数は 4B が書きやすい今の組み込みの形のままにできる(filesystem の `edit_file` のような配列の引数を避けられる)
