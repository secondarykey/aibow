## 目的

`tool` パッケージのツール(ファイルの読み書き・コマンド)を MCP のサーバーとして出す仕組みを Go で作り、aibow をそれにつなぎ直す。

```
今:        aibow.exe [ LLM(頭)+ 会話の仕組み + ツール(手) ]
ステップ5: aibow.exe [ LLM(頭)+ 会話の仕組み ] ⇄ MCP ⇄ 自作サーバー [ ツール(手) ]
                                                    ├ aibow の中(メモリ内のつなぎ方)… ふだん使う組み込みのツール
                                                    └ aibow-mcp.exe(標準入出力)… Claude Code などほかのクライアントから使う
```

- 外に出すのは**ツール(手)だけ**。LLM(頭)を外に出すのはステップ6(OpenAI 互換 API)の役目
- クライアント/サーバー構成(TODO.md)との関係:ステップ5は「手(ツール)をどこで動かすか」を切り離す土台、ステップ6は「頭(モデル)をサーバーに置く」(A の形)の土台

学ぶこと(ステップ4の反対側):

- `tools/list`・`tools/call` を受けて答える側の作り。版の取り決め(`server/discover` に答える / 古い版の `initialize`)
- 標準出力は通信に使うので、ログは標準エラー出力に書くこと(aibow はそれをサーバーの名前を付けてログに出す)。サーバー自身もファイルに残す(決定事項 11)
- サーバーの側からユーザーに確認を求める仕組み(MRTR。下の決定事項 4)
- 自作サーバーと自作クライアントがつながることで、両方の作りが正しいことを確かめる。同じツールを 4B と Claude で使い比べる

## 決定事項(ユーザーと決めたこと)

1. **サーバーの中身はライブラリのパッケージ `mcp/server/` に置く**(2026-10-14)。`tool` と SDK だけを使い、LLM・会話・画面・ルートの `aibow` を import しない。
   `package main` はほかから import できないので、main に書くと、テストでプロセスを起動せずにつなぐこと・aibow の中で動かすこと(決定事項 3)ができなくなる
2. **標準入出力のサーバーは別の exe にする**(`_cmd/aibow-mcp/`。2026-10-14)。別モジュールにせず、ルートのモジュールに入れる(Wails を使わず、`tool` と SDK はルートの `go.mod` にあるため。`replace` が無いので `go install` できる見込み)。
   Wails の画面アプリは Windows では GUI のプログラムで、標準入出力で話すサーバーに向かないため。`main.go` は引数を読んで `mcp/server` を起動するだけ
3. **aibow の組み込みのツールは、aibow の中で自作サーバーをメモリ内のつなぎ方(SDK の `NewInMemoryTransports`)で立て、MCP 越しに呼ぶ**(2026-10-15。検討メモの論点 6 の (ii))。
   - exe を別に用意しなくても、組み込みのツールが MCP を通る(ロードマップの「ステップ3のツールを MCP サーバー経由に置き換える」に合う。送受信のメッセージもログに出る)
   - 別の exe(`aibow-mcp`)は、Claude Code などほかのクライアントから使うときと、プロセスの境目(起動・終了・標準入出力)を確かめるときに使う。aibow から `settings.json` に書いてつなぐこともできる(5-2 で比べる)
   - 検討メモの決定事項 C(組み込みのツールは残す)は、「組み込み = aibow の中で動く自作サーバー」の意味になる。`tool` のツールを直接呼ぶ道は、置き換えたら消す
4. **確認の画面の差分は、サーバーからユーザーに確認を求める(MRTR)で出す**(2026-10-15。検討メモの論点 1 の (b))。
   MRTR(Multi Round-Trip Requests。2026-07-28 版)は、サーバーが `resultType: "input_required"` の結果で聞きたいこと(`inputRequests`)を返し、
   クライアントが答えを `inputResponses` に入れて同じ呼び出しを送り直す仕組み。サーバーは途中の状態を覚えず、送り直しの中身だけで続きを決める(ステートレス)
   - 書き換えるツール(`write_file`・`edit_file`・`run_command`。`tool.Confirmable` のもの)は、最初の呼び出しでは実行せず、今の `Preview`(差分・コマンド)を入れた確認(`ElicitParams`)を返す。
     確認の答えが「受け入れる」で送り直されたら実行する
   - aibow は確認を受け取ったら、今の確認のカード(差分付き)を出す
5. **二重の確認を避ける**(2026-10-15):確認をサーバーに任せたツールは、aibow が呼ぶ前の確認をしない。確認はサーバーから来たときに1回だけ出す(下の「確認の流れ」)
6. **確認を受け付けないクライアントには、書き換えずにエラーを返す**(2026-10-15):elicitation に対応していないクライアントからの書き換えるツールの呼び出しは、実行せずに
   「このクライアントは実行前の確認(elicitation)に対応していないため、書き換えません」を返す(クライアント自身の確認に任せて実行する案より安全なほう)
7. **Streamable HTTP で出す(検討メモの 5-5)は、今回はやらない**(2026-10-15。あとに回す)
8. **時間の上限はサーバーごとに `settings.json` の `callTimeout`(秒)で書けるようにする**(2026-10-15)。書かなければ今の 60 秒。aibow の中のサーバーは 120 秒(`run_command` の上限に合わせる)
9. **`readOnlyHint` は自作サーバーの読むだけのツールに付ける。ただし aibow がそれを信じて確認を省くかは決めず、今の扱い(tools.json・会話の上書き)のまま**(2026-10-15)。
   どう扱うかは TODO.md の「ツールの信頼の続き」で決める
10. モジュール名を `github.com/secondarykey/aibow` に変える(**済み**。2026-10-14)・MCP のクライアントを `mcp/client/` に移す(**済み**。2026-10-14)。
    クライアントとサーバーの両方で使う部分(やり取りを1行ずつログに出す部分など)は `mcp/internal/` に置く
11. **サーバーのログはファイルにも書く。形は aibow にならい、名前でサーバーのものだと分かるようにする**(2026-10-15、ユーザーの指示。5-1 のあとに足した)。
    標準エラー出力はクライアントの中に取り込まれて見えにくく、aibow の exe も Info の行をファイルに残さないため。
    「サーバー側のログは別に考える」(0008 のやり残し 7)は、このときのために `aibow/log` を作り直しておいた、という意味だった
    - 置き場所はアプリと同じ `%APPDATA%\aibow\logs`(`AIBOW_LOG_DIR`)。名前は `aibow-mcp_<日付>.log`・`aibow-mcp_crash.log`(`log.Options.Prefix` を足した)
    - 10 日分を残す・異常終了を記録する(`log.CatchCrash`)もアプリと同じ。前回の異常終了は、画面が無いのでログに Warn で書く
    - レベルは Info(ツールを1回呼ぶごとに1行なので少ない)。標準エラー出力にも、これまでどおり出す
    - 作業フォルダごとに複数のプロセスが同じ日のファイルに書くので、各行にプロセスの番号(`pid=…`)を付ける。ファイルは追記で開くので壊れない。
      ログの土台が書く区切りの行(`since the file exists, starting from here.` / `end here.`)には pid が付かない
12. **Claude Code からつなぐ確認は 5-3 のあとで行う**(2026-10-15、ユーザーと決めた)。5-1 では読むツールしか動かず、SDK のクライアント・手で書いた JSON・aibow のクライアントで確かめた。
    クライアントの対応で動きが変わるのは 5-3 の確認(elicitation)なので、そのときに確かめる

## 決定事項(Code が決めて書き、ユーザーが確かめたこと。2026-10-15)

### サーバー(`mcp/server`)

- 出すツール:`tool` のツール全部(`get_current_time`・`calculate`・`list_files`・`read_file`・`write_file`・`edit_file`・`run_command`)。
  ツールの名前・引数・説明は今の組み込みのまま(4B が書きやすい形。filesystem の `edit_file` のような配列の引数を避けられる)
- 作業フォルダは起動の引数で受け取る(`aibow-mcp <作業フォルダ>`。aibow の `settings.json` では `${workdir}`。0006 と同じ)。サーバーの中でも `os.Root` で外に出られない。
  作業フォルダが無いときは、作業フォルダを使わないツール(時刻・計算)だけを出す
- ログは標準エラー出力とファイルに書く(決定事項 11)。標準出力には何も書かない
- 停止:クライアントが止めると、SDK が `notifications/cancelled` を送り、サーバーのツールの処理の context が止まる(SDK のコードで確かめた。下の「調べた結果」)。
  `run_command` は今の `internal/proc` で子プロセスまで止める。実際に止まることをテストで確かめる
- MRTR の確認(`ElicitParams`)の中身:
  - `message`:人が読む文(何をするか・対象・差分またはコマンド)。aibow 以外のクライアント(Claude Code など)はこれを出す
  - `_meta` の `aibow/preview`:今の `tool.Preview` を JSON で入れる。aibow はこれがあれば今のカード(差分の色付け)で出す
  - `requestedSchema`:理由(`reason`。文字列・省略可)だけを持つフォーム。拒否したときの理由をモデルに返すため(0005 の「拒否したら理由をモデルに返して続ける」)
  - 答えが `decline` / `cancel` なら実行せず、今の組み込みと同じ拒否の文(理由付き)を結果に返す
- 確認と実行の間にファイルが変わったときの扱い:サーバーは覚えないので、送り直しで差分を作り直す。
  最初の確認のときの対象の中身のハッシュを `requestState` に入れておき、送り直しで違っていたら実行せず「確認のあとでファイルが変わったため書き換えませんでした」を返す

### aibow(クライアントの側)

- **MRTR の送り直しは SDK に任せず、aibow で書く**(`ClientOptions.MultiRoundTrip.Disabled`)。理由:
  - SDK の自動の送り直しは1つの context の中で回るので、ユーザーが確認のカードを見ている時間まで時間の上限(`callTimeout`)に数えてしまう。aibow で書けば、サーバーとのやり取りの1往復ごとに上限をかけ、確認を待つ時間は数えない
  - `input_required` で返ってくる → 答えを入れて送り直す、の往復がコードに見える(学ぶ題材)
  - elicitation に対応していることはクライアントの capabilities で宣言する
- **確認の流れ**(決定事項 5):
  - 確認をサーバーに任せるのは、aibow の中の自作サーバーのツールだけ(aibow が自分で立てたので信頼できる)。
    `settings.json` に書いたサーバー(`aibow-mcp.exe` も含む)は、今までどおり呼ぶ前に確認し、さらにサーバーから確認が来たらそれも出す(サーバーの名乗りは偽れるので、名乗りでは信頼しない)
  - サーバーから確認が来たときは、そのツールの扱い(会話の上書き → PC の既定 → 決まりの既定)を見る:`allow`(確認しない)なら出さずに受け入れて答える、`ask` ならカードを出す
  - カードのボタン(「今後許可しない」「この会話では今後聞かない」など。0010)は今のまま使え、答えたときに会話の上書きを書く
- **ツールの名前とグループは今の組み込みのまま**:aibow の中のサーバーのツールは、今の組み込みと同じグループ(組み込み)・同じ名前で見せる。
  tools.json の `builtin` と会話の `tool_policies` は書き直さなくてよい。決まりの既定(書き換えるツールとコマンドは確認する、ほかは確認しない)も今のまま
- 学習用のログ:今の MCP のクライアントのログ(送受信を1行ずつ)に、`input_required` の往復(何回目か・何を聞かれたか・答え)を足す

## 調べた結果(2026-10-15。Code が Go SDK v1.8.0 のコードを読んで確かめた)

- **MRTR に対応している**(`mcp/mrtr.go`)
  - サーバー:ツールの処理が `CallToolResult.InputRequests` に `ElicitParams` などを入れて返す。送り直しでは `CallToolParams.InputResponses` に答えが入り、ツールの処理がもう一度呼ばれる。`RequestState` で状態を往復させられる
  - クライアント:既定では、送り直しを SDK が自動で行う(`ClientOptions.ElicitationHandler` で答えを作る)。`ClientOptions.MultiRoundTrip.Disabled` で止めると、`CallToolResult.NeedsInput()` を見て自分で送り直す
  - 古い版(2026-07-28 版より前)のクライアントが相手のときは、サーバー側の SDK が以前の `elicitation/create`(サーバーからクライアントへのリクエスト)に切り替えて同じ流れにする。ツールの処理の書き方は同じ
- **停止の知らせはサーバーの処理まで届く**:クライアントの context が止まると SDK が `notifications/cancelled` を送り(`mcp/transport.go`)、
  サーバーは `jsonrpc2.Connection.Cancel` でそのリクエストの処理の context を止める
- **メモリ内のつなぎ方** `NewInMemoryTransports` がある(`mcp/transport.go`)

## 完了の条件

- `aibow-mcp <作業フォルダ>` を Claude Code から MCP のサーバーとしてつなぎ、読むツール・書き換えるツール(確認が出る)・コマンドが使える
- aibow の `settings.json` に `aibow-mcp` を書いてつなぎ、組み込みと並べて動く(速さ・トークン数・ログを比べて `_docs/tuning.md` に書く)
- aibow の組み込みのツールが、aibow の中の自作サーバーを MCP 越しに通る(ログに送受信が出る)。`tool` のツールを直接呼ぶ道は無くなる
- 書き換えるツールの確認が MRTR で来て、今と同じ差分付きのカードで出る。拒否の理由がモデルに返る。「この会話では今後聞かない」「今後許可しない」が今までどおり効く。確認は1回だけ出る
- 確認を待っている時間は時間の上限に数えない
- 停止ボタンで、サーバーの中の `run_command` の子プロセスまで止まる
- elicitation に対応していないクライアントからの書き換えるツールの呼び出しは、実行せずにエラーを返す(テスト)
- `settings.json` の `callTimeout` がサーバーごとに効く
- テスト:プロセスを起動せずに(メモリ内のつなぎ方で)`mcp/client` と `mcp/server` をつなぎ、ツールの一覧・呼び出し・MRTR の確認(受け入れ・拒否・確認のあとでファイルが変わった)・停止を確かめる
- `AGENTS.md`・`_docs/mcp.md`・`_docs/usage.md` を直す
