## 目的

過去の会話を探せるようにする。雑なイメージは全文検索だが、どんな検索が作れるかを含めて考える。

## 作れる検索の候補

### ① 部分一致(LIKE)

- 仕組み: SQL の `content LIKE '%語%'` で、発言を1件ずつ文字列として探す
- 良い点: いちばん簡単。1文字の語でも引ける。DB の形を変えなくてよい
- 弱い点: 発言が増えると遅くなる(ただ、個人の会話なら数万件くらいまでは十分速いはず)
- 学べること: SQL の基本だけ

### ② 全文検索(SQLite の FTS5)

- 仕組み: 検索用の索引の表(仮想テーブル)を別に作り、そこを引く。
  日本語は語の間に空白が無いので、文を3文字ずつに区切って索引にする `trigram` を使う
- 良い点: 速い。ヒットした箇所を抜き出して強調する `snippet()` や、関係の深い順に並べる `bm25()` も付いている
- 弱い点: 2文字以下の語(「要約」「検索」など)は trigram では引けないので、短い語は ① で補う必要がある。
  マイグレーションで索引の表を足し、発言の保存と索引を同期させる仕組み(トリガー)も要る
- 学べること: 索引の仕組み、日本語の区切り方の難しさ

### ③ 意味の近さで探す(埋め込み / embedding)

- 仕組み: 文を「意味を表す数値の列」(埋め込みベクトル)に変えて保存しておき、検索語の数値に近い発言を探す
- 良い点: 言葉が違っても意味が近ければ引ける(「あの GPU の話」で「VRAM が足りない」の発言が見つかる)
- 弱い点: 埋め込み用のモデルが別に要る(llama.cpp で動かせる)。VRAM 8GB に会話用のモデルと同時に載せるか、CPU で動かすかを決める必要がある。
  全部の発言を変換しておく時間もかかる
- 学べること: 埋め込みと、RAG(探した資料をモデルに読ませる仕組み)の基礎。ステップ3〜4のエージェントにもつながる

### ④ 探した結果をモデルに読ませて答えさせる

- 仕組み: ①〜③ で見つけた発言をモデルに渡し、「前に〇〇について何て決めたっけ?」に答えさせる
- 「会話を検索する」をモデルが自分で呼ぶ道具(ツール)にすると、ステップ 2-3(ツール呼び出し)の題材にもなる

## 調べたこと

- 今のドライバー(`modernc.org/sqlite`、SQLite 3.53.4)で、FTS5 の `tokenize='trigram'` が使える(2026-10-12 に確認)
  - 「要約し」「上限を超」「キャッシュ」のような3文字以上の語は、日本語でも部分一致で引けた。`snippet()` で該当箇所の抜き出しと強調もできた
  - 「要約」のような2文字の語は引けなかった(trigram は3文字以上が必要)

## 相談して決めたいこと

1. **どこを探すか**: タイトル・発言・思考・要約のどれか。思考は量が多いので、混ぜるか分けるか
2. **方式**: どれにするか、組み合わせるか。
   Code のおすすめは、まず ① か ①+② の文字で探す検索を作り、意味で探す ③④ はあとの段階にすること
   (① は確実に引けて簡単、② は速さと学びがある。③④ は 2-3 以降の流れと合わせたほうが自然)
3. **画面**: 検索欄の置き場所(会話の一覧の上など)、結果の見せ方(会話ごとにまとめて抜き出しを付けるか)、
   結果を押したらその発言まで飛んで強調するか
4. **絞り込み**: 今の会話の中だけを探すか、全部の会話を探すか。日付や、自分の発言だけ・返事だけで絞るか
