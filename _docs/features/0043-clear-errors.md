# 0043: 設定・管理・会話の設定の画面のエラーを次の操作で消す

- 状態: ✅ 完了(2026-11-08。実際の画面では確かめていない。下の「確かめていないこと」)
- ロードマップ: ロードマップの外(画面の不具合の直し)
- 決めた日: 2026-11-08(ユーザーが Code のセッションで直接頼んだ。aibow-server へのログインを間違えるたびに「名前かパスワードが違います」が積み重なった画面を見せて、
  「この手のエラーが頻発します。何か抜本的に変更しないと行けないのではないでしょうか？」。
  直し方はユーザーが決めた:「エラーが起こっている状態で次の操作をした場合って、まずクリアすれば OK」「致命的なエラーの場合って少なくともログファイルに残ってますよね？あんまり気にしないでいいと思います(ユーザが気にせず次の操作をしているわけですし)」)
- 前提: 0019(画面からつなぐ・ログイン)、0032(管理の画面)

## 目的

設定・管理・会話の設定の画面は、開いてから出たエラーを上に並べる。エラーは会話の表示と同じ仕組み(`transcript.addError`)で**足すだけ**なので、
同じ操作を3回失敗すると同じ文が3つ並び、成功しても消えず、閉じることもできなかった。

同じ形の直しは前にもあった(起動に失敗した理由と同じエラーを出さない `startupError`、会話を開くたびにエラーが積み重なる)。
部品ごと・エラーごとに直しても、また別の所で起きるので、エラーの扱いそのものを決める。

学ぶこと:

- **エラーには「記録」と「状態」がある**:会話の表示のエラーは「どこで何が起きたか」の記録で、足していくのが正しい。
  フォームの操作のエラーは「今の操作が通らなかった理由」で、次の操作で役目を終える状態。性質の違うものを1つの口に流すと、どちらかの扱いが合わなくなる
- **イベントの capture**:React の `onClickCapture` などは、外側の要素が内側より先に受け取る。外枠で「操作した」を拾えば、中の部品を1つも変えずに決まりを足せる
- **`display: contents`**:包む要素そのものは並べ方に入らず、子がそのまま親(`main` の flex)の子として並ぶ

## 決定事項

1. **設定・管理・会話の設定の画面のエラーは、その画面で次の操作をしたら消す**(ユーザーが決めた)。前のエラーを読んだうえで次の操作をしているので、残さなくてよい
2. **操作に数えるもの**:ボタンを押す・フォームを送る・入力欄で Enter(IME で変換を決める Enter は除く)・選択肢やチェックを変える。
   **文字を打っている途中は数えない**(パスワードを打ち直している間もエラーを読めるように。エージェントが決めた)
3. **消してから操作が動く**(capture で、ボタンの `onClick` が Go を呼ぶより先に消す)。同じ失敗をやり直したときは、一度消えてから出直すので、やり直したことが見える
4. **部品ごとには直さない**。`App.tsx` で3つの画面を `operationEvents`(`errors.ts`)の箱で包み、表示を始める位置(`settingsFrom`)を操作のたびに進めるだけ。50 か所ほどある `onError` の呼び出しはそのまま(エージェントが決めた)
5. **会話の表示のエラーは消さない**(どこで失敗したかの記録なので。エージェントが決めた)
6. **ログについて**:画面に返すだけでログに出ないエラーもある(アプリはログインの失敗をログに出していない。2026-11-08 に確かめた)。
   操作の結果なので、もう一度やれば出る。消しても困らない、とユーザーに伝えたうえで、この形にした

## やらないこと

- 同じ文のエラーを1つにまとめる・×で閉じる(次の操作で消えるので要らない、と判断した。積み上がる別の形が見つかったら考える)
- 起動に失敗したときの `startupError` の特別扱いを外す(タブの切り替えも操作に数えるので、外しても積み上がらない見込みだが、確かめていないので残した)
