# 0014: 設定のプロファイル化

- 状態: 仕様(未着手)
- ロードマップ: ロードマップ2 ステップ 7
- 決めた日: 2026-10-19(Chat でユーザーと決めた)
- 前提: 0009(会話の個別設定・新しい会話の既定・会話ごとの作業領域)、0006 / 0010(ツールの扱いの層・`tools.json`)、0013(クライアント/サーバー構成。ステップ10・11で、プロファイルを管理者が作って配る)

## 目的

今の「新しい会話の既定」(1つだけ)を、**名前を付けて何個も持てる「プロファイル」**にする。会話はプロファイルを選んで作る。

あわせて、**「変更できない項目」(決まり)**をプロファイルに持たせる。
最終的には上位(サーバー・管理者)から「このツールは使えない」「この設定は変えられない」とできる必要があるので(2026-10-19、ユーザーの指摘)、今のうちにその形で作っておく。
今はプロファイルを作るのは自分なので、自分で自分に決まりをかける形(例:コマンドを実行させないプロファイル)。

学ぶこと:

- 設定を「値」(写す)と「決まり」(そのつど見に行く)に分けること。ステートレスのモデルに毎回履歴を渡すのと同じく、「何を写し、何を参照するか」で動きが変わる
- 扱いを決める場所を1か所にし、画面は結果を出すだけにすること(0006・0009 の方針の続き)。画面で押せなくするだけでなく、保存のときに Go が断る
- DB の表を足すマイグレーション(`user_version`)と、古い設定の引き継ぎ

## 決定事項(ユーザーと決めたこと。2026-10-19)

### プロファイルの中身

1. **プロファイルには、この PC に依存しないものだけを入れる**(ステップ11で、ほかの人にそのまま配れるようにするため)
   - 入れる(値):システムプロンプト・temperature・思考・presence penalty・compact の方式・会話の上限・返事の上限・**モデル**・使うツールのグループ(組み込み・MCP サーバーの名前)
   - 入れない:作業フォルダ(PC のパス)・GPU の層数(下の 4)・MCP サーバーの起動のしかた(`settings.json`)・ツールごとの確認の扱い(`tools.json`)
   - この PC の `settings.json` に無い MCP サーバーがプロファイルに書かれていたら、無視する
2. **会話とプロファイルの関係は「値は写し + どのプロファイルから作ったかを覚える」**
   - 会話を作るときに値を写す(今の既定と同じ)。プロファイルの値をあとで変えても、今ある会話の値は変わらない(0009 の約束のまま)
   - 会話は元のプロファイルを覚える(`profile_id`)。決まり(下の 5)を引くのと、ステップ11で「どの共有の作業の会話か」を決める手がかりに使う
3. **モデルを会話ごとに持つ**。送信(と今すぐ要約・作り直す)の前に、読み込んでいるモデルと会話のモデルが違えば読み直す
   - 0009 の作業領域と同じやり方:会話を開いただけでは読み直さない(一覧を見て回るだけで読み直しが続かないように)。読み直したらトーストとログで知らせる
   - 入力欄の下のモデルの選択は「この会話のモデルを変える」の意味になる(0011 の「9B に切り替えて作り直す」もこれで動く)
   - 欠点:モデルの違う会話に切り替えた最初の送信は、読み直しの分(数秒〜十数秒)待つ
4. **GPU の層数は、モデルごとにこの PC に覚える**(プロファイルに入れない)
   - 載せられる層の数は、モデルの大きさと PC の VRAM で決まるため。モデルが会話ごとに変わるので、層の数もモデルと一緒に変わってほしい
   - まだ覚えていないモデルは、今の全体の値(`gpu_layers`)を使う

### 決まり(変更できない項目)

5. **決まりはプロファイルに持たせる**。決まりは2種類:
   - **固定**:項目ごとの印。固定した項目は、そのプロファイルの会話では変えられない(対象は 1 の「入れる(値)」の項目。ツールのグループの選択も含む)
   - **使えない**:ツールのグループ(組み込み・MCP サーバー)単位と、ツール単位。会話の上書き(`tool_policies` の `on`)でも使えるようにはできない。
     0009 の「既定で使わない」(`tools.json`。会話で使うにできる)の上に、「使えない」の段が加わる
6. **値は写し、決まりは参照**。決まりは、会話が覚えているプロファイルをそのつど見に行く(管理者があとからツールを禁止したら、今ある会話にもすぐ効いてほしいため)
7. **固定した項目は、会話の値ではなくプロファイルの値を使う**(あとから固定して、会話の値と違うときも)。
   つまり「固定していない項目は写し、固定した項目は参照」。モデルを固定した場合は、送信のときに読み直す(3 と同じ)
8. **扱いを決めるのは Go の1か所**
   - 「この会話でこの項目を変えてよいか」「このツールを使ってよいか」「送信に使う実際の設定(固定の項目をプロファイルの値にしたもの)」は Go が決めて返す
   - 画面は、押せなくして理由(「プロファイルで固定」「プロファイルで使えない」)を添えるだけ(0009 の「どこで決まったか・使えない理由を添える」と同じ)
   - **保存のときにも Go が断る**(画面で押せなくするだけでは、ステップ9のブラウザなどほかの入口から変えられてしまうため)
   - ツールの扱いは、今の `toolPolicy`(会話の上書きが一番優先)の上に「使えない」を足す。順は:使えない(プロファイル)→ 会話の上書き → PC の既定(`tools.json`)→ 決まりの既定

### 保存・引き継ぎ・消したとき

9. **`profiles` の表を新しく作る**(DB の版を1つ上げる)。列は id(UUIDv7)・名前・値(JSON)・決まり(JSON)・作った日時・更新した日時・しまったか(下の 11)。
   会話の表に `profile_id` の列を足す(外部キーで消えないようにする。会話はプロファイルを消しても残す)。
   ステップ10・11で、持ち主・公開範囲の列を足す場所になる。`Store` の interface にプロファイルのメソッドを足す
10. **今の設定の引き継ぎ**(起動したときに1回)
    - 今の「新しい会話の既定」(`conversation_defaults`)と最後に使ったモデル(`last_model`)と、新しい会話で最初から使うツールのグループから、プロファイル「既定」を1つ作る。決まりは無し
    - プロファイルは必ず1つ以上ある。**新しい会話で最初に選ばれるプロファイル**に印を付ける(最初は「既定」)
    - 今ある会話は「既定」から作ったものとして紐づける(中身も実際に既定の写しなので)。今の「既定」には決まりが無いので、動きは変わらない
    - 今ある会話には、今のモデルを写して保存する(0009 の `FillMissingLimits` と同じやり方)
    - GPU の層数は、今の値を今のモデルの値として覚える
    - DB が空のとき(初めての起動)の「既定」の値は、今の環境変数の初期値(`AIBOW_HISTORY_TOKENS` など)から作る
11. **プロファイルを消すときは「しまう」**:しまったプロファイルは新しい会話では選べないが、決まりは残る(会話からは引ける)。
    使っている会話が1つも無ければ、本当に消せる。「新しい会話で最初に選ばれる」印の付いたプロファイルはしまえない。
    (会話の `profile_id` を空にして決まりも外す、だと、消しただけで禁止が黙って外れる。使っている会話があれば消せない、だと会話が多いと消せなくなる)

### 画面

12. **画面は一旦作ってから、使い方を考える**(ユーザーと決めた)。下は大まかな案で、Code が作ってユーザーが使ってみて直す
    - 新しい会話の画面:プロファイルを選ぶところを出す。選ぶと、その値(モデルも)で会話を作る
    - 設定の画面:「新しい会話の既定」をプロファイルの一覧と編集に置き換える。編集は今の `ConversationSettingsForm` に、モデル・ツールのグループ・決まり(項目ごとの固定の印・使えないツール)を足す
    - 会話の設定の画面:どのプロファイルから作ったかを出す。固定の項目は押せなくして「プロファイルで固定」と添える。
      「この設定を新しい会話の既定にする」は「プロファイルに保存」(上書き / 新しいプロファイルとして保存)にする

## 決定事項(話の流れから Chat が決めて書き、ユーザーが確かめたこと。2026-10-19)

- 「新しい会話で最初から使うツールのグループ」は、プロファイルの値(使うツールのグループ)で決める。今の `tools.json` の `notDefault`(グループのチェック)と `seen`(足したサーバーを最初は使わない、0009 の 7)の役目はプロファイルに移る。
  `tools.json` に残るのは、ツールごとの使う / 使わない / 確認するの PC の既定。
  `settings.json` に足したばかりのサーバーは、どのプロファイルにも書かれていないので、新しい会話では使わない(0009 の 7 と同じ結果)
- ツールを指す名前は、会話の上書き(`tool_policies`)と同じく、モデルに見せる名前を使う
- `aibow-api` はプロファイルを使わない(DB を読まない。0012 のまま)

## 完了の条件

- プロファイルを作る・名前を変える・値と決まりを変える・しまう・消す(使っている会話が無いとき)ができる
- 新しい会話はプロファイルを選んで作り、その値(モデルも)が写る。会話は元のプロファイルを覚えている
- 会話ごとにモデルを持ち、モデルの違う会話に送信すると読み直す。GPU の層数はモデルごとに覚える
- 固定した項目は会話で変えられず(画面で押せない + Go が保存を断る)、送信にはプロファイルの値が使われる。あとから固定しても効く
- 使えないツールはモデルに見せず、会話の上書きでも使えるようにできない。あとから使えないにしても効く
- 今の DB を引き継げる:「既定」ができ、今ある会話はそれに紐づき、モデルが写っている。前の版の DB から起動して、会話がそのまま続けられる
- モデルなしのテスト(`go test ./...`)で、引き継ぎ・決まりの判定(固定・使えない・ツールの扱いの順)・保存のときに断ることを確かめている
- `AGENTS.md`・`_docs/`(`conversations.md`・`tools.md`・`ui.md` など)の説明を今の形にしている
