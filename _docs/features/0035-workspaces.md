## 目的

今の作業フォルダは「会話ごとのパス1つ」。これを、**対象のソースコード(リポジトリ)を会話の外に独立して登録し、複数のフォルダをまたいで扱える**ようにする(2026-11-02、ユーザーの要望)。

ユーザーの考え(2026-11-02):メインのターゲットに「リポジトリ」を1つ、ほかの複数のディレクトリを「読み物」として扱うイメージ。ただし読み物の側も編集しうるので、
「ディレクトリを複数設定でき、それぞれがリポジトリでありうる」ほうが拡張性がある。

学ぶこと:

- **「対象」を会話から切り離す**:コーディングエージェントは「どのソースに対して働くか」が先にあり、会話はその上の1回の作業。Claude Code の「起動したフォルダ + 追加のフォルダ」と同じ形
- **フォルダごとに守り方を変える**:読むだけのフォルダは、書くツールを `os.Root` の仕組みで受け付けない(0005 の「仕組みで守る」の続き)。コマンドは今と同じく確認が守り
- **PC の事情は PC に置く**:フォルダのパスは「その PC のもの」なので、会話(server.db に入りうる)には ID だけを置く(`tools.json` と同じ考え方)
- **モデルに複数の場所を見せる**:引数を増やすか、パスに埋めるか。4B が迷わない形を試して確かめる

## 今の作り(2026-11-02、Chat がコードを読んで確かめた)

- 作業フォルダは `ConversationSettings.WorkDir`(絶対パス1つ)。入力欄の上の `WorkDirBar` で決める。「新しい会話の既定」とプロファイルには入れない
- ツールは `tool.Files(dir)` で会話ごとに作る。`Conversations.workDir(set)` が、アプリでは `set.WorkDir`、ブラウザ(`IgnoreWorkDir`)では資料のフォルダを返す(`rules.go`)
- `run_command` は作業フォルダをカレントにして動く
- `${workdir}` を使う MCP のサーバーは、作業フォルダごとに1つ起動する(`mcp/client` の `serverKey`)
- 環境の説明(`Conversations.environment`。`conversation.go`)に `Working directory: <パス>` を1行書く
- 穴:aibow-server につないでいると `work_dir` が server.db に入り、別の PC で開くと前の PC のパスが残る(backlog「会話の作業フォルダを PC ごとにする」)

## 決定事項(ユーザーと決めたこと)

1. **ワークスペースを名前付きで PC に登録し、会話はその ID だけを持つ**(検討メモの案 B)。backlog の「会話の作業フォルダを PC ごとにする」は、これで塞ぐ(別の PC にはその ID が無いので、フォルダのツールを出さない)
2. **ワークスペースはフォルダの組**。フォルダごとに「メインか」と「読むだけ / 書く」を持つ。メインは1つだけ。**リポジトリかどうかは種類として分けず、`.git` があるかを自動で見る**(どのフォルダもリポジトリでありうる)
3. **モデルには、ファイルのツールの引数 `folder` でフォルダを選ばせる**。省くとメイン。名前は JSON Schema の `enum` で並べる(パスの先頭に名前を付ける形は、メインの中のサブフォルダと区別できないので採らない)
4. **3段に分ける**:段1 ワークスペース(フォルダ1つ。今と同じ動き + PC ごとの穴を塞ぐ)→ 段2 フォルダを複数に → 段3以降 worktree など(別の仕様。backlog「コーディングエージェントとして洗練する」)

## 決定事項(話の流れから Chat が決めて書いたこと。ユーザーの確認待ち)

### 呼び名とプロジェクトとの関係

- 呼び名は「**ワークスペース**」(画面・コード `Workspace`)
- ユーザーの迷い(2026-11-02):「プロジェクトと一緒では? プロジェクトにワークスペースがある、とも言える」。Chat の整理:
  - **ワークスペース = PC のフォルダの組**(パスは PC ごと。人と共有しない)
  - **プロジェクト = 人と会話のまとまり**(backlog「共有の再検討」で出た、まだ無い概念。server.db に置いて人と共有するもの)
  - プロジェクトを作るときは「**プロジェクトがワークスペースを持つ**」形でつなぐ(プロジェクトには ID と名前だけを置き、各 PC でその ID に自分のパスを結び付ける)。今のうちに分けておけば、プロジェクトの有無に関係なくワークスペースだけで使える
  - この仕様ではプロジェクトを作らない。プロジェクトを決めるときに、この線で合うかを見直す

### 保存(段1)

- 置き場所は PC の手元の `%APPDATA%\aibow\workspaces.json`(`tools.json`・`connection.json` と同じ「アプリが書くファイル」。環境変数で場所を変えられるようにするかは、ほかのファイルに合わせる)。aibow-server につないでいても PC に残る
- 1つのワークスペース:`id`(UUID)・`name`(画面の名前)・`folders`(段1では1つ)
- 1つのフォルダ:`path`(絶対パス)・`name`(モデルが呼ぶ短い名前。既定はフォルダ名。ワークスペースの中で重ならない)・`main`・`writable`
- 会話の設定は `WorkDir` の代わりに `Workspace`(ID)を持つ。見つからない PC では、作業フォルダが無いものとして扱い(フォルダのツール・`${workdir}` の MCP・環境の説明を出さない)、入力欄の上に「この PC にはこのワークスペースがありません」と出して選び直せるようにする
- **今ある会話の移し方**:起動したときに、`work_dir` が入っている会話のうち**そのパスがこの PC にあるもの**は、パスごとに1つのワークスペース(フォルダ1つ・メイン・書く。名前はフォルダ名)を作って ID に置き換える。パスが無いものはそのまま残し、その PC では使わない(別の PC で起動したときにそちらで移せるように)。移し終えた `work_dir` は空にする
  - aibow-server につないでいるときの会話(server.db)も、つないでいる PC で同じように移す
- 「新しい会話の既定」とプロファイルにはワークスペースを入れない(0005・0014 のまま)。会話を作るときに選ぶ
- 共有で写すときもワークスペースは渡さない(0018 のまま)

### 画面(段1)

- 入力欄の上の `WorkDirBar` を、ワークスペースを選ぶ部品にする(決めていないときはアイコンだけ、決めたら名前と ×)。一覧の最後に「フォルダから新しく作る」(今のフォルダを選ぶダイアログ → そのフォルダ1つのワークスペースを作って選ぶ)
- ワークスペースの一覧・名前の変更・削除は、設定の画面に置く(どのタブに置くかは未決事項)。削除しても会話は消さない(見つからないワークスペースになる)
- ブラウザ(aibow-server)の会話では出さない(今と同じく資料のフォルダ。0024)

### ツールと環境の説明(段2)

- `list_files`・`read_file`・`write_file`・`edit_file` に `folder`(省略可・`enum`)を足す。フォルダが1つのときは引数を出さない(4B のプロンプトを増やさない。段1と同じ定義のまま)
- 読むだけのフォルダに `write_file`・`edit_file` を向けたら、「<名前> は読むだけのフォルダです」のエラーをモデルに返す(確認のカードを出す前に)
- フォルダの中を指す絶対パスは、どのフォルダの中かを見て振り分ける(今も作業フォルダの中の絶対パスを受け付けているため)。`folder` と食い違えばエラー
- `run_command` はメインをカレントにする。読むだけのフォルダもコマンドからは書けてしまうので、守りは今と同じく確認(環境の説明に書くのは「読むだけ」の印まで)
- `${workdir}` の MCP はメインのパスで起動する(ほかのフォルダを渡す書き方は作らない)
- 環境の説明は、フォルダが1つなら今と同じ形。複数なら次のように並べる(英語。今の説明の決まりのまま):

```
# Environment
Folders (pass the folder argument; omit it for the main folder):
- aibow (main, writable, git): D:\Go\Projects\aibow
- notes (read-only): D:\Docs\notes
OS: windows
...
```

- 確認のカードに、どのフォルダかを出す(メイン以外のとき)
