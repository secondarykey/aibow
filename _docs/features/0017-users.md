## 目的

**組織の人が、ほかの PC からブラウザやデスクトップアプリで aibow-server を使えるようにする**。
そのために、利用者とログインを入れ、会話・プロファイル・表示の設定を「その人のもの」に分ける。
デスクトップアプリは、ループとツールを手元で動かしたまま、生成と保存をサーバーに頼む(0013 の表の C)。

```
ブラウザ ──HTTPS(cookie のセッション)──→ aibow-server [ 画面用の口 → 会話の仕組み(ツールなし)→ engine ]
aibow.exe(ほかの PC)──HTTPS(API キー)──→ aibow-server [ 保存の口(Store)・生成の口 ]   ループとツールは aibow.exe の PC
Cline など ──HTTPS(API キー)──→ aibow-server [ OpenAI 互換の口 ]
                                              保存は server.db(利用者ごとに分ける)
```

学ぶこと:

- **「誰の会話か」を全部の口に通す**:今の `Store` は全部が自分の会話という前提。ログインした人を `ctx` で運び、保存・SSE・設定のすべてで「この人の」に絞る。
  **認証**(この人は誰か)と**認可**(この人は何をしてよいか)の違い。ステップ10は認証と「自分のものだけ」の認可まで、管理者などの認可はステップ11
- **ブラウザとアプリで認証の形が違う**:ブラウザは cookie のセッション(サーバーが「ログイン済み」を覚える)、アプリと Cline は API キー(`Authorization: Bearer …` を毎回送る)。
  ステートレスな OpenAI 互換の API(毎回全部を送る)と、サーバーが覚えるセッションの対比
- **パスワードの保存**:パスワードそのものではなく、塩(salt)を付けて何度もハッシュを重ねた値を保存する理由
- **C の形**:HTTP を越えるのは画面の呼び出し(B の `ui.Service`)ではなく、保存の約束(`Store`)と生成(`Generator`)になること

## 決定事項(ユーザーと決めたこと。2026-10-22)

1. **ログインは自前のアカウント(名前とパスワード)。アプリと Cline は利用者ごとの API キー**
   - パスワードは標準ライブラリの `crypto/pbkdf2`(Go 1.24 で標準に入った)でハッシュにする。bcrypt / argon2 は `golang.org/x/crypto`(外部パッケージ)なので使わない
   - 組織の SSO(OIDC)はこのステップでは作らない。ログインの口を差し替えれば後から足せる形にしておく
2. **127.0.0.1 以外で待ち受けるときは、ログインを必須にする。証明書のファイルを指定すれば HTTPS で待ち受ける**(標準の `net/http` の TLS)
   - 待ち受けのアドレスは設定(`server.json`・引数・環境変数)で広げる。既定は今のまま 127.0.0.1
   - 自己署名の証明書の作り方を手順(またはコマンド)で用意する。ブラウザの警告が出ることは `_docs/setup.md` に書く
   - 証明書なしで 127.0.0.1 以外に出すときの扱い(断るか、警告して HTTP で動かすか)は Code が案を示す(未決事項)
3. **アプリは serverUrl(と API キー)を書いたら、生成も保存も aibow-server**。手元の DB(`aibow.db`)は直接の形のときだけ使う
   - 手元の DB の会話はサーバーに移さない。直接の形に戻せば見える
   - ループとツールは今のまま手元で動く。**ツールの結果(手元のファイルの中身・コマンドの出力)もサーバーの DB に入る**ことを `_docs/usage.md` に書く

## 決定事項(話の流れから Chat が決めて書いたこと。2026-10-22 にユーザーが確かめた)

4. **管理者は作らない**(ステップ11)。ステップ10では、サーバーの PC で aibow-server のコマンドを打てる人が実質の管理者
   - 利用者は aibow-server のコマンドで作る・消す・パスワードと API キーを作り直す(例: `aibow-server user add <名前>`。形は Code が決める)

5. **プロファイルは人ごと**。利用者を作ったら、その人のプロファイル「既定」を作る(今の `PrepareProfiles` と同じ)。人をまたいで配るのは「共有の作業」(ステップ11)
6. **表示の設定(明るさ・質問の写しなど)は人ごと**。サーバー全体の設定(`AppSetting`)と、人ごとの設定を分ける
7. **SSE はその人にだけ送る**(0016 の決定事項 14 で持ち越したこと)。同じ人の別のタブ・別の PC には送る(一覧の取り直しに使える)
8. **127.0.0.1 だけで待ち受けるときは、ログインなしでも今のまま動く**(利用者1人)。設定で「ログイン必須」にもできる
   - 今ある会話・プロファイルは、最初の利用者(ログインなしの形の利用者)のものにする(DB の版を上げる)
9. **OpenAI 互換の口と aibow 専用の口も API キーで守る**。127.0.0.1 以外では必須、127.0.0.1 だけでログイン必須でなければ今のままキーなしで通す
10. **保存先は SQLite のまま**(数人〜数十人を想定。`Store` の interface なので後で替えられる)
11. **画面用の口(`/aibow/ui/…`)と、C の保存の口は別にする**
    - 0016 の決定事項 3 では「画面用の口を C の口に育てる」としていた。だが C はループが手元にあるので、HTTP を越えるのは `ui.Service` の呼び出しではなく `Store` の操作になる
    - `Store` の HTTP 版を `api/client` に足し、aibow-server に保存の口を足す(場所と形は Code が決める。例: `/aibow/store/…`)
    - 画面用の口(ブラウザ = B)はそのまま。同じ server.db を両方から使うので、アプリで作った会話をブラウザで見られる
12. **ログインした人は `ctx` で運ぶ**(0013 の気づき)。`ui.Service` のメソッドに `ctx` を通す。利用者の印を付けるのは aibow-server の HTTP の層だけ(偽れない)

## 10-0 で決めたこと(Code が決めて書いた。2026-10-23)

動きは変えない下ごしらえ。ログインはまだ無いので、利用者はいつもログインなしの形の利用者(`LocalUser`)。仕組みは [../conversations.md](../conversations.md) の「持ち主」。

- **利用者は `ctx` で運ぶ**(決定事項 12):`aibow.WithUser` / `aibow.UserOf`(`user.go`)。`Store` のメソッドは全部 `ctx` を最初に受け取り、`ctx` の利用者のものだけを読み書きする。
  会話の仕組み(`Conversations`)と `ui.Service` のメソッドも `ctx` を受け取って渡すだけ。Wails は最初の引数の `context.Context` を画面の関数に出さないので、画面とバインディングの呼び出しは変わらない
  - `ctx` には、保存先が HTTP の向こうになったとき(10-3)に止める役目もあるので、利用者を別の引数にせず `ctx` 1つにまとめた
- **利用者を入れるのは一番外だけ**:aibow-server の画面用の口は `ui.Handler(s, ev, who)` の `who` で決める(`ui.Who`。今はいつも `LocalUser`。10-1 でセッションの人に替える。決められなければ 401)。
  起動のときの引き継ぎ(`PrepareProfiles` など)は、利用者を分ける前の会話のためのものなので `LocalUser` として行う
- **利用者の無い `ctx` は保存先が断る**(`aibow.ErrNoUser`)。印を付け忘れたときに、黙ってほかの人の会話を見せないため。
  デスクトップのアプリの aibow.db だけは `store.SQLite.OneUser()` で、利用者の無い `ctx` を `LocalUser` として扱う(使うのはその PC の1人で、印を付ける HTTP の層が無い)
- **`LocalUser` は決まった ID**(`00000000-0000-7000-8000-000000000001`)。DB の作り変えの SQL にも同じ値を書くため。10-1 で利用者の表を作るときも、この ID の人を「最初の利用者」にする
- **DB の版 6**(決定事項 8):`conversations` と `profiles` に `owner`、人ごとの設定の表 `user_settings`。今ある会話・プロファイル・表示の設定は `LocalUser` のもの。
  利用者の表はまだ作らない(10-1)ので外部キーにしない。発言と要約は会話を通して持ち主を確かめる(列を足さない)。ほかの人の会話の ID を渡されたら、無い会話と同じに扱う
- **人ごとの設定とアプリ全体の設定**(決定事項 6):人ごと = 表示の設定(`pin_question`・`theme`)と、新しい会話で最初に選ばれるプロファイル(`default_profile`。プロファイルが人ごとなので)。
  アプリ全体 = モデルと GPU の層数(`last_model`・`gpu_layers`・`model_gpu_layers`)。`Store` に `UserSetting` / `SetUserSetting` を足した
- **新しい会話で最初に選ばれるプロファイルを覚えておかない**:前は `Conversations` が1つ覚えていたが、人ごとに違ううえ、同じ人がブラウザとアプリの両方から変えることがある(10-3)ので、そのつど保存先から読む(`DefaultProfile(ctx)`)
- **停止しても保存する**:保存先の呼び出しに `ctx` を渡すようにしたので、停止ボタンで止まった `ctx` のままでは、そこまでの返事を保存できなくなる。
  保存(発言・要約)と、そのあとのメーターの読み直しには `context.WithoutCancel(ctx)` を渡す(利用者は残り、止める合図だけ外れる)
- **GPU の層数は aibow.db のまま**(未決事項。2026-10-23、ユーザーと決めた):aibow.db は直接の形のときだけ使う(決定事項 3)ので、ファイルに移さない。
  aibow-server につなぐ形では、層の数はサーバーの PC の `server-models.json` に覚え(0015 の 9)、サーバーの DB には入らない
- テスト:持ち主で分かれること・利用者の無い呼び出しを断ること・版 5 からの作り変え(`store/sqlite_test.go`)、画面用の口で利用者ごとに見えるものが分かれること・401(`ui/web_test.go` の `TestWebUsers`)

## 10-1 で決めたこと(2026-10-23。見た目・ログアウト・セッション・パスワードはユーザーと決めた)

127.0.0.1 のまま、ブラウザの画面にログインを入れた。仕組みは [../api.md](../api.md) の「ログイン」、使い方は [../usage.md](../usage.md) の「ログインと利用者」。

- **`auth` パッケージ**を新しく作った(認証だけ。ルートの `aibow` を import しない):パスワードのハッシュ(`password.go`)・セッション(`sessions.go`)・ログインの口と cookie(`http.go`)。
  保存の約束 `auth.Store` は、会話の `aibow.Store` とは別(利用者を扱うのは aibow-server だけなので)。実装は `store/users.go`(server.db)
- **パスワード**(決定事項 1):`crypto/pbkdf2`(PBKDF2-HMAC-SHA256・60 万回・16 バイトの塩)。保存の形は `pbkdf2-sha256$回数$塩$値`。比べるのは決まった時間(`subtle.ConstantTimeCompare`)。
  いない名前でも同じだけ時間をかけ、エラーは「名前かパスワードが違います」の1つ(いる名前を探られないように)
- **パスワードは aibow-server が作る**(ユーザーと決めた):`user add`・`user passwd` で 16 文字(4 文字ずつ `-` で区切る。見間違えやすい 0/o・1/l/i は使わない)を作り、標準出力に一度だけ出す(ログには残さない)。
  自分で打つ形にしなかったのは、標準ライブラリだけでは打った文字が画面に出てしまうため(隠すには `golang.org/x/term` が要る)
- **利用者のコマンド**(決定事項 4):`aibow-server [-config …] user list|add|passwd|remove [名前]`。llama.cpp を読み込まずに server.db だけを開く。
  `add` はその人のプロファイル「既定」も作る(決定事項 5。`PrepareProfiles` をその人として呼ぶ)。`passwd` はその人のセッションを全部消す。`remove` はその人の会話・プロファイル・設定も消す。名前は 1〜32 文字で、空白と見えない文字は使えない
- **ログインなしの形の利用者**は、利用者の表に名前 `local`・パスワード空で入れた(DB の版 7)。消せない。ログインが要る形でも今までの会話を使うときは `user passwd local`
- **セッション**:合言葉(32 バイトのでたらめな値)を cookie `aibow_session` で渡し、server.db には SHA-256 だけを保存する。
  cookie は `HttpOnly`・`SameSite=Strict`・(HTTPS なら)`Secure`。期限は**最後に使ってから 30 日**(ユーザーと決めた)。延ばすのは前に延ばしてから1日以上たったときだけ(毎回 DB に書かない)。期限の切れたセッションはログインのときに片付ける
- **ログインが要るか**(決定事項 8):`-login`・`server.json` の `login`・`AIBOW_SERVER_LOGIN`。既定は要らない(127.0.0.1 だけなので)。要らない形では、ブラウザはいつも `local`
- **利用者を決めるのは aibow-server の `browser.go` の `who` だけ**(決定事項 12):`auth.Middleware` が cookie からログインした人をリクエストの ctx に入れ、`who` がそれを `ui.Who` として返す。いなければ 401
- **ログインの口**は `/aibow/auth/`(`me`・`login`・`logout`)。ログインの本文は JSON だけ受け付ける(ほかのサイトのフォームから、知らないうちにログインさせられないように)
- **SSE はその人にだけ送る**(決定事項 7):`ui.Notifier.Chat` が ctx を受け取り、`ui.Events` は画面ごとに利用者を覚えて、会話の持ち主の画面にだけ送る(同じ人の別のタブ・別の PC には送る)。モデルの読み込みの知らせは全員に送る。
  「要約だけ止める」(`StopSummary`)も、ctx の利用者の会話の要約だけを止める
- **ログインの画面**(ユーザーと決めた):画面の中央に「AIBow」・名前・パスワード・ログインのボタンだけ。間違えたら下に赤い文。使っている途中で期限が切れたら(呼び出しが 401)、ログインの画面に戻し、ログインしたら画面を読み直す
- **ログアウト**(ユーザーと決めた):会話の一覧の下(AIBow とバージョンの行)にログインしている人の名前を出し、押すと上に「ログアウト」。ログアウトしたら画面を読み直す(ログインの画面になる)。ログインが要らない形とデスクトップのアプリでは出さない
- 確かめたこと(2026-10-23。qwen3.5:4b・一時フォルダの server.json でポート 8091・ログインが要る形):利用者を2人作り、curl で「ログインの前は 401・違うパスワードは 401・ログインすると自分の会話だけ見える・ほかの人の一覧は空・ログアウトで戻る」を、
  ブラウザで「ログインの画面・違うパスワードの赤い文・ログインして送信し、返事が SSE で届く・一覧の下の名前からログアウトするとログインの画面に戻る」を見た
- まだしていないこと:ログインを何度も間違えたときの制限(試す回数を絞る)はしていない。127.0.0.1 の外に出す 10-2 のときに考える
