# 0016: ブラウザからも使う(aibow-server が画面を配る)

- 状態: ✅ 完了(2026-10-22)
- ロードマップ: ロードマップ2 ステップ 9
- 決めた日: 2026-10-22(Chat でユーザーと決めた)

- 関係する資料: brender の `_docs/server-transport.md` と Skill `brender-server-mode`(Wails の Transport を差し替えてブラウザに出す形)。
  **この仕様ではその形は使わない**(下の「決定事項」の 1)が、長い呼び出し・停止・SSE などの気づきは使える(0013 の「aibow で気をつけること」)

## 目的

**組織の人が aibow を入れなくても、ブラウザから使えるようにする**(2026-10-22、ユーザー)。
ステップ9では、その土台として、aibow-server が画面を配り、ブラウザから会話できるところまで作る(ほかの PC から使うのは、ログインと一緒にステップ10で)。

```
ブラウザ ──HTTP──→ aibow-server.exe [ 画面を配る・画面用の口 → 会話の仕組み → engine → llama.cpp → GPU ]
                                      会話の保存(aibow-server の DB)       ↑ 順番待ちの席は1つ
Cline など ──HTTP──→ aibow-server.exe [ OpenAI 互換の口(今のまま)] ─────────┘
aibow.exe(画面のアプリ)は今のまま(直接でも aibow-server 越しでも)。会話はアプリの DB
```

0013(2026-10-19)では「デスクトップアプリが Wails の Transport の差し替えでブラウザにも配る」としていた。
そのあとステップ8で aibow-server がサーバー役になったので、**ブラウザは aibow-server につなぐ**形に変えた(2026-10-22、ユーザーと決めた)。
画面のアプリが「aibow-server のクライアント」になっていく線(ステップ10の C)とそろう。

学ぶこと:

- **画面と Go のやり取りを、自分で HTTP の口にする**:今は Wails が仲立ちしている(メソッドの呼び出し・返事が流れてくるイベント・停止)。
  それをネットワーク越しに自分で書くと、Wails が裏で何をしていたかが見える
  - メソッドの呼び出し → HTTP のリクエストと返事(エラーの返し方も)
  - 返事が流れてくるイベント(`ChatEvent`)→ サーバーから送り続ける(SSE)
  - 停止ボタン → リクエストを取り消すと、サーバーの `ctx` が止まる
- **会話の仕組みがサーバーで動く**(0013 の表の B):ループと保存がサーバーにあると、ツール(手元で動くもの)が使えなくなること
- 1つの GPU を、ブラウザの会話と Cline などで取り合うこと(順番待ちの席・モデルの読み直し)

## 決定事項(ユーザーと決めたこと。2026-10-22)

1. **ブラウザは aibow-server につなぐ**。画面のアプリ(aibow.exe)はブラウザに配らない
   - AGENTS.md の「画面のアプリは HTTP サーバーを立てない」はそのまま
   - Wails の server モード(`-tags server`)は使わない。aibow-server に Wails を入れない(Wails は `_cmd/aibow` だけで使う方針のまま)
2. **画面の部品は、アプリとブラウザで同じものを使う**(ユーザーの条件)
3. **画面用の HTTP の口を、aibow-server に自分で作る**
   - 画面には「Go を呼ぶ係」を1か所作り、部品はその係だけを呼ぶ。デスクトップでは中で Wails のバインディングを、ブラウザでは fetch と SSE を使う
   - この口は、ステップ10で画面のアプリが会話をサーバーに置くとき(C)の口に育てる(「aibow がサーバーで、画面のアプリはそのクライアント」の形。2026-10-22、ユーザー)
4. **ブラウザの会話は aibow-server の DB に保存する**。画面のアプリの DB とはステップ9では別のまま
   - 2つをまとめるのはステップ10(C)
5. **ステップ9は 127.0.0.1 で待ち受けるところまで**。ログインと、PC の外(LAN)から使うのはステップ10
   - ステップ8で決めた「認証が無いまま LAN に出さない」のまま。それまでほかの PC から試すなら SSH のポート転送(`ssh -L 8089:127.0.0.1:8089 …`)
6. **ブラウザでは、サーバーの PC の事情を見せも変えもしない**(0015 の決定事項 21・23 の、サーバー越しの画面のアプリと同じ線)
   - 見せない・変えない:モデルを読み込む / 降ろす・GPU の層数・置き場所・モデルの出どころ・サーバーの PC のパス・ツールと MCP・作業フォルダ
   - 見せる:モデルの一覧(名前・大きさ・読み込み中か)・作業領域の大きさ。会話のモデルは選べる(送信のときにサーバーが読み直す。今のサーバー越しの画面と同じ)
   - 理由:ブラウザの人はサーバーの PC の持ち主ではない(ステップ10で本当にそうなる)
7. **ブラウザではツールを使わない**(TODO で決めていたこと)
   - aibow-server の会話の仕組みにはツールを渡さない(組み込みのツールも MCP も)。なので、実行前の確認の往復をネットワークで流す仕組みも作らない
   - サーバーの上でツールを動かすのはステップ12(必要になったら)
8. **名前は aibow-server のまま**(ユーザーは「どちらでもよい」。ステップ8で付けたばかりで、Cline などの設定にも出ているため。Chat が決めた)

13. **aibow-server の DB は、アプリの DB(`aibow.db`)とは別のファイル**にする。同じ PC でアプリと aibow-server を同時に動かす(ステップ8の形)ため。
    名前は Code が決める。置き場所は `server-models.json` と同じ考え方(既定は `%APPDATA%\aibow\`、`-config` のファイルの隣)。
    初めて起動したときはプロファイル「既定」を作る(アプリと同じ `PrepareProfiles`)
14. **送信は今と同じく「生成が終わるまで返らない長い呼び出し」にする**。経過(`ChatEvent`)は SSE で流す
    - 停止はリクエストの取り消し(ブラウザで fetch を止める → サーバーの `ctx` が止まる)。Wails の今の動き(呼び出しの取り消し)と同じ意味にそろえる
    - 書き込みの時間の上限(`WriteTimeout`)は付けない(今の aibow-server と同じ)
    - SSE は、ステップ9ではつないでいるブラウザ全部に送る(利用者は1人)。その人にだけ送るのはステップ10(0013)
15. **表示の設定(明るさ・質問の写しなど)は、ステップ9では aibow-server の DB に1つ持つ**(利用者が1人なので)。人ごとにするのはステップ10

## 9-0 で決めたこと(Code が決めた。2026-10-22)

決定事項の 9 で「名前と線の引き方は Code が決める」としたもの。

- **パッケージはルートの `ui`**(`github.com/secondarykey/aibow/ui`)。画面から呼ぶメソッドの中身(`ui.Service`)と、モデルを扱う係(`ui.ModelHost`。直接 `DirectHost`・aibow-server 越し `RemoteHost`)、

  - `ModelHost` のメソッドは小文字のままにして、`ui` の外では作れないようにした(形は2つだけ)。9-1 で aibow-server 用の形が要れば、そのとき開く
- **`ChatService` は `*ui.Service` を埋め込むだけ**。Wails は埋め込んだ型のメソッドも `ChatService` のメソッドとしてバインディングにする(生成も実行も)ので、
  画面から見た名前と ID(`main.ChatService.Send` など)は変わらない。変わったのは、戻り値の型(`ModelsResult` など)の置き場所が `bindings/…/ui` になったことだけ
  - `ChatService` に残したのは Wails が要るものだけ:起動と終了の合図(`ServiceStartup` / `ServiceShutdown`)・ダイアログ(`ChooseWorkDir` / `ChooseModelPlace`)・Wails のイベントで知らせる係
  - 起動と終了で呼ぶもの(起動時のモデルの読み込み・生成を止める)は `ui.New` が返す `ui.Lifecycle` に置いた。`Service` のメソッドにすると画面から呼べてしまうため(`modelLoader` と同じ考え方)
- **Go から画面に知らせる係は `ui.Notifier`**(`Chat(ev)` と `ModelLoaded()`)。デスクトップは Wails のイベント(`wailsNotifier`)、ブラウザは SSE(9-1)。イベントの名前は `ui.ChatEventName` / `ui.ModelsEventName`
- **画面の「Go を呼ぶ係」は `frontend/src/backend.ts`**。部品は `ChatService`(名前は Go と同じ)・イベントを受け取る `onChat` / `onModelLoaded` / `onWindowFocus`・止められる呼び出し `Call` と `isCancel` を、ここから使う
  - Wails のランタイムに頼るもの(クリップボード `copyText`・リンク `openURL`・ウィンドウの操作 `appWindow`)も、ここに集めた(決定事項の 17 の分かれ道を、9-2 でこのファイルだけに書けるように)。
    `@wailsio/runtime` とバインディングの呼び出しを import するのは `backend.ts` だけ
  - Go の型(バインディングの `models.ts`)は、部品から直接 import したままにした。`-i` で生成した interface と enum だけで、Wails の呼び出しの仕組みを含まないので、ブラウザでもそのまま使える
- 確かめたこと:`gofmt`・`go test ./...`・`wails3 build`・`go vet`。一時ビルド(CDP)で、直接(起動時のモデルの読み込みと models イベント・送信・停止・最大化と戻す・設定の画面のモデルのタブ)と

- **画面用の口の場所と形**:`/aibow/ui/` の下。OpenAI 互換の口(`/v1/`)と aibow 専用の口(`/models` など)は今のまま
  - `POST /aibow/ui/call/{メソッド}`:本文は引数の JSON の配列、返事は戻り値の JSON。Wails の呼び出し(メソッドの名前と引数の配列)と同じ形にして、Wails が裏でしていることと見比べられるようにした
  - `GET /aibow/ui/events`:SSE。`event: chat`・`event: models`(Wails のイベントと同じ名前)。つないでいるブラウザ全部に送る(決定事項の 14)
  - 呼べるメソッドは `ui/web.go` の `browserMethods` だけ。ツールと MCP・確認の答え、GPU の層数・降ろす・置き場所は口に出さない(決定事項の 6・7。`ServerHost` も断るが、口にも出さない)
- **DB は `server.db`**(`server.json`・`server-models.json` の隣。`-config` で設定ファイルを指せば、その隣)。初めて起動したときにプロファイル「既定」を作る(`ui.New` の中の `PrepareProfiles`)
- **席**:api の順番待ちの席を `api.Seat` として外に出し、ブラウザの会話も同じ席を使う(決定事項の 11)
  - 送信の全体(会話のモデルの読み直し・要約・返事)の間、席を持つ。生成1回ごとに取り直すと、その間に Cline などがモデルを入れ替えてしまうため
  - ふさがっていれば、chat の `notice` で「ほかの生成が終わるのを待っています…」を送ってから待つ(画面はトーストで出す)
  - 入力欄の下でモデルを選んだとき(`SwitchModel`)も席を取ってから読み込む。そのため `SwitchModel` は ctx を受け取るようにした(Wails は ctx をバインディングに出さないので、画面からの呼び方は変わらない)
- **モデルを扱う係 `ui.ServerHost`**:aibow-server の engine を直接使う。作業領域は作り直さず、入るかを確かめるだけ(決定事項の 12。`api/client` と同じ `ContextError`)。
  見せ方は aibow-server につないだ画面のアプリ(`RemoteHost`)と同じにし、`server()` に aibow-server のアドレスを返す。
  画面はそれを見て「サーバー越し」の見せ方(モデルのタブはつなぎ先と作業領域だけ・降ろすや層の数を出さない)になるので、決定事項の 6 の多くは今の画面のままで満たせる見込み(9-2 で確かめる)
- **ツールなし**:`ui.Options.WithoutTools` で空のツールの係を渡す。会話の仕組みは、ツールの係を渡さないと組み込みのツールを直接使うため(渡さないだけでは足りない)
- **新しい会話の既定**(システムプロンプトなど)は `ui.InitialAppSettings` にまとめ、画面のアプリと同じにした。環境変数(`AIBOW_HISTORY_TOKENS`・`AIBOW_MAX_TOKENS`・`AIBOW_PRESENCE_PENALTY`)も同じ
- SSE の細かいところ:最初に `: connected`(受け取る側に入ってから送る。逆だと、その間の知らせを取りこぼす)、15 秒ごとに `: ping`。
  1つのブラウザに 1024 件溜まったら、そのつながりを切る(黙って捨てると、答えの途中が抜けたまま気づけないため。ブラウザはつなぎ直す)
- 確かめたこと:
  - `httptest` のテスト(`ui/web_test.go`。モデル不要):呼べるメソッドと呼べないメソッド・引数の誤り・作業領域に入らないとき・送信と SSE・会話のモデルの読み直し・停止(fetch を止める)・席の順番待ち・ツールを知らせないこと
  - 本物のモデル(qwen3.5:4b・9b)で、curl から:送信と SSE で答えが流れる・Cline の形のリクエスト(9B)を送っている間にブラウザから送ると「待っています」が届き、そのあと 4B に読み直して答える・
    aibow-server を起動し直しても会話が残る。aibow-server につないだ画面のアプリ(一時ビルドの CDP)で、モデルの選択と送信が今までどおり動く
  - 2回目の質問で KV キャッシュの再利用が 0 になるのは、画面のアプリと同じ(公式テンプレートが前の思考を捨てるため。[tuning.md](../tuning.md))

  - ブラウザでは `@wailsio/runtime` を読み込まない。読み込むと、ページ全体の右クリックのメニューを消す(Wails の `--default-contextmenu`)など、デスクトップ向けの動きが入るため

- **ブラウザでの分かれ道**(決定事項の 17・18):タイトルバー(`TitleBar`)・入力欄の上の作業フォルダとツールの行・会話の設定とプロファイルの「ツール」を出さない。

  - モデルのタブは、Go の `ServerHost` がつなぎ先を返すので、aibow-server につないだ画面のアプリと同じ見せ方になった(一覧とつなぎ先・作業領域だけ)。分かれ道は要らなかった
- **SSE が切れたとき**(未決事項のまま):今は EventSource の既定の動き(自分でつなぎ直す。切れている間の経過は届かない)。どう見せるかは 9-3 でユーザーと決める
