- ロードマップ: ステップ 3(3-0 `tool` パッケージの切り出し / 3-1 読む / 3-2 書く・確認 / 3-3 コマンド)

## 目的

0004 のエージェントループに、作業フォルダの中のファイルを読む・書くツールと、コマンドを実行するツールを足し、
小さなコーディングエージェントにする。何かを書き換えるツールは、実行する前にユーザーに確認する。

学ぶこと:

- コーディングエージェントの中身は「読む → 直す → 動かす → 結果を見て直す」をツールで回すループだということ(0004 のループがそのまま使える)
- ツールの守り方は2種類あること。ファイルのツールは**仕組みで**作業フォルダの外に出られなくできる(Go の `os.Root`)。
  コマンドは何でもできるので、仕組みでは縛れず、**実行前の確認**が唯一の守りになる
- 確認が要る理由の1つは、ファイルの中身もモデルへの入力だということ(読んだファイルに「このコマンドを実行して」と書いてあれば、モデルはそれに従うかもしれない)
- ループを途中で止めて、ユーザーの返事を待つ仕組み(確認)
- ファイルを丸ごと書き直す方式と、文字列を置き換える方式の違い(4B での正確さ・トークン数・時間)
- ファイルの中身やコマンドの出力で、会話がどれくらい速く長くなるか(この後の 2-2 の比較につながる)

## 決定事項(ユーザーと決めたこと)

1. **3段に分けて作る**:3-1 作業フォルダと読むツール → 3-2 書くツールと実行前の確認 → 3-3 コマンド実行。仕様はこの1本、`TODO.md` の行を3つに分ける
2. **作業フォルダは会話ごとの設定**。画面でフォルダを選ぶ。決めていない会話にはファイルとコマンドのツールを出さない(時刻・計算だけ)
3. **確認するのは書くツールとコマンド**。読むツールは確認しない。
   **拒否したら「ユーザーが実行を拒否しました。理由: …」という結果をモデルに返し、ループは続ける**(0004 の「失敗しても送信は止めない」と同じ考え方。モデルに別のやり方を考えさせる)。拒否の理由はユーザーが一言書ける(空でもよい)
4. **ファイルの直し方は2つ**:`write_file`(丸ごと書く)と `edit_file`(古い文字列 → 新しい文字列の置き換え。古い文字列がファイルの中に1か所だけのときだけ置き換える)
5. **1回の送信で実行するツールの上限を 8 回から 20 回に上げる**(コーディングは回数がかさむため。停止ボタンがあるので困りにくい)
6. **`read_file` は行番号付きで、1回 200 行・8,000 文字まで**。開始行と行数を引数で指定できる。超えた分は切り、続きの読み方を書き添える。
   **`list_files` は下のフォルダまでたどり、500 件まで**。`.git` と `node_modules` は飛ばす
7. **今の組(最後のユーザーの発言から後ろ)だけで会話の上限を超えたら、今の動き(止めてエラー)のまま**にする。困るかどうかは 2-2 の比較のときに観察する
8. **確認の画面**:ツールのカードに「実行する / 拒否」のボタンと理由の欄を出す。
   `edit_file` は古い文字列と新しい文字列を並べ、`write_file` は新しい中身を全部見せる(すでにあるファイルなら「上書き」と出す)。行ごとの差分(diff)は作らない
9. **コマンドを動かすシェルは OS の標準のもの**:Windows は `cmd.exe`(どの Windows にも入っていて、Git Bash を入れていない人でも使えるため)。
   Windows 以外(クラウドセッションの Linux など)は `/bin/sh -c`
10. **3-1 の前に、ツールを `tool` パッケージに切り出す(3-0。動きは変えない)**。理由:
    - ステップ5の MCP サーバーはツールだけを外に出すプログラムで、ルートの `aibow` を import すると LLM(yzma)や会話の仕組みまで入ってしまう。ステップ4の MCP クライアントも「遠くのツールを `Tool` として見せる」ので、interface が独立しているほうが素直
    - ステップ3でツールが5つ増え、`os.Root` や OS ごとのファイル(`_windows.go` など)も入るので、ルートに置くと散らばる
    - 依存の向き(ツールは LLM を知らない、書式はツールの定義を知っている)が import として見え、仕組みが読みやすくなる
    - 0004 の仕様の「ツールはルートの `aibow` パッケージに置く」は、これで置き換える
11. **ほかの部分(`engine` / `format` / `models`)は今は分けない**。使う相手(ステップ6の OpenAI 互換 API など)が現れたときに分ける(`TODO.md` のロードマップの外に記録)。

### `tool` パッケージ(3-0)

### 作業フォルダとパス

- `ConversationSettings` に作業フォルダ(絶対パス)を足す。既定は空
- **「新しい会話の既定の設定」には入れない**(前の会話のフォルダを引き継いで、別のフォルダを書き換えてしまうのを防ぐため。会話ごとに毎回選ぶ)
- ファイルのツールは Go の標準ライブラリの `os.Root`(決めたフォルダの下しか開けないファイル操作の口)で作業フォルダを開いて使う。
  `..` やフォルダの外を指すシンボリックリンクで外に出ようとするとエラーになる。開くのはツールの呼び出しごとでよい
- パスは作業フォルダからの相対パスで書くよう、ツールの説明と環境の説明で伝える。作業フォルダの中を指す絶対パスも受け付ける(4B は絶対パスで書きがちなため)。外を指すパスはエラー
- 作業フォルダは会話ごとなので、ツールが「どの会話の作業フォルダか」を受け取れるようにする(今の `Tool.Run` は作業フォルダを受け取らない。渡し方は任せる)
- 作業フォルダが消えていたら、ツールはエラーの結果を返す

### 環境の説明(システムプロンプトに自動で足す)

ツールが ON で作業フォルダがある会話では、次のような数行を英語で足す(ツールの指示文が英語のため)。書式に関係ない情報なので、会話の仕組みの側で組み立てる。
置く場所は会話のシステムプロンプトの後ろ(0002 の要約より前。会話の中で変わらないので、KV キャッシュの再利用が効く位置)。

```
# Environment
Working directory: D:\Work\example
OS: windows
Shell for run_command: cmd.exe (use dir, type, findstr; ls, cat and grep are not available)
Use paths relative to the working directory.
```

- シェルの行は OS ごとに変える(Linux なら `/bin/sh`)。3-3 より前は、シェルの行を出さない

### 実行前の確認

- `Tool` に「実行前に確認が要るか」を持たせる。エージェントループは、確認が要るツールを実行する前に画面に確認を求め、返事を待つ
- 確認を待つ間は、ツールの時間の上限に数えない。停止ボタンで確認待ちも止まる(「停止」の結果を残す)
- 拒否・停止・上限で実行しなかった呼び出しにも、必ず結果を残す(0004 と同じ。次の送信の履歴が崩れないように)
- 確認の結果(実行した / 拒否した・理由)はツールの結果と一緒に保存し、再起動しても見えるようにする
- ログに確認の結果を出す

### コマンド(3-3)

- 時間の上限は 120 秒(`go test` の初回のコンパイルも収まるように)。0004 の 10 秒はほかのツールのまま。ツールごとに上限を持てるようにする
- 標準出力とエラー出力はまとめて返し、終了コードを付ける。長い出力は先頭と末尾を残して間を切る(エラーは末尾に出やすいため。合わせて 8,000 文字程度)
- 標準入力は空にする(入力待ちで止まらないように)
- **Windows**:Go の `os/exec` の説明にあるとおり、cmd.exe は引数の解釈のしかたが違うので、コマンドライン全体を自分で組み立てて `SysProcAttr.CmdLine` に入れる
- **Windows 以外**:`/bin/sh -c`。子プロセスもまとめて止められるよう、プロセスグループを分けて起動し、止めるときはグループごと止める(`syscall` の `Setpgid` と、負の PID への kill。標準ライブラリでできる)
- OS ごとに違う部分はビルドタグでファイルを分け(`_windows.go` など)、「どのシェルで動かすか」はその1か所にまとめる(あとからシェルを足しやすいように)
- 動作確認は Windows(ユーザーの環境)と Linux(クラウドセッション)で行う。macOS は確かめない(動くはずだが未確認と書いておく)

### 画面

- 会話の設定に作業フォルダを出し、フォルダを選ぶダイアログで決められるようにする。外すこともできる
- 新しいツールも 0004 と同じカードで出す。確認を待っているカードには「実行する / 拒否」と理由の欄を出す

## 調べてから決めること(Code が試して、結果を仕様に書き足す。決めにくければユーザーに相談)

- **Windows で停止したとき、子プロセスまで止まるか**:`cmd.exe` を止めても、そこから起動された `go` などが残ることがある(Go の `os/exec` の説明にも、残った子プロセスが出力のパイプを握ったままになる話がある)。

  `go` や `git` の出力はもともと UTF-8
