## 1. worktree での確認の付け方(2026-11-24 の相談。最初に考える)

### ユーザーの考え

**worktree では確認なしで編集させ、元のフォルダ(本体)へ直接書くときは確認する。**
worktree に書いたものは、取り込む前に差分の画面でまとめて見られるので、1つずつ聞く必要は無い。本体に直接書くときは取り消す場所が無いので聞く。

### 今の作り(2026-11-24、Chat がコードと 0039 を読んで確かめた)

- 0039 で、worktree の会話では `write_file`・`edit_file` の**決まりの既定**を「確認しない」にしている(`tools.go` の `defaultPolicy`。`worktreeWrites` の名前のときだけ)。
  `run_command` は今までどおり確認する(コマンドは worktree の外にも書けるため)
- つまり、ユーザーの考えの**大筋はもう入っている**。ただし穴が2つある

### 穴1:PC の既定で「確認する」にしていると、そちらが勝つ

扱いの決め方(`policyOf`)は「プロファイルの使えない → 管理者の禁止 → 会話の上書き → **PC の既定(`tools.json`)** → 決まりの既定」の順。
worktree の「確認しない」は一番下の決まりの既定なので、PC の既定で `write_file` を「確認する」にしていると、worktree の会話でも毎回聞かれる。
0039 では「会話・PC で `ask` にしていればそちらが勝つ」と決めて書いた(わざとそうした)が、ユーザーの考え(worktree なら聞かない)とは合わない。

ふだん(直接書く会話)のために PC で「確認する」にしている人ほど、worktree でも聞かれることになる。

### 穴2:ツールの名前だけで見て、書き込む先(`folder` の引数)を見ていない

worktree にするのはワークスペースの**メインのフォルダだけ**(0039 の決定事項 5)。ほかの書き込めるフォルダは今までどおり直接書く。
ところが「確認しない」はツールの名前(`write_file`・`edit_file`)で決まり、呼び出しの引数の `folder`(0035)は見ていない。
そのため、**worktree の会話で、メイン以外の書き込めるフォルダに直接書いても確認が出ない**。ユーザーの考え(本体に直接書くときは聞く)に反する。

### 案

- **案 A:呼び出しごとに、書き込む先で決める**(Chat のおすすめ):`write_file`・`edit_file` の呼び出しのたびに、`folder` の引数から書き込む先を解き、
  - 書き込む先が **worktree の中**なら確認しない
  - 書き込む先が**本体(worktree でないフォルダ)**なら確認する

  ツールの扱い(`off` / `ask` / `allow`)をツールの名前で決めたあとに、「worktree の中なら `ask` を `allow` に下げる」段を足す形になる。
  穴2はこれで閉じる。穴1は、PC の既定の「確認する」を、この段で下げてよいかで決まる(下の「決めること」)
- **案 B:今の名前での判定のまま、PC の既定より worktree を強くする**:穴1だけ閉じる。穴2は残る。メイン以外のフォルダが書き込めるワークスペースは多くないので困りにくいが、残るのは「気づかないうちに本体へ書く」穴なので、案 A がよい

### 決めること

- PC の既定で「確認する」にしたものを、worktree の中への書き込みでは**確認しない**に下げるか(ユーザーの考えに沿うなら下げる)。
  会話の上書きで「確認する」にしたものは、その会話でわざわざ選んだものなので下げない、が自然(未決)
- 確認のカードや会話の設定の画面に、なぜ聞かれなかったか(「worktree の中なので確認しません」)をどう見せるか。今の画面は名前ごとの扱いしか出していない(`ToolStates`)
- 0051 の「今後も同じ答えにする(この返事の間・この会話の間)」との関係:範囲の選択も今はツールの名前に効く。書き込む先で分けるなら、範囲の選択も分けるか(下の 2. と同じ問い)

## 2. worktree では、決めたコマンドだけ聞かずに通す(2026-11-24 の相談)

`run_command` は worktree の会話でも毎回聞く(コマンドは worktree の外にも書けるため)。
コードを書いたら `go build ./...`・`go vet ./...`・`go test ./...` で確かめるのは、作業の決まり(0041)でモデルに頼んでいることでもあり、毎回押すのは手間。

- **案**:worktree の会話では、決めたコマンド(`go test`・`go build`・`go vet`)だけ聞かずに通す。ほかは今までどおり聞く
- これは backlog の「[確認のカードの「今後も同じ」が何に効くか分かりにくい(コマンドごとの許可)](backlog.md#確認のカードの今後も同じが何に効くか分かりにくいコマンドごとの許可)」と同じ仕組み(コマンドの頭で許す)の上に乗る。
  コマンドごとの許可を先に決め、その「既定で許すコマンドの一覧」を worktree の会話だけに持たせる、という順が自然
- 決めること(コマンドごとの許可と共通):どこで区切るか(先頭の語・最初の2語・完全一致)・`&&` や `;`・パイプでつないだときの扱い・一覧を誰が決めるか(コードの既定 / PC の既定 / ワークスペースごと)
- 気をつけること:`go test` も `go build` も、テストのコードやビルドの手順(`go generate` は別だが、テストの中ではファイルも書ける)で worktree の外に書きうる。
  「worktree の中で動かす決まったコマンドは、取り込む前の差分で見られる範囲」とはっきり言い切れるわけではない。それを承知で許すかを決める

## 3. worktree の続き(0039 で作った。使ってみてから決める残り)

0039 の未決事項に残したもの:

- **取り込む前にアプリがビルドを走らせるか**:Go は worktree でもそのままビルドできる見込みだが、画面(`tsc`)は worktree に `node_modules` が無いので通らない。今はモデルに `run_command` で書かせる形のまま
- **本体の `HEAD` が worktree を作ったあとに進んだら、差分の画面で知らせるか**(取り込みは `base` との差分を当てるので、多くは当たる)
- **残った worktree の片付け**:アプリが落ちて結び付けだけ残った worktree や、結び付けの無い `.aibow/worktrees/` を、起動のときに `git worktree prune` するか
- ビルドの成果物が `.gitignore` で無視されていないと差分に出る(2026-11-04 の試し)
- メイン以外のフォルダの worktree(0039 の「やらないこと」。使ってみてから)。1. の穴2は、これを作れば別の形で閉じる

  差分の画面で知らせるだけにするか・違えば取り込めないようにするか・当てずにブランチ `aibow/<ID>` を残してユーザーがマージする形にするか

## 5. テストを実行して落ちたら直すループ

0041 では「アプリがループを回す」のは「やらないこと」にし、作業の決まり(`# Working rules`)でモデルに「最後に確かめる」と頼むだけにした。
0041 の試しで `go test` が通ったのは 7/8。残った失敗は、テストのほうを書き換えた・直さずに「もう書いてある」と答えた・同じエラーの繰り返し、など振る舞いのもの。

- アプリの側で回すなら:返事が終わったあとにアプリが決まったコマンド(`go test` など)を動かし、落ちたら結果を足して続けさせる、のような形。上の 2.(決めたコマンドを聞かずに通す)が前提になる
- 0039 で決めたユーザーの作業のイメージは「**コードを書くことに集中させ、動作の確認はユーザーがする**。コンパイルエラーが無い程度は確かめられるとよい」。どこまでモデルに回させるかは、このイメージと合わせて決める

## 6. コマンドが無いとき(2026-10-21、ユーザーと話した)

今は確認のカードを許可したあとで、シェルの「見つからない」(cmd.exe は終了コード 9009 のはず・sh は 127)がそのままモデルに返り、モデルが立て直す。

- 困ってから考える案:確認のカードに「PATH に見つかりません」と添える / 起動のときに git・go・node などを探し、見つかったものを環境の説明に書く(会話の上限を少し使う)
- git だけは、worktree(0039)で、PATH に無ければ worktree の切り替えを灰色にして理由を出すようにした(モデルの `run_command` は今までどおり)
