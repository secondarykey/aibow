# 会話の上限と compact

会話が長くなったときに、モデルに渡す履歴を会話の上限に収める仕組みの説明です。
決めた経緯と画面の動きは [features/0002-compact.md](features/0002-compact.md) にあります。

## ファイル

| ファイル | 役割 |
|---|---|
| `compact.go` | 会話の上限に収める仕組み(`none` / `truncate` / `summary`)、メーター(`Usage`)、今すぐ要約(`Compact`)と要約だけの停止(`StopSummary`)、要約の指示の文面 |
| `compact_test.go` | compact のテスト。1文字 = 1トークンで数える偽物の `fakeGen` を使う。モデル不要 |
| `elide.go` | 今の組の中の compact(0040)。1回の送信の中で、古い一歩のツールの結果と思考を省略して続ける(`elideOld`)。省略した発言をモデルに渡す形(`elideForModel`) |
| `elide_test.go` | 今の組の中の compact のテスト(`fakeGen`) |

## 上限

- 上限は「会話の上限(`history_tokens`)+ 返事の上限(`reply_tokens`)= 作業領域」。作業領域(`n_ctx`)は aibow が計算して確保する
- 上限は会話ごとの設定(会話を作るときに新しい会話の既定から写す。0009)。compact・メーター・生成の長さは、その会話の値を使う(`Conversations.limitsOf`)
- 作業領域はエンジンに1つだけ。送信と今すぐ要約の前に、その会話の大きさと違えば作り直す(`Conversations.ensureWorkspace` → `Engine.EnsureContextSize`)。
  画面のアプリを aibow-server につないでいるときは、作業領域はサーバーが起動のときに決めた大きさで固定で、作り直さない(0015 の 3)。
  `api/client` の `EnsureContextSize` は「会話の上限 + 返事の上限 ≤ サーバーの作業領域」を確かめるだけで、入らなければ理由と対処を返す。
  compact・メーターの基準は、どちらの形でも会話の上限(トークン数はサーバーが同じ書式で数える)
- 会話の上限に収まっているかは、実際にモデルに渡す文字列(テンプレート込み・要約込み)を `Engine.CountTokens` で数えて判断する。トークン数は保存しない(モデルで変わるため)
- 環境変数は `AIBOW_HISTORY_TOKENS`(新しい会話の既定の会話の上限)と `AIBOW_MAX_TOKENS`(同じく返事の上限)。`AIBOW_CTX` は 0002 で廃止(設定されていたらログとトーストで伝える)

## compact の方式

- どの方式でも DB の発言は消さない
- ユーザーが選んで「モデルに渡さない」にした発言(0011)は、compact の前に履歴から外れている(`forModel`)。truncate も summary も、外したあとの並びで行う。外した発言は要約にも入らない。すでに要約に入った発言は、外しても要約の中に残る
- truncate は保存せず毎回計算する
- summary は `compactions` 表に積み重ね、モデルに渡すのは最新の1件だけ(system の後ろ)
- 外す・要約するのは「ユーザーの発言 + 返事」の組ごと。ツールを使った送信の返事とツールの結果も同じ組に入る(組はユーザーの発言で区切る)
- none で上限を超える・最新の発言だけで超えるときは、発言を保存せずに生成前に止める
- ツールを使う送信では、2回目からの生成の前にも収まるかを確かめ(`checkFits`)、compact の準備を通す。今の組(最後のユーザーの発言から後ろ)だけで超えたら止める
  - ツールの結果を足すと今の組が上限を超えるときは、残りの 3/4 に入る長さで結果を切って渡し、切ったことと続きの取り方を書き添えて、ループを続ける
    (`agent.go` の `fitResult`。0025。read_file は行の切れ目で切って「続きは offset=N で読めます」。残りの 1/4 は、モデルが次に書く呼び出しや答えのために空けておく)。
    1行も入らないほど残りが無ければ、渡さずに「残りは約 M トークンしかありません」のエラーの結果にし、次の生成ではツールを見せずに、ここまでに分かったことで答えさせる。
    以前は結果をそのまま保存してから止めていたので、会話が上限を超えたまま残り、最新の組は要約しないため「今すぐ要約」もできなかった
  - それでも超えるのは、エラーの結果の文そのもの(1件 150 トークンほど)や返事で残りを使い切ったとき。そのときは今までどおり止める。
    最新の組は要約しないので、次の質問を送ると、その組が古い組になって送信の前に要約される(`TestCompactNowWhenLatestTurnIsTooLong`)
  - 「今すぐ要約」で要約するものが無いのは失敗ではないので、エラーではなくお知らせ(`notice` イベント。画面はトースト)で伝える。
    理由は2つ。最近の発言が上限の半分に収まっている(`errNothingToSummarize`)と、
    要約に入っていないのが最新の組だけで、それが半分を超えている(`errOnlyLatestTurn`。「次に送信すると要約の対象になる」と伝える)
- ツールを使う会話では、ツールの説明もトークン数に入る(メーターも同じ)
- 読み込んだファイル(0030)は、展開した文字のままトークン数に入る(メーターも同じ)。画像は画像トークン数(1 枚 1,024 まで)で入る。要約に渡すときは、中身ではなく「[ファイル: 名前]」・「[画像]」にする(`summaryMessages`)。
  重いうえ、要約に要るのは話の流れなので。truncate はファイルの付いた発言も、ほかの発言と同じく組ごと外す
- **作業の予定(update_plan。0037)は compact のあとも渡す**:渡さない部分(要約した・truncate で外した。`history[:first]`)に成功した `update_plan` があれば、
  その最後の予定を、システムの文の最後(要約の後ろ。truncate なら残した発言の前)に「Current plan (from update_plan in the earlier part of this conversation, which is no longer shown):」と項目で足す(`plan.go`)。
  足すのは `passFrom` なので、送信・メーター・truncate の位置探し・要約の前後の数え方のどれも同じ内容で数える。
  会話全体の最後の予定ではなく「渡さない部分の」最後の予定にするのは、モデルが予定を書き直すたびにシステムの文が変わって KV キャッシュが使えなくなるのを避けるため
  (渡す部分で書き直した予定は、履歴の中で足した予定より後ろに見えるので、新しいほうだと分かる)
- **今の組の中の compact(0040。`elide.go`)**:ツールを使う送信では、1回の送信(= 最新の組)の中で結果と思考が積み重なり、最新の組だけで上限を使い切る。
  そこで、今の組の中の「一歩」(返事1つ = 思考とツールの呼び出し + その結果)のうち古いものを縮めて渡す。truncate / summary の会話だけ(none は今のまま止める)
  - 縮め方:ツールの結果は札「(省略:会話の上限を空けるため、この結果はもう渡していません。元は約 N 文字。要るときは、もう一度呼んでください)」に置き換え、その一歩の返事の思考は空にする。
    ツールの呼び出し(名前と引数)は残す(update_plan の予定も引数に残る)。札より短い結果(200 文字以下。エラーや update_plan の結果など)はそのまま
  - 水位:今の組(`turnTokens`。システムプロンプト・ツールの説明を含む)が会話の上限の 3/4 を超えたら、古い一歩から順に 1/2 まで縮める。新しい 2 歩(今まさに使っている結果と、その一つ前)は縮めない。
    少しずつ縮めると、そのたびに縮めた一歩から後ろの KV キャッシュが使えなくなるので、まとめて縮めて回数を減らす。全部縮めても 1/2 まで下がらなければ、縮められるだけ縮める
  - 順番:ツールの結果を足す前に、足すと水位を超えるなら先に縮める → それでも入らなければ切る(`fitResult`)→ それでも駄目なら渡さない(`noRoomLeft`)。ループの2回目からの生成の前(`checkFits` の前)にも同じことをする
  - 縮めたことは、一歩の発言(返事と結果の全部)に印 `StoredMessage.Elided` を付けて保存する(`Store.SetMessagesElided`。印は外さない)。DB の文と思考は消さない(画面には全部残す)。
    札に置き換えるのは `promptMessages`(`elideForModel`)なので、`passFrom` を通る送信・メーター・truncate の位置探し・要約の前後の数え方は、どれも縮めた形で数える。
    上限で止まったあとに「続けて」と送っても、前の組は元の長さに戻らない(戻ると truncate なら組ごと外れ、summary なら大きな組を要約することになる)
  - 印は会話の方式によらず効く(縮めたあとで会話の設定を none にしても、縮めた形で渡す)。要約(`summaryMessages`)に渡すときは、今までどおり結果の先頭 200 文字(縮めた結果も同じ)
  - 知らせ:compact イベントの `Method` を `elide` にし、`Dropped` に札にした結果の数を入れる。画面は吹き出しの中(要約の知らせと同じ場所)に「古いツールの結果 N 件を省略して渡しました(X → Y トークン)」を出す。
    ログ(Info)には、縮めた一歩の数・前後のトークン数・うち思考と結果がそれぞれ何トークン減ったか(思考だけを空にした形をもう1回数えて分ける)を出す
- 送信の途中の要約中だけは `ChatService.StopSummary()` で要約だけを止められる(その回は truncate で返事に進む。仕様の「失敗したとき」)
- 要約の生成(`summarizePart` → `generateSummary`): 上限は会話の上限の 1/4・最低 1024(`summaryMaxTokens`)、指示で伝える字数はその半分(`summaryRunes`)、
  presence penalty は会話の設定の値、思考オフ、temperature 0.3。要約ごとに字数とトークン数をログ(Info)に出す(0002 の「使ってみて変えたこと」)
- 要約に失敗したとき(送信の途中)は、compact イベントの `Error` に「理由・代わりに truncate したこと・何度も続くときの対処」(`summaryFailHelp`)を入れる。
  画面は注意(赤ではない)として出し、途中まで書いた要約の文を畳んで残す(`ChatView.tsx` の `CompactNote`。`compactDraft`)
