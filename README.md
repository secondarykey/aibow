# aibow — 自作チャット(ステップ2-2: compact まで)

ローカルLLMを自分のプログラムの中で直接動かす、最小のチャットアプリです。
このアプリを少しずつ育てて、最終的に「ローカルでバイブコーディングできるエージェント」と「MCP」まで進みます。

```
ウィンドウ(_cmd/aibow/frontend の React) ⇄ Wails ⇄ aibow ⇄ 関数呼び出し ⇄ llama.cpp(_cmd/aibow/lib の DLL)⇄ GPU
                                                  ⇅                           ↑
                                  会話の保存(SQLite)   _cmd/aibow/models\*.gguf  または  Ollama が保存したモデル
```

画面は [Wails v3](https://v3.wails.io/) のデスクトップアプリです。Wails は OS に入っている WebView(Windows なら WebView2)で HTML の画面を出し、
画面の JavaScript から Go のメソッドを呼べるようにする枠組みです。画面は React + TypeScript で書き、Vite でビルドして実行ファイルに埋め込みます。
Go のメソッドを呼ぶための TypeScript の関数と型(バインディング)は、`wails3 generate bindings` が Go のコードから自動で作ります。

aibow が llama.cpp(LLM を計算するライブラリ)を直接読み込み、モデルの読み込みから1トークンずつの生成まで、自分で行います。
Ollama のサーバーは使いません。ただし、**Ollama で `ollama pull` したモデルはそのまま使えます**。
Ollama が保存したファイルを aibow が直接読むので、Ollama は起動していなくて構いません。
「モデルの管理は Ollama、動かすのは aibow」という分担です。

## ファイル構成

| ファイル | 役割 |
|---|---|
| `aibow.go` | パッケージの説明。リポジトリのルートは LLM を動かす部分(`aibow` パッケージ)で、画面のことは知らない |
| `engine.go` | llama.cpp を呼んで文章を生成する部分(モデルの読み込み・入れ替え、トークン化とトークン数を数えること、計算、選択の繰り返し) |
| `models.go` | 使えるモデルの一覧を作る(`models\` フォルダと Ollama の保存フォルダ) |
| `prompt.go` | 会話を、モデルが理解する書式(ChatML)の1本の文字列にする |
| `stream.go` | 生成された文字を「思考」と「答え」に振り分ける(文字の切れ目や、文字にならないバイトの扱いも) |
| `conversation.go` | 会話の仕組み。発言を保存し、送信のたびに履歴を並べ直してモデルに渡す(モデル自身は何も覚えていない) |
| `compact.go` | 長くなった会話を「会話の上限」に収める仕組み(古い発言を捨てる / 要約する)と、メーターの計算 |
| `store.go` | 会話の保存先の約束(interface)と、会話・発言・要約の形。会話の仕組みは保存先が SQLite かどうかを知らない |
| `appsettings.go` | アプリ全体の設定(会話の上限・返事の上限・GPU の層数・最後に使ったモデル・新しい会話の既定の設定) |
| `store/sqlite.go` | 会話・発言・要約を SQLite のファイルに保存する部分(テーブルの作り変え = マイグレーションもここ) |
| `*_test.go` | テスト(モデルなしで実行できる) |
| `_cmd/aibow/main.go` | デスクトップアプリの起動(Wails のアプリとウィンドウを作る) |
| `_cmd/aibow/config.go` | 環境変数から設定を読む |
| `_cmd/aibow/service.go` | 画面から呼ばれる Go のメソッド(モデル・会話・設定・メーター・送信・今すぐ要約)。会話の仕組みとの中継だけをする |
| `_cmd/aibow/frontend/src/` | チャット画面(React + TypeScript)。`App.tsx` が全体、`use*.ts` が Go とのやり取り、`components/` が表示 |
| `_cmd/aibow/frontend/bindings/` | `wails3 generate bindings` が作る、Go のメソッドを呼ぶ関数と型(自動生成。手で直さない) |
| `_cmd/aibow/build/` / `Taskfile.yml` | `wails3 dev` / `wails3 build` の設定(アプリ名、アイコン、OS ごとのビルド手順) |
| `_cmd/aibow/version` | アプリのバージョン(唯一の正)。exe に埋め込まれ、タスクバーなどに出るウィンドウ名に入る |
| `_cmd/version.go` | `version` の値を `build/config.yml` / `frontend/package.json` に書き写す・上げるスクリプト |
| `go.work` | ルートと `_cmd/aibow` の2つのモジュールをまとめる(下の説明を参照) |
| `_cmd/aibow/lib\` | llama.cpp の DLL(自分で取得。Git には入れない) |
| `_cmd/aibow/models\` | 自分でダウンロードしたモデル(Git には入れない) |

llama.cpp の呼び出しには [yzma](https://github.com/hybridgroup/yzma) という Go のライブラリを使っています。
llama.cpp の C の関数を Go から呼べるようにするだけの薄い層で、C コンパイラ(cgo)は不要です。
会話の保存には SQLite のドライバー [modernc.org/sqlite](https://pkg.go.dev/modernc.org/sqlite) を使っています。
SQLite の C のコードを Go に変換したもので、こちらも C コンパイラは不要です。

Wails に依存するのは `_cmd/aibow` だけです。`_cmd/aibow` は自分の `go.mod` を持つ別のモジュールにしてあり、
ルートの `go.mod` は yzma と SQLite のドライバーだけに依存します。`go.work` は「この2つのモジュールを一緒に扱う」という Go のワークスペースの設定で、
これがあるので、`_cmd/aibow` でビルドすると、ルートの `aibow` パッケージ(手元のコード)が使われます。
(`_` で始まるフォルダは `go test ./...` などの `./...` に含まれないので、ルートのテストは Wails なしで動きます)

## 準備(最初の1回だけ)

bash(Git Bash など)で、アプリのフォルダ `_cmd/aibow` に移動して作業します。
llama.cpp の DLL(`lib\`)とモデル(`models\`)は、モデルを動かすこのアプリの持ち物なので、アプリのフォルダに置きます。

```bash
cd /d/Go/Projects/aibow/_cmd/aibow
```
以降のコマンドは、すべてこのフォルダで実行します。

以前の版(ブラウザ版)でリポジトリのルートに `lib\` と `models\` を置いていた場合は、ダウンロードし直さなくても、
ルートの `lib\` と `models\` をフォルダごと `_cmd\aibow\` へ移せば準備の 3・4 は済みます。

### 1. 道具の確認

```bash
go version
```
Go のバージョンを表示します。標準の `uuid` パッケージ(会話や発言の ID を作る)を使うため、`go.mod` に `go 1.27.0` と書いてあります。
手元の Go が古い場合でも、Go が必要なバージョンを自動でダウンロードして使います(Go 1.21 以降の機能)。

```bash
node --version
```
Node.js のバージョンを表示します。画面のビルドに使う Vite が **Node.js 20.19 以上(または 22.12 以上)** を必要とします。
画面(React)のパッケージを入れる npm は Node.js に付いてきます。入っていなければ https://nodejs.org/ から入れてください。

```bash
go install github.com/wailsapp/wails/v3/cmd/wails3@v3.0.0-beta.26
```
Wails の CLI(`wails3` コマンド)を入れます。バージョンは `_cmd/aibow/go.mod` の Wails と合わせます。

```bash
wails3 doctor
```
Wails でビルドするのに必要なもの(Windows なら WebView2 など)がそろっているかを確認します。

### 2. 依存ライブラリの取得

```bash
go mod tidy
```
`_cmd/aibow/go.mod` に書いてあるライブラリ(Wails と yzma など)をダウンロードし、改ざん検知用のチェックサムを `go.sum` に書き出します。

```bash
cd frontend && npm install && cd ..
```
画面で使うパッケージ(React、Vite、Wails の JavaScript 用ランタイム、アイコンの react-icons など)を `frontend/node_modules/` にダウンロードします。
`wails3 dev` / `wails3 build` は `node_modules` が無いときだけ自動で `npm install` するので、パッケージを増減したときは手で実行します。

### 3. llama.cpp の取得

```bash
go run github.com/hybridgroup/yzma@v1.29.1 install --lib lib --processor cuda
```
yzma に付属しているインストーラーを、インストールせずにその場で1回だけ実行します。aibow のビルドとは無関係の、準備用の道具です。

- `go run パッケージ@バージョン` … 指定したプログラムをダウンロードしてビルドし、そのまま実行する
- `install` … llama.cpp のビルド済み DLL を GitHub からダウンロードする
- `--lib lib` … 置き場所。相対パスはコマンドを実行したフォルダが基準なので、`_cmd\aibow\lib\` にできる
- `--processor cuda` … NVIDIA GPU 用のビルドを選ぶ。CUDA の実行に必要な DLL(cudart)も一緒に入る

`go run パッケージ@バージョン` は今いるフォルダの `go.mod` / `go.work` を見ないので、`_cmd/aibow` で実行しても問題ありません。
バージョン(`@v1.29.1`)は、ルートの `go.mod` に書いてある yzma のバージョンと合わせてください。yzma と llama.cpp は組み合わせが決まっています。

GitHub の llama.cpp のリリースページから zip を手で落として `_cmd\aibow\lib\` に展開しても同じです。

### 4. モデルの用意

次のどちらでも構いません。両方あれば、両方とも画面の一覧に出ます。

**A. Ollama で管理する**

```bash
ollama pull qwen3.5:4b
```
Ollama がモデルをダウンロードして保存します。すでに pull 済みなら何もしなくて構いません。
aibow は Ollama の保存フォルダ(既定は `C:\Users\<ユーザー>\.ollama\models`、環境変数 `OLLAMA_MODELS` があればそちら)を見に行きます。

注意: Ollama のモデルの中には、Ollama 独自の形式になっていて llama.cpp では読めないものがあります。
読めなかった場合は画面にエラーが出て、元のモデルに戻ります。その場合は B の方法で GGUF を用意してください。

**B. GGUF ファイルを自分で置く**

GGUF は llama.cpp 用のモデルファイルの形式です。ダウンロードして `_cmd\aibow\models\` フォルダに置くだけです。例えば Qwen3.5 4B なら、次の URL をブラウザで開くとダウンロードが始まります(約3GB)。

https://huggingface.co/bartowski/Qwen_Qwen3.5-4B-GGUF/resolve/main/Qwen_Qwen3.5-4B-Q4_K_M.gguf

`Q4_K_M` は「重みを4ビット程度に圧縮したもの」という意味で、元のサイズの約1/4になり、VRAM 8GB に余裕で収まります。

## 起動

```bash
cd /d/Go/Projects/aibow/_cmd/aibow
```
アプリのフォルダに移動します。`lib\` と `models\` はカレントフォルダから探すので、必ずここで起動します。

```bash
wails3 dev
```
開発モードで起動します。中では次のことが順に行われます。

- Go のコードからバインディング(`frontend/bindings/`)を作り直す
- Go をビルドする(`bin/aibow.exe`)
- 画面の開発サーバー(Vite)を起動する。画面のコードを保存すると、ウィンドウにすぐ反映される
- アプリを起動する。`_cmd/aibow` の Go のコードを保存すると、ビルドし直して起動し直す

リポジトリのルートの `aibow` パッケージ(`engine.go` など)は見張っていないので、そちらを変えたときは `Ctrl+C` で止めて起動し直してください。
初回は Go のライブラリのダウンロードとビルドがあるので、ウィンドウが出るまでしばらくかかります。

起動すると、ターミナルに次のようなログが出ます(Wails 自身のログも混ざります)。

```
会話の保存先: C:\Users\<ユーザー>\AppData\Roaming\aibow\aibow.db
会話の上限 8192 + 返事の上限 8192 = 作業領域 16384 トークン
計算装置: CUDA0 [GPU] <GPU の名前>(VRAM 空き ○ / ○ GB)
計算装置: CPU [CPU] <CPU の名前>
モデルの置き場所: D:\Go\Projects\aibow\_cmd\aibow\models / Ollama: C:\Users\<ユーザー>\.ollama\models
  ollama   qwen3.5:4b                               ○ GB
  ollama   qwen3.5:9b                               ○ GB
aibow 起動
モデルを読み込み中: qwen3.5:4b (...)
読み込み完了 (○ 秒): <モデルの種類> / ○B パラメータ / ○ GB / ○ 層 / GPU に載せる層: 999 / 作業領域: 16384 トークン
```

ウィンドウが開きます。モデルはウィンドウが出てから裏で読み込むので、読み終わるまでは送信できません。
止めるときはウィンドウを閉じます(VRAM も解放され、`wails3 dev` も終わります)。生成中に閉じても、生成を止めてから終了します。

うまく動かないとき:

- ウィンドウに「起動できません: llama.cpp のフォルダが見つかりません: …」と出る場合は、表示されたフォルダに `lib\` がありません。
  `_cmd/aibow` で起動しているか、`AIBOW_LIB` の指定が正しいかを確認してください。環境変数の値が不正なときも、同じようにウィンドウに理由が出ます。
- `計算装置` に GPU が出てこない場合は、GPU 用ではない llama.cpp が入っているか、ドライバーが古い可能性があります(準備の3の `--processor cuda` を確認)。
- Ollama のモデルが一覧に出てこない場合は、ログの `Ollama:` の場所が正しいか確認してください。違う場所に保存しているなら、環境変数 `OLLAMA_MODELS` で指定します。

### 実行ファイルを作る

```bash
wails3 build
```
画面をビルドして埋め込み、アイコン付きの実行ファイル `bin\aibow.exe` を作ります。コンソールは出ません。

```bash
wails3 task run
```
`bin\aibow.exe` を、`_cmd/aibow` をカレントフォルダにして起動します。`bin\aibow.exe` をエクスプローラーからダブルクリックすると
カレントフォルダが `bin\` になり、`lib\` が見つかりません。その場合は、起動できない理由がウィンドウに表示されます
(`AIBOW_LIB` / `AIBOW_MODELS_DIR` を絶対パスで設定しておけば、どこから起動しても動きます)。
`bin\aibow.exe` はコンソールを持たないので、ログは出ません。ログを見たいときは `wails3 dev` で起動します。

### 自分の PC にインストールする(local:deploy)

普段使いの場所へ、バージョン管理込みでインストールします。
インストール先などのローカルの設定をリポジトリに残さないよう、`local:deploy` は各自の `_cmd/aibow/Taskfile.local.yml` に書きます。
このファイルは Git に入れません(`.gitignore` 済み)。`Taskfile.yml` が optional で読み込むので、無い環境でも他のタスクはそのまま動きます。

```bash
wails3 task local:deploy
```
`_cmd/aibow` で実行します。`Taskfile.local.yml` の `local:deploy` は、次のことを順に行う作りにしています。

1. 起動中の aibow を終了する(起動中の exe は上書きできないため)
2. 前回インストールしたバージョンのままなら、patch を1つ上げる(0.1.0 → 0.1.1)
3. `version` の値を、`build/config.yml`・`frontend/package.json`・`frontend/package-lock.json`・exe に焼き込むバージョン情報(`build/windows/info.json` など)に反映する
   (`go run _cmd/version.go` → `npm install --package-lock-only` → `wails3 update build-assets -name aibow -binaryname aibow`)
4. `wails3 build`
5. 3 で変わったファイルだけをコミットする(作業中の他の変更は巻き込まない)
6. コミットに `v0.1.1` のようなタグを打つ(push はしない)。どのコミットをインストールしたかが分かる
7. `bin\aibow.exe` と `lib\` をインストール先へコピーする(`lib\` は変わったファイルだけ)

インストール先の `aibow.exe` を起動すると、隣の `lib\` を使います。モデルは Ollama のものが使えます。
GGUF を自分で置く場合は、インストール先に `models\` を作って置くか、`AIBOW_MODELS_DIR` で指定します。

```bash
go run _cmd/version.go -bump
```
patch は自動で上がりますが、minor / major を上げたいときは、**リポジトリのルートで**これを実行してから `local:deploy` します。
上げ方を選ぶと、`version`・`build/config.yml`・`frontend/package.json` が書き換わります。

`Taskfile.local.yml` の変数(インストール先など)を一時的に変えたいときは、`KEY=値` で渡します(`wails3 task` は `--` の後ろの引数を受け取れないため)。

```bash
wails3 task local:deploy DEPLOY_DEST="D:/tmp/aibow"
```

### 起動時に落ちた場合

`GGML_ASSERT(...) failed` と出て落ちたことが一度ありましたが、同じ条件で10回起動し直しても再現しませんでした(原因は未特定)。
もう一度起きたら、llama.cpp 自身のログを出して起動し、落ちる直前のログと、そのとき動いていた他のアプリ(Ollama、ゲームなど)を記録してください。

```bash
AIBOW_LLAMA_LOG=1 wails3 dev 2>&1 | tee aibow.log
```
`2>&1` でエラー出力も含めて、`tee` で画面に出しつつ `aibow.log` にも保存します。

### モデルの切り替え

入力欄の下のドロップダウンで選ぶと、aibow が今のモデルを VRAM から降ろして、新しいモデルを読み込みます(数秒〜十数秒)。
モデルはアプリ全体で1つです(VRAM に1つしか載らないため)。会話を切り替えてもモデルは変わりません。
会話はそのまま続けられるので、同じ質問を 4B と 9B で比べる、といった使い方ができます。
回答の下の統計行の先頭に、どのモデルの返事かが表示されます(発言ごとに保存されています)。
最後に使ったモデルは保存され、次の起動で読み込まれます。

aibow を起動したまま `ollama pull` した場合は、aibow のウィンドウに戻ると一覧に出てきます(ウィンドウにフォーカスが戻るたびに一覧を作り直しています)。

### 会話の保存

会話は SQLite のファイル `%APPDATA%\aibow\aibow.db` に保存され、アプリを閉じても残ります。
起動したときと「+ 新規」を押したときは、入力欄が真ん中にある新しい会話の画面になり、最初に送ったときに会話ができます。
左の一覧で、会話の切り替え・削除ができます。タイトルは最初の発言の先頭から自動で付き、一覧でダブルクリックすると変えられます。
生成中に別の会話を開いて読むことはできますが、送信は生成が終わるまでできません(エンジンが1つのため)。

保存先は `AIBOW_DB` で変えられます。試しに動かすときに、普段の会話と混ぜたくない場合などに使います。

### 長い会話(compact)

モデルに渡すのは、これまでの会話を全部並べた1本の文字列です。会話が長くなると「会話の上限」に入りきらなくなるので、
会話ごとに選んだ方式で収めます(設定の画面の「会話が長くなったら(compact)」)。どの方式でも、保存した発言は消えません。

| 方式 | 何をするか |
|---|---|
| 要約する(summary、新しい会話の既定) | 最近の発言を会話の上限のおよそ半分まで残し、それより古い発言をモデル自身に要約させる。要約は前回の要約と一緒に作り直して積み重ねる |
| 古い発言を捨てる(truncate) | 古い発言から順に(ユーザーの発言と返事の組ごとに)、モデルに渡すのをやめる |
| 何もしない(none) | 上限を超えたら、生成する前に止まって知らせる |

- **メーター**: 入力欄の下の右端の `5,210 / 8,192` は、次の送信でモデルに渡す文字列のトークン数 / 会話の上限です。
  90% を超えると橙、上限を超えると赤になります。トークン数は保存せず、そのときのモデルで数え直します(モデルが変わると同じ文章でも変わる)
- **薄い表示**: 要約に入った発言や、truncate で外れた発言(モデルに渡していない発言)は薄く表示されます
- **区切り**: 要約した位置に「― ここまでを要約しました ―」が出ます。クリックすると、モデルに渡している要約の文と、要約前後のトークン数・かかった秒数が読めます
- **今すぐ要約**: summary の会話では、メーターの左のボタンで、上限を超えていなくても要約できます
- 要約を作っている間は、返事の吹き出しに要約の文が流れます。「要約を停止」で要約だけを止めると、その回は truncate で返事を生成します。
  要約に失敗したとき(答えが出なかった、途中で切れた、エラー)も同じで、理由が吹き出しに出ます

### 設定の変更

会話の一覧の下にある「設定」を押すと、チャットの代わりに設定の画面が開きます。
「会話に戻る」を押すか、一覧で会話を選ぶ・「+ 新規」を押すと閉じます。入力欄に打ちかけていた文は、戻ったときにそのまま残っています。

- **この会話の設定**(システムプロンプト・会話が長くなったら(compact)・temperature・presence penalty・思考する): 会話ごとに保存され、次の送信から効きます。
  「この設定を新しい会話の既定にする」で、これから作る会話の初期値になります
- **アプリ全体の設定**:
  - **会話の上限**(モデルに渡す、これまでの会話のトークン数の上限)と**返事の上限**(1回の返事で生成するトークン数の上限)。
    作業領域(コンテキスト)は、この2つの合計の大きさで確保します(パネルに計算した値が出ます)。
    変えると、モデルを読み直さずに作業領域(KV キャッシュの置き場)だけを作り直します
  - GPU に載せる層の数は、モデルを読み込み直します

環境変数でも変えられます。bash では `名前=値 コマンド` と書くと、そのコマンドにだけ渡せます(`export 名前=値` ならそのターミナルの中でずっと有効)。

| 環境変数 | 既定値 | 内容 |
|---|---|---|
| `AIBOW_MODEL` | 最後に使ったモデル → 一覧の先頭 | 起動時に読み込むモデル。`ollama:qwen3.5:4b` のような Ollama の名前か、GGUF ファイルのパス |
| `AIBOW_MODELS_DIR` | `models` | GGUF ファイルを探すフォルダ(相対パスはカレントフォルダが基準) |
| `OLLAMA_MODELS` | `%USERPROFILE%\.ollama\models` | Ollama の保存フォルダ(Ollama 自身と同じ変数) |
| `AIBOW_LIB` | `lib` | llama.cpp の DLL があるフォルダ(相対パスはカレントフォルダが基準) |
| `AIBOW_DB` | `%APPDATA%\aibow\aibow.db` | 会話を保存する SQLite のファイル。フォルダが無ければ作る |
| `AIBOW_HISTORY_TOKENS` | `8192` | 会話の上限(モデルに渡す、これまでの会話のトークン数の上限)。超えたら会話ごとの compact の方式で収める |
| `AIBOW_MAX_TOKENS` | `8192` | 返事の上限(1回の返事で生成するトークン数の上限。思考 + 答えの合計) |
| `AIBOW_GPU_LAYERS` | `999` | GPU に載せる層の数。VRAM に入りきらないモデルは減らす(残りは CPU で計算) |
| `AIBOW_PRESENCE_PENALTY` | `1.5` | すでに生成した言葉を選ばれにくくする強さ。思考の堂々巡りを抑える。`0` で無効 |
| `AIBOW_LLAMA_LOG` | なし | `1` にすると llama.cpp 自身の詳しいログ(どの層をどこに置いたか、読めない理由など)を出す。起動時に数千行出る |

作業領域(コンテキスト長)は「会話の上限 + 返事の上限」から計算します。増やすと長い会話ができますが、VRAM を使います(Qwen3.5 4B で 1 トークンあたり約 32KB)。
以前の `AIBOW_CTX`(コンテキスト長)は使わなくなりました。設定されていると、起動時にログと画面のお知らせで伝えます。

`AIBOW_HISTORY_TOKENS` / `AIBOW_MAX_TOKENS` / `AIBOW_GPU_LAYERS` / `AIBOW_PRESENCE_PENALTY` は、DB にまだ値が無いときの初期値です。
画面で一度変えると、DB に保存した値が優先されます(`AIBOW_PRESENCE_PENALTY` は新しい会話の既定の初期値になります)。
以前の版で保存したコンテキスト長があれば、`会話の上限 = コンテキスト長 − 返事の上限`(最低 2048)として引き継ぎます。

```bash
AIBOW_MODEL=ollama:qwen3.5:4b wails3 dev
```

Git の worktree など、別の場所にあるコードから起動するときは、`lib\` と `models\` は Git に入っていないので、本体の場所を指定します。
worktree に `lib\` / `models\` を入れ直す必要はありません。

```bash
AIBOW_LIB=/d/Go/Projects/aibow/_cmd/aibow/lib AIBOW_MODELS_DIR=/d/Go/Projects/aibow/_cmd/aibow/models wails3 dev
```

本体の `lib\` / `models\` へのジャンクション(フォルダの別名)は作らないでください。
worktree を消すツールによっては、ジャンクションの先(本体の `lib\` / `models\`)の中身まで消してしまいます。
`frontend/node_modules/` も Git に入っていないので、worktree の `_cmd/aibow/frontend` で `npm install` します。

## このステップで観察してほしいこと

- **長い会話(compact)**(このステップで足したもの)
  会話の上限を小さく(例えば 2048)して、同じ長い会話を truncate と summary で比べてみてください。
  truncate では外した発言の内容をモデルが完全に忘れます。summary では内容は残りますが、要約を作る分だけ待ち時間とトークンを使い、
  要約の質しだいで細部が落ちます。どちらも、モデルに渡す文字列の先頭が変わるので、KV キャッシュの再利用がほとんど効かなくなることも統計行で分かります。
  メーターの値が、compact の前後で下がるのも見えます。
- **会話を覚えているのはアプリ**
  モデルは何も覚えていません。aibow が発言を DB に保存し、送信のたびに並べ直して読ませています(会話の上限を超えたら compact で収めたもの)。
  会話を切り替えても、モデルを入れ替えても、続きを話せるのはそのためです。

- **設定の画面の「モデルに渡した文字列」**
  会話が `<|im_start|>user …<|im_end|>` という書式の1本の文字列になっていて、最後が `<|im_start|>assistant` で終わっています。
  モデルはこの「続き」を書いているだけです。送信のたびに会話全部が入っていることも分かります
  (会話の上限を超えて compact したあとは、要約が system の後ろに入り、古い発言が外れた形になります)。
  過去の返事の思考は保存されていて画面で開けますが、この文字列には入っていません(Qwen3.5 の公式テンプレートと同じ)。
- **「思考する」のオン/オフ**
  オフにすると、文字列の最後に空の `<think></think>` が入ります。モデルは「考え終わった」と思い込んで、すぐ答え始めます。
- **統計行**
  `モデル名 ・ 初回応答 ○s ・ プロンプト ○ tok(再利用 ○)○s ・ 生成 ○ tok ・ ○ tok/s` の形式で出ます。
  プロンプトを読む速さと、1トークンずつ生成する速さが大きく違うことが分かります。
  「再利用」は KV キャッシュ(前回読み終えた部分の計算結果)を使い回せたトークン数です。
  Qwen3.5 は一部の層が途中まで巻き戻せない仕組みのため、多くの場合 0 になります。
- **モデルの切り替え**
  読み込み時間、生成速度、答えの質がモデルの大きさでどう変わるか。設定の画面で GPU に載せる層の数を減らすと、どれくらい遅くなるか。
  会話の上限・返事の上限を変えたときは、モデルの読み込み時間が変わらない(重みは読み直さず、作業領域だけ作り直している)ことも分かります。
- **ターミナルのログ**(`wails3 dev` で起動したとき)
  起動時の計算装置とモデル一覧、1回ごとのトークン数・速度・終了理由、compact したこと(方式・前後のトークン数・秒数)が出ます。
